# invoice-lines · 金额分解

**一句话**：一笔钱拆开 —— 原价 → 各减项／加项 → 实付，**每行读得出「为什么」**；实付加粗放大、均摊写在它的副语里。另一形态给**纯 CSS 瀑布条**，「省了多少」在形状上看得见。

**形态**：本件落地**形态 A「逐行分解 ＋ 收口」**与**形态 D「瀑布条」**——出处＝原型墙 `.scratch/ui-组件墙/parts-11-加量池.mjs` 的 `.c-p7-lines` 与 `.c-p7-wfbar`。

**这一件是重做件**（原型 3/3/3）。改掉的是什么：原型读起来像一摞普通账目行（一列标签对一列金额），**每行说不出「为什么」**。重做后 ① 减项／加项的**原因成了必填**（说不出原因直接 `badInput`）；② 从原价到实付读成**一条链**：逐级**缩进**＋一道左竖线，实付由一条**重线**收口、**加粗放大**，均摊写进实付行的副语；③ 另一形态把「省了多少」做成**形状**（瀑布条）。

## 何时用它（选型三条）

| 你要的 | 用 |
|---|---|
| 一笔钱的**拆分**（原价／优惠／实付／均摊） | **本件** |
| 平铺读数（一列标签对一列值，没有加减关系） | `ledger-rows`（账目行） |
| 一条流水线走到了第几步 | `step-flow`（步骤条，未落地） |

**别用本件列清单**：这里讲的是「一笔钱怎么拆的」（一条减法链 ＋ 一个收口）；普通清单仍走账目行／明细行。

## 入参

| 字段 | 类型 | 缺省 | 说明 |
|---|---|---|---|
| `lines` | `InvoiceLine[]` | 必填 | 分行（下表几行走同一张表：`lines[].x`）。**第一行必须是 `base`**；至少两行 |
| `lines[].label` | `string` | 必填 | 这一行是什么（「原价 · 超市买菜」「店铺满减」）。**非空** |
| `lines[].amount` | `number` | 必填 | 金额（**正的量**，有限数且 > 0）。符号由 `kind` 定 |
| `lines[].kind` | `'base' \| 'cut' \| 'add'` | 必填 | 行类：`base` 原价（只许第一行）／`cut` 减项／`add` 加项 |
| `lines[].why` | `string` | 非 `base` 时必填 | **为什么**（「满 100 减 12，已达标」）。说不出原因的行一律拒 |
| `symbol` | `string` | `'¥'` | 钱符号 |
| `totalLabel` | `string` | `'实付'` | 实付那一行的名字 |
| `share` | `{ people; note? }` | — | 均摊到几人（写进实付行副语）；`people` 是 ≥ 2 的整数 |
| `share.people` | `number` | 必填（给了 `share` 时） | 几个人（≥ 2 的整数） |
| `share.note` | `string` | — | 除不尽时那句补充；不给＝本件按「除不尽」算一句 |
| `note` | `string \| string[]` | — | 口径行。串＝一句话；数组＝分段 |
| `form` | `'chain' \| 'waterfall'` | `'chain'` | 形态键（闭集；闭集外一律 `badInput`） |
| `extraClass` | `string` | — | 附加类名（空格分隔，逐个过类名正则） |

## 契约与不变量（判据逐条断）

1. **每行读得出「为什么」**：`kind` 是 `cut`／`add` 而没给 `why` ⇒ `badInput`。样式里，那一行左端还会点出「为什么减」／「为什么加」，原因整行独占（不挤在行尾）。
2. **一条链的形状**：减项／加项逐级**缩进**（`INVOICE_LINES_INDENT_PX`＋左竖线），实付行由**重线**（`INVOICE_LINES_RULE_PX`）收口、字号 `fs-h3 × INVOICE_LINES_TOTAL_SCALE`（加粗放大）。
3. **账由本件算**：实付 ＝ 原价 − 减项合计 ＋ 加项合计；副语里的「比原价少 ¥34.00」「合 8.04 折」都是算出来的，调用方不传。减项超过原价 ⇒ `badInput`（不静默出一个负的实付）。
4. **均摊写在实付那一行的副语里**（不另开一块）；除不尽时**说清差的那几分钱去哪了**，不四舍五入糊过去。
5. **瀑布条是纯 CSS**：段宽 ＝ 该段金额 ÷ 条长满分（**满分 ＝ 原价 ＋ 加项合计**，所以减项与实付合起来正好铺满，加项自己抬高了起点）；窄于 `INVOICE_LINES_SEGMENT_MIN_PCT` 的段不写字，**金额仍然在图例里逐行出** —— 关键语义（金额）任何一档都不被截断。
6. **色不是唯一信息**：减项是 `−` ＋ 缩进 ＋ 左竖线，加项是 `＋` ＋ 缩进 ＋ 左竖线，实付是重线 ＋ 加粗放大 —— 把强调色换成墨黑，三类行照样分得开。
7. **零阴影下层次仍在**：链靠缩进与发丝线、收口靠一条重线、条靠实色块，样式段里**不出现 `box-shadow`**。
8. **金额只有一条排法**：`formatInvoiceAmount`（两位小数 ＋ 千分位 ＋ 自算不依赖 locale）；数字 `font-variant-numeric: tabular-nums`，同一条链上下对齐。
9. **样式只经 `skinVar()`**：不写手抄的 `var(--ilife-…)`、不写 `:root`／`!important`、不新增 token 名；scope 在 `.<prefix>page-ui` 之下；宽度只判容器（`@container`）。

## 常见错法

- 优惠行只写金额、不写原因 —— 读者不知道为什么减，下次还踩同一个坑（本件把 `why` 变成必填）；
- 把本件当普通账目行用（平铺一列标签对一列值）—— 那是 `ledger-rows` 的活；
- 让调用方把「实付」「合几折」「每人多少」算好传进来 —— 同一个事实两处算，偏差无处可查；
- 把均摊另开一块计算区 —— 读者从实付那行读不出「我该掏多少」；
- 让细段自己撑开写金额（把条挤变形）—— 窄段不写字，金额走图例。

## 关系

- 用在哪：记账（原价／优惠／实付／均摊）／私家大厨（买菜清单预估价）。
- 样式由页面按需挂 `invoiceLinesCss()`（加法式：不调它、不挂 `.ilife-page-ui` 的页零命中）。
- 本件不带运行时（没有交互，瀑布条是纯 CSS）。
