## 一、架构层：固定枚举 / 查找表 / 自由文本列

问题：分类的二级三级、账户名、备注标签这些字段，到底该做成硬编码闭集、查找表外键，还是自由文本列？下面是三种做法在**一手文档里被官方自己写明的代价**。

### 1.1 PostgreSQL：`enum` 是「static, ordered set」，官方自陈三条限制

PostgreSQL 对 enum 的定义与限制写在同一节里（8.7 Enumerated Types）：

- 定义：`"Enumerated (enum) types are data types that comprise a static, ordered set of values."`（来源：https://www.postgresql.org/docs/current/datatype-enum.html §8.7）
- 排序不是字典序，而是声明顺序：`"The ordering of the values in an enum type is the order in which the values were listed when the type was created."`（同上 §8.7.2 Ordering）
- **官方对适用场景的自我限定，以及「加值可以、改名可以、删值不行」**：
  `"Although enum types are primarily intended for static sets of values, there is support for adding new values to an existing enum type, and for renaming values (see ALTER TYPE). Existing values cannot be removed from an enum type, nor can the sort ordering of such values be changed, short of dropping and re-creating the enum type."`（同上 §8.7.4 Implementation Details）
- 大小写敏感、空格也算数：`"Enum labels are case sensitive, so 'happy' is not the same as 'HAPPY'. White space in the labels is significant too."`（同上）
- 两个 enum 类型之间**不能直接比较**，要显式转 text：`ERROR: operator does not exist: mood = happiness`（同上 §8.7.3 Type Safety）

`ALTER TYPE` 一节把「加值／改名」的具体代价也写明了：

- 加值有事务可见性问题：`"If ALTER TYPE ... ADD VALUE (the form that adds a new value to an enum type) is executed inside a transaction block, the new value cannot be used until after the transaction has been committed."`（来源：https://www.postgresql.org/docs/current/sql-altertype.html "Notes"）
- 加值可能让比较变慢，且**官方给的解法是「删掉重建整个类型，或者 dump/restore 整个库」**：
  `"Comparisons involving an added enum value will sometimes be slower than comparisons involving only original members of the enum type. ... The slowdown is usually insignificant; but if it matters, optimal performance can be regained by dropping and recreating the enum type, or by dumping and restoring the database."`（同上）
- 改名是**原子且不可冲突**的：`"This form renames a value of an enum type. The value's place in the enum's ordering is not affected. An error will occur if the specified value is not present or the new name is already present."`（同上 `RENAME VALUE`）
- 加值有幂等开关，否则重复即报错：`"If IF NOT EXISTS is specified, it is not an error if the type already contains the new value: a notice is issued but no other action is taken. Otherwise, an error will occur if the new value is already present."`（同上 `ADD VALUE`）
- `ALTER TYPE` 的语法清单里**没有任何「删除单个枚举值」的子句**（只有 `ADD VALUE`、`RENAME VALUE`、`RENAME TO`、`OWNER`、`SET SCHEMA`、`SET (...)`）（同上 "Synopsis"）——这与 8.7.4「Existing values cannot be removed」互为印证。

**要点**：PostgreSQL 官方文档自己把 enum 定位成「静态集合」，并且承认取值一旦要删/要重排，代价是「drop 掉重建类型」甚至「dump/restore 整库」。它没有一句话说「取值会增长就别用 enum」——**这个判据是我们从上面三条限制推出的**（推论，依据：上述 8.7.4 与 ALTER TYPE Notes 原句）。

### 1.2 PostgreSQL 的另一条路：查找表 + 外键约束

PostgreSQL 官方对「值必须存在于另一张表里」这件事的标准机制是外键约束：「A foreign key constraint specifies that the values in a column (or a group of columns) must match the values appearing in some row of another table.」（来源：https://www.postgresql.org/docs/current/ddl-constraints.html §5.5.5 Foreign Keys）

**没查到**：PostgreSQL 官方文档（`datatype-enum.html`、`ddl-constraints.html`、`sql-altertype.html` 三页）里**没有**一句把「enum 类型」与「查找表/lookup table」并列比较、或推荐后者的话；`wiki.postgresql.org/wiki/Don%27t_Do_This`（本次采集）也没有找到 ENUM 条目。也就是说「用 enum 还是用查找表」这个取舍，**PostgreSQL 官方没有给判据**，只能从 1.1 的限制推。

### 1.3 MySQL：`ENUM` 是列定义里的取值清单，代价在排序与非法值

- 定义与定位：`"An ENUM is a string object with a value chosen from a list of permitted values that are enumerated explicitly in the column specification at table creation time."`（来源：https://docs.oracle.com/cd/E17952_01/mysql-8.0-en/enum.html §13.3.5 The ENUM Type）
- 官方列出的优点只有两条：存储紧凑、查询输出可读（`"Compact data storage in situations where a column has a limited set of possible values."` / `"Readable queries and output."`，同上）。
- 官方自己列的「potential issues」是：数字样子的取值会与内部索引混淆；`ORDER BY` 要当心（同上）。
- 排序按索引号而非字典序：`"ENUM values are sorted based on their index numbers, which depend on the order in which the enumeration members were listed in the column specification. For example, 'b' sorts before 'a' for ENUM('b', 'a')."`（同上 Enumeration Sorting）
- 非法值写不进去这件事**取决于 strict SQL mode**：`"If you insert an invalid value into an ENUM (that is, a string not present in the list of permitted values), the empty string is inserted instead as a special error value. ... If strict SQL mode is enabled, attempts to insert invalid ENUM values result in an error."`（同上 Empty or NULL Enumeration Values）
- 成员上限与重复成员：`"An ENUM column can have a maximum of 65,535 distinct elements."`；`"Duplicate values in the definition cause a warning, or an error if strict SQL mode is enabled."`（同上）
- 该节**没有出现任何「重命名单个成员」的语法**：取值是「在列定义里枚举」的，要知道有哪些取值，官方给的办法是 `SHOW COLUMNS FROM tbl_name LIKE enum_col` 然后**解析 `Type` 列里的 ENUM 定义文本**（同上 Handling of Enumeration Literals）。

**没查到**：MySQL 8.0 手册的 ENUM 一节里**没有**「取值可能会变，所以别用 ENUM、改用查找表」这类建议；它给的是「排序要小心」「别用数字当取值」两条告警。**推论**（依据：上面「成员写在列定义里、无改名语法、解析定义文本才能枚举取值」三句）：MySQL 的 ENUM 里改一个成员名＝重写列定义，且**没有**「成员重命名不会影响语义」的官方保证。

### 1.4 SQLite：**没有** ENUM 类型，只有 type affinity + CHECK 约束

- 官方对「没有的类型」的写法（以布尔、日期时间为范例）：`"SQLite does not have a separate Boolean storage class."`、`"SQLite does not have a storage class set aside for storing dates and/or times."`（来源：https://www.sqlite.org/datatype3.html §2.1、§2.2）。存储类只有五种：NULL / INTEGER / REAL / TEXT / BLOB（同上 §2）。
- 类型只是「建议」，不是约束：`"The type affinity of a column is the recommended type for data stored in that column. The important idea here is that the type is recommended, not required. Any column can still store any type of data."`（同上 §3 Type Affinity）
- 亲和性的判定规则（按顺序，命中即止）：`"If the declared type contains the string "INT" then it is assigned INTEGER affinity."` → 含 `"CHAR"`/`"CLOB"`/`"TEXT"` → TEXT → 含 `"BLOB"` 或未声明 → BLOB → 含 `"REAL"`/`"FLOA"`/`"DOUB"` → REAL → **`"Otherwise, the affinity is NUMERIC."`**（同上 §3.1 Determination Of Column Affinity）
- **推论**（依据：上一条规则、以及官方示例表把 `BOOLEAN`/`DATE`/`DATETIME` 都判成 NUMERIC，同上 §3.1.1）：在 SQLite 里声明 `ENUM('a','b')` 这个类型名，不含 INT/CHAR/CLOB/TEXT/BLOB/REAL/FLOA/DOUB 任何子串，**落进最后一条规则拿到 NUMERIC 亲和性**——它既不是枚举，也没有任何取值约束，只能靠别的手段（见下）拦住自由文本。
- SQLite 官方的动态类型是有意为之：`"Flexible typing is a feature of SQLite, not a bug."`（同上 §1）
- 官方为此提供了 STRICT 表来「刚性类型检查」：`"As of version 3.37.0 (2021-11-27), SQLite provides STRICT tables that do rigid type enforcement, for developers who prefer that kind of thing."`（同上 §1；细则见 https://www.sqlite.org/stricttables.html）

**没查到**：SQLite 官方文档里**不存在 ENUM 数据类型**——`datatype3.html` 的五种存储类、五种亲和性、以及 §3.1.1 的类型名示例表里都没有 ENUM（查了 https://www.sqlite.org/datatype3.html 全文）。SQLite 官方在 `lang_createtable.html` 的目录里给出 `3.7. CHECK constraints` 与 `4. Constraint enforcement` 两节（来源：https://www.sqlite.org/lang_createtable.html），即 SQLite 路线的「闭集」只能靠 `CHECK` 约束或应用层校验；该页正文在本次采集里被截断，**CHECK 的逐字定义没抓到**。

### 1.5 框架层：Django 给出了唯一一句成文的判据，Rails 给出的是「加值只能往后追加」

**Django `choices`**（来源：https://docs.djangoproject.com/en/5.2/ref/models/fields/#choices）

- 定义与作用：`"A mapping or iterable in the format described below to use as choices for this field. If choices are given, they’re enforced by model validation and the default form widget will be a select box with these choices instead of the standard text field."`
- 强制层级在**应用层**：choices 由 model validation 强制；作为对照，同一个页面上的 `unique` 写的是 `"This is enforced at the database level and by model validation."`（同上）。**推论**（依据：这两句的措辞差）：`choices` 不产生数据库约束，绕过 ORM 直接写库不受它拦。
- **本报告最有用的一句成文判据**：`"Note that choices can be any sequence object – not necessarily a list or tuple. This lets you construct choices dynamically. But if you find yourself hacking choices to be dynamic, you’re probably better off using a proper database table with a ForeignKey. choices is meant for static data that doesn’t change much, if ever."`（同上）
  → 官方判据：**取值基本不变 → `choices`（应用层闭集）；取值会变 → 建一张表 + `ForeignKey`。**
- 顺序也算模型的一部分：`"A new migration is created each time the order of choices changes."`（同上）
- 枚举型 choices 强制取值不重复：`"The use of enum.unique() is enforced to ensure that values cannot be defined multiple times."`（同上 Enumeration types）

**Rails `ActiveRecord::Enum`**（来源：https://api.rubyonrails.org/classes/ActiveRecord/Enum.html）

- 定位：`"Declare an enum attribute where the values map to integers in the database, but can be queried by name."`
- 数组写法下**顺序即数据库里的编号**：`"Note that when an array is used, the implicit mapping from the values to database integers is derived from the order the values appear in the array. In the example, :active is mapped to 0 as it’s the first element, and :archived is mapped to 1. In general, the i-th element is mapped to i-1 in the database."`
- **官方给的加值纪律**：`"Therefore, once a value is added to the enum array, its position in the array must be maintained, and new values should only be added to the end of the array. To remove unused values, the explicit hash syntax should be used."`
- 也可以直接存字符串，官方写明代价：`"Finally it’s also possible to use a string column to persist the enumerated value. Note that this will likely lead to slower database queries"`
- 非法值默认直接抛错：`"By default, an ArgumentError will be raised when assigning an invalid value"`；`validate: true` 时改为保存前校验。
- **推论**（依据：上面「映射到整数」「只能往后追加」两句）：Rails enum 的取值是**代码里的常量**，加一个值＝改代码＋发版＋迁移；改名会动到「第 i 个元素映射到 i-1」这套编号。查找表路线加一个值是「插一行数据」，两者成本结构不同。

**Prisma**（来源：https://www.prisma.io/docs/orm/v7/prisma-schema/data-model/models）

- 官方把 enum 列为数据模型的一等原始类型，同时明确它**受连接器支持情况限制**：`"Enums (enum primitives) (if your connector supports Enums)"`（同上）。
- **没查到**：Prisma 官方文档里关于「改枚举成员会怎样」「取值会增长该用什么」的表述，本次没抓到。尝试并失败的入口：https://www.prisma.io/docs/orm/reference/prisma-schema-reference（正文在 `enum` 一节之前被截断）、https://www.prisma.io/docs/orm/v7/prisma-schema/data-model/models（同上）、https://www.prisma.io/docs/orm/v7/core-concepts/supported-databases/sqlite（SQLite 连接器页全文未提 enum）。因此 Prisma 这一格**不作为判据依据**。

### 1.6 查找表路线：外键就是「值必须存在于另一张表」的官方机制，且它自带改名/合并的钩子

PostgreSQL 侧的定义见 §1.2。SQLite 侧官方文档把外键的用途与代价写得很全（来源：https://www.sqlite.org/foreignkeys.html）：

- 用途：`"SQL foreign key constraints are used to enforce "exists" relationships between tables."`（§1）
- 判定式：`"The foreign key constraint is satisfied if for each row in the child table either one or more of the child key columns are NULL, or there exists a row in the parent table for which each parent key column contains a value equal to the value in its associated child key column."`（§1）
- **NULL 是逃生通道**：`"There is one exception: if the foreign key column for an entry in the track table is NULL, then no corresponding entry in the artist table is required."`（§1）
- **默认不生效**：`"Foreign key constraints are disabled by default (for backwards compatibility), so must be enabled separately for each database connection."`（§2）——约束是 opt-in 的，不开就只是文档里的约定。
- **改名与合并有现成的数据库机制**（§4.3 ON DELETE and ON UPDATE Actions）：`"adding an "ON UPDATE CASCADE" clause to the foreign key as shown below ... allow the user to update the artistid (the parent key of the foreign key constraint) column without breaking referential integrity"`；`"The "RESTRICT" action means that the application is prohibited from deleting (for ON DELETE RESTRICT) or modifying (for ON UPDATE RESTRICT) a parent key when there exists one or more child keys mapped to it."`；动作为 `"NO ACTION", "RESTRICT", "SET NULL", "SET DEFAULT" or "CASCADE"`，缺省是 `"NO ACTION"`。
- 改父表名字时子表定义会被改写：`"If an "ALTER TABLE ... RENAME TO" command is used to rename a table that is the parent table of one or more foreign key constraints, the definitions of the foreign key constraints are modified to refer to the parent table by its new name."`（§5）
- 删父表会先按外键清理：`"If foreign key constraints are enabled when it is prepared, the DROP TABLE command performs an implicit DELETE to remove all rows from the table before dropping it. ... If an immediate foreign key constraint is violated, the DROP TABLE statement fails and the table is not dropped."`（§5）

**推论**（依据：§4.3 两句 + §1 的「exists relationships」）：**「停用/删除一个词」在查找表路线是一个有语义的动作**——RESTRICT 会拦住有引用的删除，CASCADE 能把引用一起改写过去；而 enum 路线里 PostgreSQL 干脆没有删除单个取值的语法（§1.1），MySQL 只能重写列定义（§1.3）。这就是「登记表里的账户」与「纯字符串的分类二级三级」在机制上的分界。

## 二、词表治理：同义合并、重命名、停用

问题：如果二三级分类、账户名、备注标签允许「填一个库里没有的新值」，新值与老值迟早重复、写错、要改名。**权威系统是不是把「合并／改名／停用」当必备配套？** 下面四个平台的一手文档（官方 API 文档、官方政策页、官方帮助中心）自己给的答案。

### 2.1 Stack Overflow / Stack Exchange：同义名是一等对象，官方明说「不追溯、要能移除」

Stack Exchange 的公开 API 文档是官方文档（`api.stackexchange.com/docs`），它把 tag synonym 建模成一个独立类型：

- 这个类型是什么：`"This type represents a mapping from one tag to another, as part of a Stack Exchange sites tag synonym list."`（来源：https://api.stackexchange.com/docs/types/tag-synonym ；原文 `sites` 系官方页面笔误，逐字照抄）
- 字段就是「从哪个词到哪个词」＋使用计数：`applied_count`／`creation_date`／`from_tag`／`last_applied_date`／`to_tag`（同上）
- 查询入口：`"Returns all tag synonyms found on the site."`（来源：https://api.stackexchange.com/docs/tag-synonyms ）
- **官方写明的两条治理义务**：
  - 不追溯：`"Note that even if a tag has been designated a synonym of another tag, that tag may still appear on some older questions in the system."`（同上 type 页）
  - 可移除，且下游要同时吃下「新增」与「移除」：`"Applications should be able to gracefully handle both the introduction of synonyms and their removal."`（同上）
- **现场读数**（2026-10-13 采集 `https://api.stackexchange.com/2.3/tags/synonyms?site=stackoverflow&pagesize=5&order=desc&sort=creation`，HTTP 200）：真实返回的五条就是形如 `{"to_tag":"sql-server","from_tag":"sql-server-vnext"}`、`{"last_applied_date":1791371431,"applied_count":2,"to_tag":"vs-code","from_tag":"visual-studio-code"}`、`{"to_tag":"next.js15","from_tag":"nextjs-15"}` 的映射；`applied_count`＝这条同义名被实际套用的次数。

**没查到**：`https://stackoverflow.com/help/tag-synonyms` 与 `https://meta.stackexchange.com/help/tag-synonyms` 两个帮助页本次都返回 HTTP 403（Cloudflare 的 `Just a moment...` 挑战页）。因此「同义名由谁创建、怎么投票、多少个 `applied_count` 才显示」这一层**没有一手原文**；本报告只引 API 官方文档与 API 现场读数能证到的部分。是「没查到」，不是「不存在」。

### 2.2 Wikipedia：合并的收尾是「源名留重定向」，而「易混淆」与「同义」待遇相反

- 合并的标准动作（`Wikipedia:Merging`，信息页/政策页，`action=raw` 抓全文）：`"A merge or merger is the process of uniting two or more articles into a single article. It is done by copying some or all content from the source article(s) into the destination article and then replacing the source article with a redirect to the destination article."`（来源：https://en.wikipedia.org/w/index.php?title=Wikipedia:Merging&action=raw ）→ **合并的收尾是「源名留一个重定向」，不是删除源名。**
- 合并理由一节（`Reasons to merge articles`）分五个小节：`Duplicate`／`Overlap`／`Short text`／`Context`／`Insufficient notability`；其中 `Duplicate` 一节正文：`"Duplicate: There are two or more articles on the same subject and with the same scope, also known as redundant content forks. If the content fork was unjustified, the article created more recently should be merged into the older one."`（同上）→ **「同一东西被写了两遍」是合并的第一类理由，且判据是「同一主题＋同一范围」。**
- 不该合并的两条：`"The resulting article would be too long or "clunky"; The separate topics could be expanded into longer standalone (but cross-linked) articles."`（同上）→ **两个东西虽然像，但各自能独立长大时，正确做法是保留两个名字并互链，不是合并。**
- 删除一个重定向的代价（`Wikipedia:Redirect/Deletion_reasons`，从 `Wikipedia:Redirect` 转发而来）：`"a redirect may contain non-trivial edit history"`；`"if a redirect is reasonably old ... then it is possible that its deletion will break incoming links"`（来源：https://en.wikipedia.org/w/index.php?title=Wikipedia:Redirect/Deletion_reasons&action=raw ）
- 该页 `Reasons for not deleting` 的 K2：`"They would aid accidental linking and make the creation of duplicate articles less likely, whether by redirecting a plural to a singular, by redirecting a frequent misspelling to a correct spelling, by redirecting a misnomer to a correct term, by redirecting to a synonym, etc."`；K4：`"Deleting redirects runs the risk of breaking incoming or internal links."`（同上）→ **同义、拼写错误、单复数差异，官方判「留」而不是「删」。**
- 反过来，`Reasons for deleting` 的 D2：`"The redirect might cause confusion."`（同上，官方举例是把某人名重定向到另一个人）→ **「像但指的不是同一个东西」是删除理由。**

**要点**：同一份政策里，「同义／拼错」与「易混淆」被**分成两类**处理，方向相反。所以相似度检测只负责「提示候选」，判「合并还是分开」要看语义（推论，依据：上述 K2 与 D2 两句原文）。

### 2.3 Discourse：官方自己写「开放打标签必须配哪几件」

- **标签是首次使用时自动创建的**：`"Tags are created upon first usage."`（来源：https://meta.discourse.org/t/admin-guide-to-tags-in-discourse/121041 ，官方文档分类下、`created_by.username`＝`Discourse` 的主题）

- **同义名与合并是同一批能力，且已存在的名字被设为同义名时自动合并并改写全部引用**（官方 2.4.0-beta8 发布说明，作者 jomaxro、`"staff":true`、分类 `release-notes`）：`"Discourse now supports tag synonyms, as well as tag merging. Similar tags, common tag mis-spellings, colloquialisms, and more can now be combined into a single tag. - 自动打标签**不追溯**：`"This feature will not apply tags retroactively to existing topics."`（同上，与 2.1 的 SO 不追溯一致）

### 2.4 GitHub labels：只有改名与删除，没有合并

- 删除会**改到所有引用它的 issue/PR**：`"Deleting a label will remove the label from issues and pull requests."`（来源：https://raw.githubusercontent.com/github/docs/main/content/issues/using-labels-and-milestones-to-track-work/managing-labels.md ）
- 默认标签集里有一个 `duplicate`（官方默认标签表，同上）→ **「重复」被建模成一个标签值，而不是一个合并动作。**
- 改名只有操作步骤，没有语义说明：官方 reusable 片段只有 `"In the labels list, to the right of the label you want to edit, click **Edit**."` 与 `"Under "Label name", type a name for your label."`（来源：https://raw.githubusercontent.com/github/docs/main/data/reusables/project-management/edit-label.md 、https://raw.githubusercontent.com/github/docs/main/data/reusables/project-management/name-label.md ）
- **没查到**：GitHub 官方文档里没有一句说明「改名之后既有 issue 上的标签会怎样」「能不能把 A 合并进 B」。别把「官方没写」当成「官方反对」——只能记「没查到」（查询入口：上面的 raw 文档全文、`managing-labels` 页、两个 reusable 片段）。

### 2.5 对照：三件事在四个系统里的对应机制

| 机制 | Stack Overflow（tag synonyms） | Wikipedia（redirect/merge） | Discourse（tags） | GitHub（labels） |
|---|---|---|---|---|
| 新值怎么进词表 | 需要提名（细节没查到，帮助页 403） | 新页面名本身就是新值 | `"Tags are created upon first usage."`（121041） | 建标签（`managing-labels` 页） |
| 同义合并 | `from_tag`→`to_tag` 一等对象，带 `applied_count`（API type 页） | 合并后源名留 redirect（Merging 页） | 同义名＋自动合并并改写全部引用（135183） | **没查到**（无合并机制文档） |
| 改名 | 由合并／重命名后的名字体现 | 页面移动（move），旧名留 redirect | `Edit tag` 页改 `name`／`slug`（121041） | `Edit`→改 `Label name`（reusable） |
| 停用／删除 | 同义名可移除，下游要能吃下（type 页） | 删除有代价，同义重定向判「留」 | `Delete unused tags`（只删没人用的） | 删除会从所有 issue/PR 上摘掉 |
| 是否追溯旧数据 | 不追溯（type 页原句） | redirect 的目的就是让旧链接继续可用 | 自动打标签不追溯（121041） | 改名语义没查到 |

**要点**：四个权威系统里，**没有一个是「开放填写 ＋ 零配套」**：开放填写的那个（Discourse）同时给了同义名、改名、配额、权限、批量替换与「只删没人用的」；只做标签集的那个（GitHub）干脆把「重复」变成一个标签值而不是合并机制。放开自由填却不给合并出口的做法，在这四份一手文档里找不到先例（推论，依据：上表逐格出处）。

## 三、近义与易混检测：给「新值像不像老值」一个可复现的判据

要回答的是「用户填的新值与库里已有值像不像」能不能不靠感觉，而用**有名字、有章节、有数据文件**的规范算法判定。三份 Unicode 官方规范各自负责一段。

### 3.1 三层判据与它们的规范出处

| 层 | 判什么 | 规范与章节 | 算法名 |
|---|---|---|---|
| ① 归一化 | 两个写法是不是同一个值（全角/半角、宽度、兼容字符） | UAX #15《Unicode Normalization Forms》§1.1、§1.2 Table 1、§7 | `toNFC()`／`toNFKC()` |
| ② 易混字形 | 两个字面不同但看起来一样的值 | UTS #39《Unicode Security Mechanisms》§4 Confusable Detection | `skeleton(X)`／`internalSkeleton(X)` |
| ③ 标识符限形 | 这个值该不该被接受为「名字」 | UAX #31《Unicode Identifiers and Syntax》§1.3、§2 | `XID_Start`／`XID_Continue`、identifier caseless match（D147） |

三份规范的官方地址分别是 https://www.unicode.org/reports/tr15/ 、https://www.unicode.org/reports/tr39/ 、https://www.unicode.org/reports/tr31/ （本次采集版本：tr15-58／2026-08-12、tr39-34／2026-08-27、tr31-45／2026-09-01，均为 18.0.0 系列）。

### 3.2 UAX #15：归一化（哪一档折什么，官方给了警告）

- 四种形式（§1.2 Table 1）：`Normalization Form D (NFD)｜Canonical Decomposition`、`NFC｜Canonical Decomposition, followed by Canonical Composition`、`NFKD｜Compatibility Decomposition`、`NFKC｜Compatibility Decomposition, followed by Canonical Composition`（来源：https://www.unicode.org/reports/tr15/ §1.2）
- 两类等价（§1.1）：`canonical equivalence` 例 `Ç ↔ C+◌̧`、`가 ↔ ᄀ+ᅡ`；`compatibility equivalence` 例 `ℌ → H`、`① → 1`、`ｶ → カ`、`i⁹ → i9`、`¼ → 1/4`；`"Compatibility equivalence is a weaker type of equivalence between characters or sequences of characters which represent the same abstract character (or sequence of abstract characters), but which may have distinct visual appearances or behaviors."`（同上 §1.1）
- **NFKC 折掉什么**：`"Normalization Form KC additionally folds the differences between compatibility-equivalent characters that are inappropriately distinguished in many circumstances. For example, the halfwidth and fullwidth katakana characters will normalize to the same strings, as well as Roman numerals and their letter equivalents."`（同上）
- **官方警告（这条直接决定我们该选哪档）**：`"Normalization Forms KC and KD must not be blindly applied to arbitrary text. Because they erase many formatting distinctions ... They can be applied more freely to domains with restricted character sets."`（同上）
- 判据可复现（§7 Goal 1 Uniqueness）：`"Two equivalent strings will have precisely the same normalized form."`；`toNFC(x) = toNFC(y)`（canonical 等价）、`toNFKC(x) = toNFKC(y)`（compatibility 等价），且全部幂等（`toNFC(toNFC(x)) = toNFC(x)`）（同上 §7）
- 实现怎么自查（§9）：`"The Unicode Character Database supplies properties that allow implementations to quickly determine whether a string x is in a particular Normalization Form"`，即 `Quick_Check` 属性三值 `NO/YES/MAYBE`，官方并给测试数据 `NormalizationTest.txt`（同上 §9）→ **这件事有官方测试数据，可写成可复现的用例。**
- 一个边界：`none of the Normalization Forms are closed under string concatenation`（拼起来可能不再规范），但 `all of the Normalization Forms are closed under substringing`（同上 §1.4）→ 归一化要在**入库前对整值做**，不能只对片段做。

### 3.3 UTS #39 §4：易混字形检测（有分步算法、有数据文件）

- `internalSkeleton(X)` 四步（来源：https://www.unicode.org/reports/tr39/ §4 Confusable Detection）：`1. Convert X to NFD format, as described in [UAX15].` / `2. Remove any characters in X that have the property Default_Ignorable_Code_Point.` / `3. Concatenate the prototypes for each character in X according to the specified data, producing a string of exemplar characters.` / `4. Reapply NFD.`
- 双向文本要另走一版：`bidiSkeleton(𝑑, X)` 按 UBA 重排（`up to and including L2`）、`Apply rule L3 of the UBA: move combining marks after their base`、`Replace any character whose glyph would be mirrored by rule L4 of the UBA by the value of its Bidi_Mirroring_Glyph property`，再做 `internalSkeleton(R″)`（同上）
- **判据（这就是「像不像」的可复现定义）**：`"The strings X and Y are defined to be 𝑑-confusable if and only if bidiSkeleton(𝑑, X) = bidiSkeleton(𝑑, Y). This is abbreviated as X ≒ Y (𝑑)."`；`"the operation skeleton is defined as skeleton(X) = bidiSkeleton(LTR, X). The strings X and Y are then defined to be confusable if and only if skeleton(X) = skeleton(Y). This is abbreviated as X ≅ Y."`（同上 §4）
- 数据文件：`confusables.txt`（条目形如 `0441 ; 0063 ; MA # ( с → c ) CYRILLIC SMALL LETTER ES → LATIN SMALL LETTER C`，`MA` 是类型字段）（同上 §4 与数据文件节）
- 三个冲突类别（§4.1／§4.2 与 Definitions）：`"Confusables are divided into three classes: single-script confusables, mixed-script confusables, and whole-script confusables ... All whole-script confusables are also mixed-script confusables."`
- **代价一：会误报**（传递性带来的）：`"This mechanism imposes transitivity on the data, so if X ≒ Y (𝑑) and Y ≒ Z (𝑑), then X ≒ Z (𝑑). ... That means that in some cases the test may be overly inclusive."`（同上 §4）→ 它适合**提示**，不适合**自动判等**。
- **代价二：skeleton 不是持久值**：`"they are not stable across versions of Unicode, so that they can only be interchanged between systems that use the same version of Unicode to compute bidiSkeleton. If they are stored, they must be recomputed when updating the version of Unicode used ... They should be thought of as an intermediate processing form, similar to a hashcode."`（同上）→ **不要把它当哈希存进库当唯一键**；要存就存归一化后的值，skeleton 现算。
- 另有整体限制档：混合文字检测（§5.1，`"A string is defined to be mixed-script if its resolved script set is empty"`）与限制级别五档（§5.2：`1. ASCII-Only`／`2. Single Script`／`3. Highly Restrictive`／`4. Moderately Restrictive`／`5. Minimally Restrictive`）；一般安全档 §3.1 写作 `C′ = (C ∩ {Identifier_Status=Allowed}) ∪ **Exception**`，并提示 `"Restricted characters should be treated with caution when considering possible use in identifiers, and should be disallowed unless there is good reason to allow them"`（同上 §3.1／§5.1／§5.2）。

### 3.4 UAX #31：显示与比较分开，「比较用算法」官方给了名字

- **显示格式与比较格式分开**（§1.3 Display Format）：`"Implementations may use a format for displaying identifiers that differs from the internal form used to compare identifiers."`；`"**Case.** The display format retains case differences, but the comparison format erases them by using Case_Folding."`；`"**Variants.** The display format retains variant distinctions, such as halfwidth versus fullwidth forms ... but the comparison format erases them by using NFKC_Casefold. Thus "A" and its full-width variant "Ａ" would be treated as the same identifier internally."`（来源：https://www.unicode.org/reports/tr31/ §1.3）
- **比较算法名与定义（要引的那一条）**：`"An implementation of [UAX31-R4] and [UAX31-R5] (Equivalent Case and Compatibility-Insensitive Identifiers) that compares identifiers under the identifier caseless match defined by D147 ..., that is, canonical decomposition (NFD) followed by the toNFKC_Casefold operation, ignores Default_Ignorable_Code_Points."`（同上 §2）
- 名字的字符合法性有现成属性：`[UAX31-D1] Default Identifier Syntax: <Identifier> := <Start> <Continue>* (<Medial> <Continue>+)*`；`XID_Start`／`XID_Continue` 由 `ID_Start`／`ID_Continue` 经 §5.1 NFKC Modifications 派生，`"They are recommended for most purposes, especially for security, over the original ID_Start and ID_Continue properties."`（同上 §2）
- **归一化档位怎么选**（§5.1.3 Identifier Closure）：`"If an implementation that uses this profile relies on identifier closure under normalization, it should conform to [UAX31-R4] using NFC, not NFKC."`（同上）→ 与 3.2 的 NFKC 警告是同一个取舍：**要封闭性就用 NFC，要折叠全角/兼容字形就用 NFKC_Casefold 做比较键**。
- 一条负面参照（§3 Immutable Identifiers）：允许未分配字符的不可变标识符 `"cannot be compared for NFC, NFKC, or case-insensitive equality"`，且 `"are unsuitable for restrictions such as those in UTS #39"`（同上 §3）→ **「永不改名的字符串」与「能做相似检测」不可兼得。**
- **没抓到**：§5 正文（`R4. Equivalent Normalized Identifiers`／`R5. Equivalent Case-Insensitive Identifiers`／`R6. Filtered Normalized Identifiers`／`R7. Filtered Case-Insensitive Identifiers`／`R1b. Stable Identifiers`／`R8. Hashtag Identifiers` 的逐字条款）在抓取时被截断，只拿到目录与别处转引；上面引的 R4／R5 内容出自 §2 的转述句，条款号可查但条款原文本次没读到。

### 3.5 落到我们这套词表：可复现的三步（推论）

以下是把上面三节拼成一条流水线的**推论**（依据：3.2–3.4 的原文）：

1. **入库前归一化**：对整值做 `toNFKC()`（把全角、兼容字形折叠掉；中文标签正是「输入法全角／半角混用」的重灾区），把归一化后的值**存进库**并作为比较键（依据：UAX #15 §1.1／§7 `toNFKC(x) = toNFKC(y)` 与 §1.4「拼接不封闭」）。
2. **提示候选，不自动判等**：拿 `skeleton()` 比对（数据文件 `confusables.txt`）＋ `skeleton` 之外的编辑距离排序，把「像不像」做成**建议列表**；因 §4 自陈 `may be overly inclusive`，判等仍要人点头（依据：UTS #39 §4 判据句与代价句）。
3. **限形＋长度上限**：接受为「名字」的值限定在 `XID_Start`／`XID_Continue`（或我们自己更窄的白名单），并给长度上限；这样才挡得住「不可见字符」「纯符号」「超长串」（依据：UAX #31 §2 `XID_Continue` 建议句与 §3 的负面参照；长度上限的现实先例见 Discourse `max_tag_length`，来源 121041）。

## 四、同一概念两套词表：账户与分类是不是同一类东西

现象：本仓把「分类」存成 `bills.category` 的字符串（三段 `一级/二级/三级`），把「账户」也存成 `bills.account` 的字符串，**但另有一份登记表** `goals.json` 的 `accounts` 行。同一概念两套词表，官方文档有没有说法？

### 4.1 判据一：外键管的是「必须存在于另一张表」，enum 管的是「静态有序集」

- 外键的定义（PostgreSQL §5.5.5）：`"A foreign key constraint specifies that the values in a column (or a group of columns) must match the values appearing in some row of another table."`（来源：https://www.postgresql.org/docs/current/ddl-constraints.html §5.5.5）
- 外键的用途（SQLite §1）：`"SQL foreign key constraints are used to enforce "exists" relationships between tables."`，判定式为「child key 全 NULL，或父表存在对应行」（来源：https://www.sqlite.org/foreignkeys.html §1）
- enum 的定位（PostgreSQL §8.7.4）：`"Although enum types are primarily intended for static sets of values, there is support for adding new values to an existing enum type, and for renaming values (see ALTER TYPE). Existing values cannot be removed from an enum type, nor can the sort ordering of such values be changed, short of dropping and re-creating the enum type."`（来源：https://www.postgresql.org/docs/current/datatype-enum.html §8.7.4）
- **这两条合起来给的判据**：一个值如果**自身带属性、会被别的记录引用、可能被停用**，它就是一个「实体」，该走**登记表＋引用**；如果它只是「把记录归堆的名字」，该走**分类值**（推论，依据：上述两条原文 + §1.6 的 `RESTRICT`／`CASCADE` 引文）。

### 4.2 判据二：官方 migration 文档怎么写「改名会怎样」

改名一个**值**，在三个引擎里是三种不同的东西——这正是「两套词表」的成本差：

- PostgreSQL：有值级改名语法，且只改标签不动排序：`"This form renames a value of an enum type. The value's place in the enum's ordering is not affected. An error will occur if the specified value is not present or the new name is already present."`（来源：https://www.postgresql.org/docs/current/sql-altertype.html `RENAME VALUE`）→ **改名会被「新名已存在」挡住（防重复），且不产生重复值。**
- MySQL：`ENUM` 节的成员列表是**建表时**写死的，成员值按**序号**（index）存储，序号从 1 开始、空串错误值序号为 0：`"The elements listed in the column specification are assigned index numbers, beginning with 1."`、`"The index value of the empty string error value is 0."`（来源：https://docs.oracle.com/cd/E17952_01/mysql-8.0-en/enum.html §13.3.5）→ 该节**没有任何成员改名语法**，改成员列表＝重写列定义；又因为按序号存，顺序动了语义就动（官方为此建议 `"Specify the ENUM list in alphabetic order."`，同上 `Enumeration Sorting`）。
- SQLite：`ALTER TABLE` 的整个语法面里**没有「改某个值」这一层**，只有表/列改名与加列删列：`ALTER TABLE ... RENAME TO new-table-name`／`RENAME COLUMN column-name TO new-column-name`／`ADD COLUMN column-def`／`DROP COLUMN column-name`／`ALTER COLUMN column-name SET NOT NULL`／`DROP NOT NULL`（来源：https://www.sqlite.org/lang_altertable.html §1 Overview 的语法行）。该页 §8 标题就叫 `Making Other Kinds Of Table Schema Changes`，§9 标题是 `Why ALTER TABLE is such a problem for SQLite`（同上，正文截断）。
- **没抓到**：SQLite `lang_altertable.html` §8 `Making Other Kinds Of Table Schema Changes` 的十二步过程正文（抓取在 §1 之后被截断），所以「官方推荐怎么改表」只能引到节标题，不能引步骤。

### 4.3 判据三：本仓现场读数（只读核查）

- `bills` 表的 DDL：`category TEXT NOT NULL`、`account TEXT DEFAULT ''`、`ledger TEXT DEFAULT '生活'`、`note TEXT DEFAULT ''`（来源：`packages/skill-bill/src/fetch/db.ts:31-42`），并为 `time`／`category` 建了普通索引 `idx_bills_time`／`idx_bills_category`（来源：`packages/skill-bill/src/fetch/db.ts:68-69`）→ **四列都是纯文本列，没有任何约束指向另一张表。**
- 分类的一级是**代码里的闭集常量**：`EXPENSE_L1 = ['餐饮','居家','穿着','出行','玩乐','学习','健康','社交','宠物','其他']`、`INCOME_L1 = ['工资','奖金','兼职','投资','其他收入','退款']`、`SPECIAL_L1 = ['借贷','分期','转账']`（来源：`packages/skill-bill/src/shared/category.ts:17-21`）。
- 分类的校验是**只封一级、放开二三级**：`validateCategory` 只对 `l1Of(s)` 查白名单，未知即抛 `POLICY_BAD_CATEGORY`（`'未知 L1 分类：' + l1`），并限制「至多 L1/L2/L3 三级」「层级含空段」即抛（来源：`packages/skill-bill/src/shared/category.ts:46-63`；注释口径见 `:45`「须含 L1（允许 L1/L2/L3 三级 / 分隔）；旧数据无 / 视为 L1；未知 L1 阻断」）→ **二三级事实上是自由文本：写什么都过，重复也没人管。**
- 账户的登记表：`goals.json` 顶层有 `accounts` 键（来源：`packages/skill-bill/src/fetch/db.ts:250` 的 `BillGoals`），新增账户时写入的行是 `{ name, type, disabled: false, created_at }`（来源：`packages/skill-bill/src/account/accounts.ts:119`）→ **账户有属性（类型）、有一等停用位、有创建时间；分类没有。**
- 账户类型这一格**已有成文决定「保持自由文本」**：`packages/skill-bill/src/account/declaration.ts:9` 的既有决定被逐字转引为「类型 `text`（"银行卡／支付／信用"只是例子，用户可自造类型，select 会锁死）」（来源：`docs/skills/skill-bill/proto/t1269/README.md:121`）→ **新增账户的「类型」与分类二三级同属「开放」侧，而 #1269 的改法是「下拉＝固定枚举 ＋『其他（自己填）』兜底」（来源：`docs/skills/skill-bill/proto/t1269/条目对照-1269.md:20`）。**
- 候选列表的来源分两路：账户候选从登记表读（`loadGoals(goalsFile).accounts`，来源：`packages/skill-bill/src/help/candidateLists.ts:103`），分类候选从 `bills` 的取值频次排（`rankByFrequency(rows.map((row) => textOf(row, 'account')), limit)` 同件 `:136`；三列的口径注释见 `:14`）→ **账户的「真值」在登记表，分类的「真值」只在记录里。**

### 4.4 结论：不是同一类东西（推论）

依据 4.1–4.3：

- **账户＝被引用的实体**：它有一行、有属性（`type`）、有生命周期状态（`disabled`）、会被多笔记录指向。官方的对应机制是**查找表＋外键**（`"exists" relationships`，SQLite §1），以及删除时的 `RESTRICT`／改名时的 `CASCADE`（§1.6）。所以账户该走**引用槽**：选择器列登记表的行，「填新值」＝**建一行**，而不是往记录里塞一个没人管的字符串。
- **分类＝把记录归堆的名字**：一级是「值域固定、且被当成归类维度用」的那一层（本仓代码里就是常量白名单，`category.ts:17-21`），官方的对应机制是 **enum／choices 式的静态集合**（PostgreSQL §8.7.4；Django `choices` 的判据句见 §1.5）；二三级是「会随时间增长的长尾」（新店、新平台、新玩法），官方对应机制是**受控文本＋配套治理**。
- **两套词表本身不是病，缺的是「谁是主」与「变更出口」**：账户现在是「登记表 ＋ 记录里同名串」的**双写**，而记录里那一列没有外键约束（`account TEXT DEFAULT ''`，`db.ts:36`）也没有开关去校验；SQLite 官方对这件事的原话是约束**默认不生效**、必须逐连接打开（§1.6 引文）。所以「两套词表」要么补上约束／校验（让登记表当主），要么承认记录里的串只是文本（那就别指望它能被统一改名）。分类相反：它只有一套（记录里的串），所以「统一改名」在对它下手时是**数据清洗**问题，而不是引用完整性问题。

## 五、对我们四个决定的直接回答

| # | 决定 | 直接回答 | 一手依据 |
|---|---|---|---|
| ① | 哪些字段该闭、哪些该开 | **看这个值会不会随时间增长、会不会被别的记录指向、有没有属性与生命周期。** 会增长的长尾（分类二三级、备注标签、账户类型）→ 开放；自身带属性、会被引用、会被停用的东西（账户）→ 登记表＋引用；值域固定且被当成归类维度的那一层（分类一级、账本枚举）→ 闭集。**判据不是我拍的**：官方成文判据是 Django `"choices is meant for static data that doesn't change much, if ever."`（§1.5）与 PG `"primarily intended for static sets of values"`＋「删值要 drop 掉重建」（§1.1／§1.2）；反面是「取值会增长却用 enum」→ 官方解法是删掉重建或 dump/restore（§1.1 `ALTER TYPE` Notes）。 | §1.1、§1.2、§1.5、§4.1 |
| ② | 开放之后必须配的三件事 | **都有权威依据，且权威系统是三件一起给的**：<br>**(a) 同义合并**——SO 把 synonym 做成 `from_tag`→`to_tag` 的一等对象并带 `applied_count`，且要求下游能吃下「引入与移除」两种变化（§2.1）；Discourse 的发布说明把 `tag synonyms` 与 `tag merging` 一起发，已存在的名字被设为同义名时**自动合并并改写全部引用**（§2.3）；Wikipedia 的合并定义里，收尾动作就是「源名留 redirect」（§2.2）。<br>**(b) 改名**——Discourse `Edit tag` 页一处改 `name`／`slug`／`description`／`synonyms`（§2.3）；PG `RENAME VALUE` 原子改名、被「新名已存在」挡住、不动排序（§1.1、§4.2）；Wikipedia 的旧名靠 redirect 续命（§2.2）。<br>**(c) 停用／删除**——Discourse 只提供 `Delete unused tags`（只删没人用的，§2.3）；GitHub 的删除会从所有 issue/PR 上摘掉、改名语义官方没写（§2.4）；SQLite 的外键 `RESTRICT`／`CASCADE` 把「停用 vs 删除」变成有语义的选择（§1.6）；而两个平台的合并／自动打标签都**不追溯**旧数据（§2.1、§2.3）。<br>**结论：放开自由填却不给合并出口，在这四份一手文档里找不到先例**；配套最少是「合并＋改名＋停用（含只删没人用的守卫）＋配额/长度上限＋权限」（Discourse 的五件套，§2.3）。 | §2.1–§2.5、§1.6 |
| ③ | 相似检测用什么算法 | **归一化用 UAX #15 的 `toNFKC()`（存归一化后的值当比较键；`"Two equivalent strings will have precisely the same normalized form."` §3.2）；易混字形用 UTS #39 §4 Confusable Detection 的 `skeleton(X) = bidiSkeleton(LTR, X)`，判据是 `skeleton(X) = skeleton(Y)`，数据文件 `confusables.txt`（§3.3）；名字限形用 UAX #31 §2 的 `XID_Start`／`XID_Continue`，比较键的官方写法是「NFD ＋ `toNFKC_Casefold`」（identifier caseless match，D147，§3.4）。** 两条边界必须照抄官方警告：skeleton `may be overly inclusive`（只当提示，不自动判等）且 `not stable across versions of Unicode`（别当哈希存库）（§3.3）。 | §3.1–§3.5 |
| ④ | 账户与分类是不是同一类东西 | **不是。** 账户是**被引用的实体**：官方机制是查找表＋外键（`"exists" relationships`），自带改名/删除的语义钩子（`CASCADE`／`RESTRICT`）；本仓现场也已给了它属性与停用位（`type`／`disabled`，`accounts.ts:119`）。分类是**归类用的名字**：一级在本仓就是代码常量白名单（`category.ts:17-21`，未知即抛），官方对应 enum／`choices` 那类静态集合；二三级是长尾，对应「受控文本＋合并/改名/停用配套」。两套词表并存的真正风险不在「两套」，而在**记录里那一列没有约束**（`bills.account TEXT DEFAULT ''`）——SQLite 官方明说外键约束默认不生效、必须逐连接打开（§1.6）。 | §4.1–§4.4、§1.6 |
