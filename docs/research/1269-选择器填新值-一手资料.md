# t1269 · 选择器里填一个库里没有的新值：一手资料

## 0. 这份文档回答什么

现场：记账 HELP 页（视口 390×844）每个字段现在是「原生下拉（候选 ≤12）」或「自绘悬浮筛选面板（候选 >12）」；用户抱怨「库里没有的新值录不进去」。讨论中的方案是给选择器加一个「其他（自己填）」入口，让用户敲新值、原样写进记录。约束：页面是自绘控件体系（不用第三方 UI 库）、值会进 SQLite、之后按出现次数生成候选。

本文件只收一手来源：w3.org / whatwg.org / unicode.org / sqlite.org 的规范与官方文档，MDN 的参考页与 `mdn/browser-compat-data` 仓库（这两项是委派口径里点名的），以及产品官方域名或其官方文档仓库。二手博客、聚合站、AI 摘要一律不作依据。每条结论后面挂 `（来源：…）`。

## 一、规范层：可创建型选择器（creatable combobox）怎么定义

### 1.1 APG 把「能敲自由文本的 combobox」当成 combobox 的两种形态之一

APG 对 combobox 的定义与分类（原文关键句）：

- "A combobox is an input widget that has an associated popup."
- "If a combobox does not support text input, it is referred to as select-only, meaning the only way users can set its value is by selecting a value in the popup."
- "Alternatively, if a combobox supports text input, it is referred to as editable. An editable combobox may either allow users to input any arbitrary value, or it may restrict its value to a discrete set of allowed values, in which case typing input serves to filter suggestions presented in the popup."

（来源：https://www.w3.org/WAI/ARIA/apg/patterns/combobox/）

推论（本节唯一一句推论）：「用户可以敲一个候选里没有的新值」在 ARIA 体系里不是新控件，而是 **editable combobox**；它既不是 select-only combobox，也不是在 listbox 里多塞一个 option。

### 1.2 「允许任意值」对应哪一种 autocomplete

APG 的四种 autocomplete 形态里，能产生「敲进去的字符串成为值」的有两种：

- "No autocomplete: The combobox is editable, and when the popup is triggered, the suggested values it contains are the same regardless of the characters typed in the combobox."
- "List autocomplete with manual selection: … The character string the user has typed will become the value of the combobox unless the user selects a value in the popup."

（来源：https://www.w3.org/WAI/ARIA/apg/patterns/combobox/）

我们这种「候选按出现次数排序、敲了过滤」的形态对应 **list autocomplete with manual selection**：`aria-autocomplete="list"`，且**不选中弹出项时输入串就是值**。若面板里再放一行「新建…」，它不改变 autocomplete 语义（仍是 list），只是面板里多一个可选项。

### 1.3 输入框与列表的 ARIA 属性要求

APG 给出的必填/必设项：

- combobox 上要指向弹出层的 `aria-controls`；`aria-expanded` 在弹出层隐藏时为 `false`、显示时为 `true`，且 "elements with role combobox have a default value for aria-expanded of false"。
- `aria-autocomplete` 取 `none` / `list` / `both`。
- 弹出层若是 `listbox`，被选中的候选项要置 `aria-selected="true"`；焦点在列表里移动时用 `aria-activedescendant` 或真实焦点，两者都要保证 `aria-controls` 仍指向弹出层。
- combobox 可用 `aria-required="true"` 表示必填；标签走 `<label>` / `aria-labelledby` / `aria-label`。
- 键盘：Down Arrow 打开弹出层并移入列表；弹出层打开时 `Esc` 关闭。

（来源：https://www.w3.org/WAI/ARIA/apg/patterns/combobox/）

两条硬警告：

- "IMPORTANT: Ensure JavaScript does not interfere with browser-provided text editing functions by capturing key events for the keys used to perform them."
- "The most robust approach for providing text editing functions is to rely on browsers, which supply them for HTML inputs with type text and for elements with the contenteditable HTML attribute."

（来源：https://www.w3.org/WAI/ARIA/apg/patterns/combobox/）

APG 自带的示例（无 autocomplete 的可编辑 combobox）里，`role="combobox"` 打在 `input[type="text"]` 上，弹出层是 `ul[role="listbox"]`，候选项是 `li[role="option"]` + `aria-selected`；示例页顶部注明 "There may be support gaps in some browser and assistive technology combinations, especially for mobile/touch devices."

（来源：https://www.w3.org/WAI/ARIA/apg/patterns/combobox/examples/combobox-autocomplete-none/）

### 1.4 「自绘」这条路在 ARIA 规范里的合法写法

ARIA in HTML 的一致性表里，`input type=text|search|tel|url|email`（或缺失/非法 type）**带 `list` 属性**时的隐式角色是 `combobox`，作者可用的角色只有：

> No `role` other than `combobox`, which is NOT RECOMMENDED.

同表还写：带 `list` 的 input 上 "Authors SHOULD NOT use the `aria-haspopup` attribute on the indicated `input`s with a `list` attribute."

而不带 `list` 的 `input type=text` 隐式角色是 `textbox`，**允许**的作者角色里含 `combobox`（以及 `searchbox`、`spinbutton`）。也就是说：想自绘弹出列表（不依赖 `<datalist>`）时，把 `role="combobox"` 打在一个普通文本 `input` 上是规范允许的写法。

（来源：https://w3c.github.io/html-aria/）

**没查到（明确记录）**：WAI-ARIA 1.2 规范本体里 `combobox` 角色定义（§5.4）与 `aria-autocomplete` / `aria-expanded` 的属性定义（§6.x）原文，我未能取到。`https://www.w3.org/TR/wai-aria-1.2/` 抓取被页面长度截断（抓到的部分只到 §2 的术语与 §2.x，正文角色定义在截断点之后），换 URL 片段无效（同一页）。因此本节的规范依据只用 APG（W3C 自己的模式文档）与 ARIA in HTML（W3C 规范），不用二手转述代替 ARIA 1.2 原文。

## 二、`<input list=datalist>` 的真实可用性

### 2.1 规范/文档记录的行为

- 元素语义："The `<datalist>` HTML element contains a set of `<option>` elements that represent the permissible or recommended options available to choose from within other controls."
- 哪些控件吃它、吃法一致不一致："Only certain types of `<input>` support this behavior, and it can also vary from browser to browser."
- 值的来源是 option 的 `value` 属性："Each `<option>` element should have a `value` attribute, which represents a suggestion to be entered into the input. It can also have a `label` attribute, or, missing that, some text content, which may be displayed by the browser instead of `value` (Firefox), or in addition to `value` (Chrome and Safari, as supplemental text). The exact content of the drop-down menu depends on the browser, but when clicked, content entered into control field will always come from the `value` attribute."
- 它不是选择器、也不约束提交值："**Note:** `<datalist>` is not a replacement for `<select>`. A `<datalist>` does not represent an input itself; it is a list of suggested values for an associated control. The control can still accept any value that passes validation, even if it is not in this suggestion list."

（来源：https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/datalist）

「提交时怎么取值」= 取控件自己的值（用户敲什么就是什么），datalist 只提供建议列表、不做约束 —— 上一条最后一句即为此行为的一手表述。（来源：同上）

**没查到（明确记录）**：WHATWG HTML 规范 `form-elements.html` 里 §4.10.8 `datalist` 的规范原文（含「suggestions source element」与 UA 过滤建议的规则）。`https://html.spec.whatwg.org/multipage/form-elements.html` 抓取在 §4.10.7 `select` 一章内就被页面长度截断，datalist 在其后；单页版更大，同样不可达。因此「浏览器如何过滤建议项（子串匹配还是前缀匹配）」我**没有**规范原文，本文件不下结论。

### 2.2 各浏览器与移动端支持现状（`mdn/browser-compat-data` 仓库条目）

仓库路径与键名：`mdn/browser-compat-data` 的 `html/elements/datalist.json`，顶层键 `html.elements.datalist.__compat.support`。

（来源：https://raw.githubusercontent.com/mdn/browser-compat-data/main/html/elements/datalist.json）

| 浏览器 | 支持情况 |
| --- | --- |
| Chrome | `20` |
| Chrome Android | `33` |
| Edge | `12` |
| Firefox | `4` |
| **Firefox Android** | `79` 起为 **`partial_implementation: true`**，附注："The dropdown menu containing available options does not appear. See [bug 1535985](https://bugzil.la/1535985)."（`4`–`79` 为旧条目，已移除） |
| Internet Explorer | `10` |
| Opera | `9.5` |
| Safari | `12.1` |
| Safari on iOS | `mirror`（跟随 Safari 桌面数据 ⇒ `12.1`） |
| Samsung Internet / Android WebView / iOS WebView | `mirror` |

同文件的子特性条目（说明「支持」是分输入类型的）：`input_type_text` 为 Chrome `20`、Safari `12.1`、Safari iOS `mirror`；`input_type_date` 在 Firefox 为 `false`、Safari 为 `14.1`；`input_type_range` 在 Chrome Android 为 `57`、Firefox `110`、**Firefox Android 为 `false`**。（来源：同上）

即：**Firefox Android 上 datalist 的下拉根本不会出现**（这是 BCD 条目自己写的 `partial_implementation` 说明，不是我的推断）；iOS Safari 与 Chrome Android 在数据上支持，但 Firefox Android 这条使得「移动端可用」不能一律成立。

### 2.3 Baseline 状态与自绘体系最在意的限制

MDN 在该元素页顶部标注："Limited availability — This feature is not Baseline because it does not work in some of the most widely-used browsers." 并列出三条与该控件体系直接冲突的限制：

- 下拉列表里选项的字号不随页面缩放；
- "As targeting the list of options with CSS is very limited to non-existent, rendering cannot be styled for high-contrast mode."；
- "Some screen reader/browser combinations, including NVDA and Firefox, do not announce the contents of the autosuggest popup."

（来源：https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/datalist）

对「自绘控件体系、390×844 视口、要精确控制外观与对比度」的页面，这三条等于否决 datalist 当主路径。

### 2.4 `showPicker()`

`HTMLInputElement.showPicker()` 能主动弹出输入控件的选择器，且 "It can also be prepopulated with items from a `<datalist>` element or `autocomplete` attribute."

- Baseline：「Widely available。It's been available across browsers since September 2022.」
- 必须由用户动作触发：`NotAllowedError` "Thrown if not explicitly triggered by a user action such as a touch gesture or mouse click (the picker requires Transient activation)."
- 跨源 iframe 里抛 `SecurityError`（file 与 color 的选择器例外）；元素不是可变的（`readonly` 之类）抛 `InvalidStateError`。
- 特性检测：`if ("showPicker" in HTMLInputElement.prototype) { … }`

（来源：https://developer.mozilla.org/en-US/docs/Web/API/HTMLInputElement/showPicker）

**没查到（明确记录）**：`showPicker()` 的逐浏览器版本号。该 MDN 页的兼容表在抓取上限之外（页面在「Examples」中途被截断）。复核位置是 `mdn/browser-compat-data` 的 `api/HTMLInputElement.json` 中 `api.HTMLInputElement.showPicker.__compat.support` 键；我只拿到 Baseline 横幅这一句（「自 2022 年 9 月起」），不逐版本下结论。

要注意 `showPicker()` 并不能解决 2.2 里 Firefox Android 那条：它只是「主动触发选择器」，选择器本身在那些浏览器里不出现。

## 三、一线产品的官方文档怎么描述「新建一个选项」

### 3.1 GitHub（labels）：两步式表单，显式提交才入库

- 文案链路：标签页右上角按钮是 **New label**（"To the right of the search field, click **New label**."），弹窗里的输入字段是 **"Label name"**（"Under \"Label name\", type a name for your label."），提交按钮是 **Create label**（"To save the new label, click **Create label**."）。
- 作用域：标签属于仓库，跨仓库互不影响 —— "You can apply labels in the repository the label was created in. Once a label exists, you can use the label on any issue, pull request, or discussion within that repository. Addition, modification, or deletion of labels in one repository has no effect on labels belonging to other repositories."
- 新建权限：任何有 write 权限的人都能建（"Anyone with write access to a repository can create a label."）。
- 内置默认标签全是小写连字符（`good first issue`、`help wanted`、`wontfix`、`good first issue` 等），这是它们自己的命名惯例。

（来源：https://raw.githubusercontent.com/github/docs/main/content/issues/using-labels-and-milestones-to-track-work/managing-labels.md ；按钮与字段原文来自 https://raw.githubusercontent.com/github/docs/main/data/reusables/project-management/create-label.md 与 https://raw.githubusercontent.com/github/docs/main/data/reusables/project-management/name-label.md ）

⇒ GitHub 的范式是**两段式**：先建标签入仓库标签表，再用到 issue 上；不存在「在 issue 上敲一个新名字就地建标签」。

**没查到（明确记录）**：GitHub 对**重名**标签的规则。查了 https://docs.github.com/en/issues/using-labels-and-milestones-to-track-work/managing-labels （抓取在默认标签表处截断，创建/编辑章节原文已单独取到官方仓库版本，两处都没有重名说明）与 https://raw.githubusercontent.com/github/docs/main/content/rest/issues/labels.md （该页是自动生成页，只有 "About labels" 段落，端点描述不在其中）。GitHub 对重名到底报错还是拒绝，本文件不写。

## 四、值规范化与去重的权威依据

### 4.1 Unicode 规范化：四种形式的定义与警告（UAX #15）

- 四种形式："Normalization Form D (NFD): Canonical Decomposition"、"Normalization Form C (NFC): Canonical Decomposition, followed by Canonical Composition"、"Normalization Form KD (NFKD): Compatibility Decomposition"、"Normalization Form KC (NFKC): Compatibility Decomposition, followed by Canonical Composition"。
- 两类等价："The Unicode Standard defines two formal types of equivalence between characters: canonical equivalence and compatibility equivalence."
- 兼容等价会**删掉区别**：图例含 "Linebreaking differences: [NBSP] → [SPACE]"、"Width variants: ｶ → カ"、"Squared characters: ㌀ → アパート"、"Fractions: ¼ → 1/4"。
- 硬警告："Normalization Forms KC and KD must not be blindly applied to arbitrary text. Because they erase many formatting distinctions, they will prevent round-trip conversion to and from many legacy character sets…" 并把它类比为大小写映射："It is best to think of these Normalization Forms as being like uppercase or lowercase mappings: useful in certain contexts for identifying core meanings, but also performing modifications to the text that may not always be appropriate."
- 幂等与唯一性（"Goal 1"）：等价串的规范形唯一；`toNFC(toNFC(x)) = toNFC(x)` 一类恒等式成立。
- 但与我们的输入直接相关的两条边界：拼接不封闭（两个规范串拼起来未必是规范串）；"Text exclusively containing ASCII characters (U+0000..U+007F) is left unaffected by all of the Normalization Forms."、"Text exclusively containing Latin-1 characters (U+0000..U+00FF) is left unaffected by NFC."

（来源：https://www.unicode.org/reports/tr15/ ，Version Unicode 18.0.0 / Rev 58）

⇒ 对中文输入法产生的全角、兼容字符（例：`１` U+FF11、`㍿` 一类），NFKC 是有效折叠；但 4.1 的警告要求**只把它用在去重键上，不用它改写用户存进记录的原值**。

### 4.2 ECMAScript 侧的可用能力（`String.prototype.normalize`）

- "The **`normalize()`** method of `String` values returns the Unicode Normalization Form of this string."
- 形参："One of `\"NFC\"`, `\"NFD\"`, `\"NFKC\"`, or `\"NFKD\"`, specifying the Unicode Normalization Form. If omitted or `undefined`, `\"NFC\"` is used."；非法值抛 `RangeError`。
- 为什么需要它（也是「为什么不能拿裸串做去重键」的一手说明）："However, since the code points are different, string comparison will not treat them as equal."（例子是 `ñ` = U+00F1 与 `n` + U+0303，两者 `===` 为 `false`、`length` 不同）
- Baseline：「Widely available。It's been available across browsers since September 2016.」

（来源：https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/String/normalize ）

**没查到（明确记录）**：ECMA-262 规范本体里 §22.1.3.13 `String.prototype.normalize` 的算法原文。`https://tc39.es/ecma262/multipage/text-processing.html` 抓取只到全站目录（§7 之前）就被截断，单页版更大同样不可达。上表依据 MDN 参考页（委派口径点名允许的 MDN 文档）。

### 4.3 大小写折叠（case folding）能做到什么程度

ICU 官方文档的表述：

- "Case folding maps strings to a canonical form where case differences are erased. Using the case folding API, ICU supports fast matches without regard to case in lookups, since only binary comparison is required."
- 数据来源与性质："The CaseFolding.txt file in the Unicode Character Database is used for performing locale-independent case folding."；"Unicode case folding is not context-sensitive. It is also not language-sensitive, although there is a flag for whether to apply special mappings for use with Turkic (Turkish/Azerbaijani) text data."
- 与「完整大小写映射」的区别："case mapping … is language-sensitive (results may differ depending on language), and is context-sensitive (a character in the input string may map differently depending on surrounding characters)."，例：土耳其语的 `i` 对应 U+0130 `İ`。

（来源：https://unicode-org.github.io/icu/userguide/transforms/casemappings.html ）

NFKC + 折叠合成一步的官方公式出现在 UCD 的属性定义里（`DerivedNormalizationProps.txt` 头部对已废弃属性的定义）：

> Derived Property: FC_NFKC_Closure (DEPRECATED as of Unicode 6.0.0)
> …

### 4.4 SQLite 侧：能给的只有 ASCII 折叠，去重键必须应用层自己算

- 默认排序规则是 BINARY："Every column of every table has an associated collating function. If no collating function is explicitly defined, then the collating function defaults to BINARY."
- 三种内置排序规则的定义：**BINARY** "Compares string data using memcmp(), regardless of text encoding."；**NOCASE** "Similar to binary, except that it uses `sqlite3_strnicmp()` for the comparison. Hence the 26 upper case characters of ASCII are folded to their lower case equivalents before the comparison is performed. Note that only ASCII characters are case folded. SQLite does not attempt to do full UTF case folding due to the size of the tables required. Also note that any U+0000 characters in the string are considered string terminators for comparison purposes."；**RTRIM** "The same as binary, except that trailing space characters are ignored."
- 效果示例（官方例子）：在 `COLLATE NOCASE` 列上 `GROUP BY`，"Values 'abc', 'ABC', and 'Abc' are placed in the same group"；换成 `GROUP BY (d || '')` 就走 BINARY，三者分成 3 组。

（来源：https://www.sqlite.org/datatype3.html ，§7 Collating Sequences）

⇒ 用 `COLLATE NOCASE` 当去重键在中文/带音标文本上**不成立**（它自己写明只折 26 个 ASCII 字母、不做 full UTF case folding）。`RTRIM` 也只处理尾部空格，不做空白折叠。去重键只能在应用层算出来再存一列（或建唯一索引）。

### 4.5 产品侧的去重/规范化例子（一手）

- Notion：选项名**不能含逗号**（"Option names cannot contain commas."），这是编码方式倒逼的字符级约束。
- Linear：同名不报错、不同 team 的同名标签在视图层被当成同一语义；重复项用 merge 收拾；另有预留名清单（assignee/cycle/effort/estimate/hours/priority/project/state/status）。
- GitHub：标签的作用域是单个仓库（因此「去重」天然被作用域切碎成 per-repo），默认标签用小写连字符风格。

（来源：分别同上 3.3、3.2、3.1 各条）

## 五、对我们四个具体决定的直接回答

### ① 入口文案该用哪个词

**建议：`新建“<当前输入>”`（输入为空时写 `新建…` 并把焦点给输入框），不要用「其他（自己填）」。**

依据：

1. 三家可核到的官方文档，入口词都是「动作词 + 值本身」，不用兜底词：GitHub `New label` / `Label name` / `Create label`；Linear 在 `Add label` 流程里 "type the name of the label you want to create"；Notion 的表述是 "A new option name adds an option to the schema"。（来源：同 3.1 / 3.2 / 3.3）
2. ARIA 体系里没有「其他」这种角色：可敲自由文本这一路的规范名字是 editable combobox 的 list autocomplete with manual selection，值是「用户敲的字符串」而不是一个叫「其他」的候选。（来源：https://www.w3.org/WAI/ARIA/apg/patterns/combobox/ ）
3. 「其他」是缺席证据：在我取到原文的三家产品文档里没有出现这种兜底选项词（Airtable、Todoist 未取到，见 3.4/3.5，因此这条不是穷尽结论）。

配套要求（来自 1.3/1.4）：这一行是弹出层里的一个可选项，选中它等同于「把当前输入串当值提交」，不要为此改动 `role`；控件仍是 `combobox` + `aria-expanded` + `aria-autocomplete="list"`，键盘事件不要吃掉浏览器原生的文本编辑键。

### ② 新值该立即入选还是保存后入选

**建议：保存后入选**（先落成记录，再由「按出现次数生成候选」把新值算进候选池）。这不是规范问题，而是一手资料显示两种范式都存在，需要我们自己定：

| 范式 | 一手例子 |
| --- | --- |
| 写时即建（立即入选） | Notion select/multi-select："A new option name adds an option to the schema…"；Linear：在 `Add label` 流程里敲名字就建（workspace 或 team 级） |
| 提交才建（保存后入选） | GitHub：`New label` → 填 `Label name` → `Create label` 才入仓库标签表 |
| 写值不建（另一极端） | Notion status："A page write does not create a new status option or set its group." |

（来源：同 3.1 / 3.2 / 3.3）

选「保存后入选」的理由（**这段是我的推断，不是一手结论**）：本项目的候选是「按出现次数」生成的，未提交的输入不该计入次数；而 GitHub 的两段式说明「先落库、再使用」也是主流产品接受的做法。若最终选「立即入选」，一手资料里没有任何一家给出「用户敲了又取消」的回收机制，回收得我们自己设计（Notion status 那条说明同一产品里「可建/不可建」是按字段分开定的，所以这个决定可以逐字段定，不必一刀切）。

### ③ 移动端能不能用原生 datalist

**不能当主路径。** 兼容数据与官方限制：

- Firefox Android 上 `partial_implementation: true`，附注原文 "The dropdown menu containing available options does not appear. See bug 1535985." —— 即列表根本不弹；`input_type_range` 在 Firefox Android 为 `false`。（来源：https://raw.githubusercontent.com/mdn/browser-compat-data/main/html/elements/datalist.json ）
- iOS Safari `mirror`（随 Safari 桌面 `12.1`）、Chrome Android `33` 起支持 —— 数据上「能用」。（来源：同上）
- MDN 明说它不是 Baseline："Limited availability — This feature is not Baseline because it does not work in some of the most widely-used browsers."；且选项列表"CSS is very limited to non-existent"、字号不缩放、`NVDA` + Firefox 不播报弹出内容。（来源：https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/datalist ）
- `showPicker()` 只是主动触发的办法，它要求 transient activation（否则 `NotAllowedError`），跨源 iframe 抛 `SecurityError`；Baseline 自 2022 年 9 月起。（来源：https://developer.mozilla.org/en-US/docs/Web/API/HTMLInputElement/showPicker ）

结论：在「自绘控件体系、390×844、要控制外观/位置/对比度」的前提下，原生 datalist 只能作为**降级增强**（例如桌面端、或仅作输入建议），不能作为「填新值」这条路的唯一实现；主实现应是 1.4 允许的 `input` + `role="combobox"` + 自绘 `listbox` 弹出层。

### ④ 去重/规范化做到哪一步

**结论：存储保留原值；去重另算一键，键 = NFKC → 空白折叠（含首尾 trim）→ 大小写折叠；不要用 SQLite 的 NOCASE 当这个键。**

| 层级 | 做什么 | 一手依据 |
| --- | --- | --- |
| 存储 | 原样写入（不改写用户输入） | UAX #15 对 NFKC/NFKD 的警告："must not be blindly applied to arbitrary text"（来源：https://www.unicode.org/reports/tr15/ ） |
| 键 · 规范化 | `NFKC` | 兼容等价会折叠全角/宽度/合字等差异（`ｶ → カ`、`㌀ → アパート`）；ASCII 与 Latin-1 不受影响（来源：同上） |
| 键 · 空白 | trim + 连续空白折叠为单空格 | SQLite 只有 `RTRIM`（"trailing space characters are ignored"），文档没给全局空白折叠（来源：https://www.sqlite.org/datatype3.html ） |
| 键 · 大小写 | 与语言无关的大小写折叠 | ICU："Case folding maps strings to a canonical form where case differences are erased."、locale-independent、not context-sensitive（来源：https://unicode-org.github.io/icu/userguide/transforms/casemappings.html ） |
| 实现 | 浏览器里可用的是 `String.prototype.normalize()`（四形式，默认 `NFC`），大小写折叠需自己实现或用 `toLowerCase` 近似 | （来源：https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/String/normalize ） |
| 数据库 | 别指望 `COLLATE NOCASE`：它只折 ASCII 26 字母，"SQLite does not attempt to do full UTF case folding" | （来源：https://www.sqlite.org/datatype3.html ） |
| 产品侧参照 | Notion 的选项名不允许含逗号（编码倒逼的字符约束）；Linear 不拦同名、靠同名语义 + merge 收拾 | （来源：同 3.3 / 3.2） |

不建议做的：locale 感知的比较（ICU 说明完整大小写映射是 language-sensitive 与 context-sensitive，例：土耳其语 `i` ↔ `İ`）—— 我们只有中文场景，引入 locale 只会让同一串在不同设置下被折叠成不同键。

**没查到、因此不下结论的部分（汇总）**：WAI-ARIA 1.2 本体的 `combobox` 角色与 `aria-autocomplete`/`aria-expanded` 定义原文（一 1.4）；WHATWG HTML §4.10.8 `datalist` 原文与 UA 过滤建议的规则（二 2.1）；`showPicker()` 逐浏览器版本号（二 2.4）；GitHub 标签重名规则（三 3.1）；Airtable 与 Todoist 的全部官方说法（三 3.4/3.5）；`NFKC_CF` 属性名在 UCD 文件里的定义（四 4.3）；ECMA-262 §22.1.3.13 算法原文（四 4.2）。
