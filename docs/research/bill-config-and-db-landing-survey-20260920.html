1 · 一句话结论

记账技能不「记住」库在哪，它每次被调用时现读一份配置文件算出落点。那份配置文件是 ~/.ilife/bill.yaml（本机：C:\Users\辰辰洋洋\.ilife\bill.yaml），它是唯一真相——环境变量在 2026-09-19 的 #726 之后一个都不参与配置。链路是：命令 → 现读 bill.yaml → 算出绝对路径（顺手 mkdir -p）→ 用 node 内置的 node:sqlite 打开 → 缺表就 DDL 自愈。

而这次调查最重要的发现不在配置项里：技能现在读的是一份 0 行的库，你 2022-01-01 到 2026-09-16 的 7127 条记录躺在另一个目录里，当前的默认落点看不见它。见 第 7 节。

3 · 取库链路：从「记一笔」到打开 SQLite

你在对话里说一句「记一笔」，到 SQLite 文件被打开，中间是这 8 跳：

#发生了什么住哪
1DSH 侧把技能唯一出口开成一个 agent 工具 run_bill_command：不经会话 shell、不读 PATH，在宿主进程里 spawn 技能 CLI。源码 packages/plugin-bill-ilife/src/skill-tool.ts:20（工具名）、:101-117（执行）
2入口路径不写死：读技能包 package.json 的 bin 声明，挑名字以 -cmd-read 结尾那条；运行时用宿主自带的执行体（Electron 宿主＝该二进制加 ELECTRON_RUN_AS_NODE=1）。源码 skill-tool.ts:41-52、packages/plugin-bill-ilife/src/bridge.ts:82-85
3真正跑起来的是 packages/skill-bill/dist/cli/cmd_read.js，取一个 bill.* 命令键 ＋ --params JSON。源码 skill-tool.ts:108；出口契约见 packages/skill-bill/src/cli/cmd_read.ts:1-4
4出口先拦两类「设置页专用」键（配置读写、配置体检），再做预检——因为「读写配置」不该要求库已经配好。源码 cmd_read.ts:221-230；packages/skill-bill/src/cli/config.ts:66-84
5预检只剩一道门：node 版本 ≥ 22.13（node:sqlite 的要求）。老线那道「必须设 SKILLS_DB_PATH」已经整道删掉。源码 cmd_read.ts:53-56
6算落点：resolveDbPath() → 现读配置 → db.dir 非空即用它，空串＝配置数据目录（默认 ~/.ilife/data）→ join(目录, db.name)，并顺手把目录建出来（mkdir -p）。源码 packages/skill-bill/src/fetch/paths.ts:45-55
7现读配置那一步：定位配置目录 → 文件不在就按默认值落一份 → 在就解析＋校验＋把缺的项补默认值。源码 packages/skill-bill/src/config.ts:50-67、packages/base-link-core/src/config/store.ts:135-145
8开库：new DatabaseSync(路径)（node 内置 sqlite，无第三方依赖）→ PRAGMA journal_mode=WAL ＋ busy_timeout=5000 → CREATE TABLE IF NOT EXISTS bills（10 列）＋两个索引 → 老库缺 deleted_at 就 ALTER TABLE 补上。跑完 finally 里关库。源码 packages/skill-bill/src/fetch/db.ts:31-42（DDL）、:52-77（开库）、cmd_read.ts:147-158

两条容易忽略的性质

  • 「看帮助」不开库：HELP 在开库之前分派，初始化状态只看「库文件在不在」（源码 cmd_read.ts:62-77、:103-105）。但注意它仍会建目录——因为落点函数本身就带 mkdirSync。
  • 记账有两份「库」：SQLite 一份（biscuit_accountant.db，单表 bills）＋ JSON 一份（goals.json，装预算／储蓄目标／账户）。后者走「临时文件 ＋ 改名」的原子写（源码 fetch/db.ts:253-260）。

4 · bill.yaml 是什么机制（10 条口径）

#口径出处
1落点是 <配置目录>/bill.yaml；配置目录＝环境变量 ILIFE_CONFIG_DIR（设了且非空）否则 os.homedir()/.ilife。不读 $DSH_HOME——技能要能在没有 DSH 的平台上单独跑。源码 packages/base-link-core/src/config/dirs.ts:3,40-49,52-63
2配置文件是唯一真相，环境变量全部退役：老那套 SKILLS_DB_PATH、五个写库开关（*_FORCE_PROD）、两个钉钟变量读取点一个不剩。现在环境变量只剩两个角色：ILIFE_CONFIG_DIR（位置口子）与运行期继承类（PATH／NODE_OPTIONS）。文档 docs/env.md:3-9；记账侧落地读数 docs/skills/skill-bill/t726-证据.md:13-23（git grep process.env -- packages/skill-bill/src 零命中）
3格式是手写的受限 YAML 子集（全仓零 YAML 依赖）：一层嵌套、缩进恰好 2 个空格、不支持列表、标量只有字符串／数字／布尔。不支持的写法会给人话报错＋行号。源码 packages/base-link-core/src/config/yaml.ts:74-140（解析）、:45-67（形状校验）、:213-225（生成）
4写出去恒是完整一份：没给的项按默认值补齐 ⇒ 盘上的文件永远只有默认值表那一组键。源码 store.ts:147-159；store.ts:89-107
5「读配置」有落盘副作用：文件不在 → 按默认值落一份（created: true）；配置目录与数据目录也会被建出来（mkdir -p）。所以「打开一次设置页」就会落一份 bill.yaml。源码 store.ts:137-141、dirs.ts:65-76
6校验是硬失败：不认识的键、类型不符一律抛错，报文带行号＋文件名；出口把 CONFIG_* 这类错误映成 exit 1。源码 store.ts:44-86；cmd_read.ts:271-273
7空串＝按默认落点，不是「没配、失败」，也不是「禁用」。⇒ 没有任何一项是必设的，缺配置不会 exit 1。文档 docs/env.md:15；packages/skill-bill/src/config.ts:11-12
8「重置为默认」＝先把现有文件另存 bill.yaml.bak（已有就覆盖）再按默认值重写；备份失败即不写盘，原文件保持不动；本来没有文件时 backupPath 为 null。源码 store.ts:161-180；packages/skill-bill/src/config.ts:77-81
9保存即生效：每进程按「配置文件路径」记住一份，写／重置会清掉记忆 ⇒ 同进程后续读也现取，不用重启宿主。源码 packages/skill-bill/src/config.ts:43-47,70-74
10测试隔离护栏：跑在 node --test 里却没设 ILIFE_CONFIG_DIR 直接抛 CONFIG_TEST_ISOLATION_MISSING。这是删掉五个写库哨兵之后的替代护栏——把「忘了配」从「静默写真实数据」变成「响亮失败」。源码 dirs.ts:28-48；文档 docs/base/base-link-core/t694-证据.md:73-76

谁能改它、谁只看不改

角色怎么碰它出处
设置页（插件）只经 RPC → 宿主 spawn 技能 CLI 的三个配置 key：bill.config.read／write／reset。插件自己不读盘、不算默认值。源码 packages/plugin-bill-ilife/src/bridge.ts:125-144、src/index.ts:34-58、packages/skill-bill/src/cli/config.ts:17-21

6 · 「能不能生效」：8 项都接在活代码上，但有 6 处配了不等于如愿

先给结论：8 项全部真接在执行路径上（第 5 节每一行的读取点都是活代码，不是死配置）。但下面 6 处会让「配了」≠「如愿」。前 4 条里，带 实测 的是我在这台机器上真跑过探针的。

① 设置页那个「数据目录」框，此刻正在骗你 实测

你截图里「数据目录」框写着 C:\Users\辰辰洋洋\.ilife\data，而你 bill.yaml 里是 db.dir: ""。这是 #743 加的预填：取值空着时把技能算好的默认落点显示出来（源码 settings.ts:46,57；client.ts:194）。

问题在写回：fromDraft() 提交全部 8 项（client.ts:200-214），所以只要你改了任意一行再点「保存」，db.dir 就从 "" 被写成那串绝对路径——「留空＝用默认目录」这条语义当场失效；此后再换机器、换用户名、换 ILIFE_CONFIG_DIR，库都不会跟着走。测试甚至把「空值预填后的显示」与「配了同一条路径的显示」断言成相等（packages/plugin-bill-ilife/test/config-surface-677.test.mjs:354）——页面上这两种状态无法区分。

#743 当初解决的是另一个面：「打开面板不会凭空变『未保存』」（docs/plugins/plugin-bill-ilife/t743-证据.md:14）。同一条代码的相反面没有被覆盖。

② 相对路径会落在「宿主进程的当刻工作目录」 实测

resolveDbDir() 把 db.dir 原样返回（paths.ts:48），mkdirSync 与 new DatabaseSync 都按 process.cwd() 解析；而宿主 spawn 技能出口时不传 cwd（bridge.ts:92、skill-tool.ts:77）。实测把一个相对路径交给 DatabaseSync：它按调用者的 cwd 解，cwd 不对就是 unable to open database file。

⇒ 填 db.dir: 账单 不是「放在配置目录旁边」，而是在宿主的工作目录下静默建一个新的空库。

对照：同一份配置里 backup.dir 非空走 resolve()（paths.ts:65-68）——同名「目录项」两种相对语义；调查确认仓内没把这条记为挂账。

③ db.name／backup.stem 能写进路径分隔符，落点悄悄变成子目录，而目录不会建 实测

实测：db.name: sub/x.db → 父目录 sub 不建 → ERR_SQLITE_ERROR unable to open database file → 记账侧包成 BILL_DB_UNREADABLE、exit 4。backup.stem: sub/biscuit_ → copyFileSync 到不存在的目录、exit 5。这两项是纯文本框，没有任何形状校验。

④ html.dir 填绝对路径会拼出跑不出来的路径，而体检判它绿 实测

落点算式是 join(库目录, htmlDirName())（cmd_read.ts:123,134）。实测 join(dataDir, 'D:\help') → …\data\D:\help，mkdir 抛 ENOENT ⇒ 交付时落盘失败（exit 5）。而体检那条判据「目录不存在」一律判绿，文案还写「交付页面时才落这里，那时自动建」（源码 health.ts:416-431）——这条死配置在体检里读起来是正常的。

⑤ 三个「名字主体」项体检不覆盖

体检一共 7 条：配置文件／数据目录／库文件／产物目录／这个值从哪来／第二份库／备份目录（源码 health.ts:325-486）。html.helpStem、html.quickRefStem、backup.stem 填错了不会红，只有产物名字变了才看得出来。

⑥ 改名＝换库，没有任何提示；另有一条配置文件的读写隐患

db.name 一改，openBillDb 就按新名字 DDL 自愈建一张空表（db.ts:57-71），旧库留在原地、技能不再看它——没有一句回执说「旧库还在 <旧路径>」。

另外两条与配置文件本身有关（调查）：保存会把文件整份重写成默认键组（你手写的注释与排布都会没）；写盘无锁、无版本、last-writer-wins（store.ts:4,117-124 是裸 writeFileSync，对照 DSH 自己的设置服务用 writeFileAtomic＋文件锁）。反过来，你手工加一个不认识的行 → 下一次任何命令都 CONFIG_UNKNOWN_KEY → exit 1，是技能整体起不来，不是那一项失效。仓内没把这条记为挂账。

怎么变成这样的（能对上号）

  1. #726 之前，TS 线读的是环境变量 SKILLS_DB_PATH；你那时指的应该就是这个老目录——老库里已经有 deleted_at 列和 idx_bills_time／idx_bills_category 两个索引，与本机新库逐字相同（实测 两次 PRAGMA table_info／sqlite_master 对比）。那两个索引名正是新线 DDL 里的名字（db.ts:68-69）。
  2. #726 把环境变量全删、落点改读配置文件 ⇒ db.dir: "" 落到新默认目录 ~/.ilife/data/ ⇒ 账「没了」。

同一个现象不是记账一家：那个老目录里躺着六家的老数据（实测 目录清单）：calorie_data.db 3.0 MB、schedule_data.db 2.4 MB、home.db 1.7 MB、memo.db 238 KB、chef_data.db 294 KB⋯而新默认目录 ~/.ilife/data 里目前只有记账与卡路里的库。

12 · 待裁决的 8 个问题（Q0–Q7）

下面是这次调查读出来的设计岔口。每条只给一次推荐，等你答完再进下一轮（`/grill-me` 的规矩：先把当下的岔口一次问全，答案会改写下游的问题）。

❓ Q0 · 那 7,127 条老账怎么办

甲）永久把 db.dir 指到 D:\2Study\StudyNotes\.db；乙）把老库与 goals.json 拷进 ~/.ilife/data/、db.dir 保持空；丙）在技能里加「检测到老库在 <路径>，要不要用它」的探测（等于改 #675 的「不做兼容」）；丁）封存不动。

推荐 甲：① 零拷贝、零风险，且两边 bills 的列与两个索引逐字相同，指过去不会触发任何 DDL 变更；② 六家老数据都在那同一个目录里，指过去是六家一起回位，而不是记账单独搬家；③ 那个目录是 git 仓库、旁边有导出与同步脚本，搬走反而脱离原有备份。代价要认：db.dir 从此是一条钉死的绝对路径（这恰好是 Q1 那个「保存＝钉死」语义在这里帮你的地方）。
落地＝设置页「数据目录」那一行填 D:\2Study\StudyNotes\.db 再保存。

❓ Q1 · 设置页那个输入框，代表「空」还是代表「那一条路径」

甲）提交时只送真改过的键（没碰的行不写回，技能侧的 mergeValues 本来就支持只给一部分）；乙）框里保持空、用灰色占位符显示默认落点；丙）承认「保存＝钉死」，把文案改成「这里显示当前生效目录，保存即固定」。

推荐 甲：改动只在插件侧、技能侧一行不动，而且它把「留空＝默认」这条已经写进文档的语义还给用户。

❓ Q2 · 五个「只影响文件名」的项该不该留在页面上

甲）全留；乙）四项进「高级」并加一句「改名＝旧数据不再被读」；丙）从页面撤下、只留在配置文件里（技能照读）；丁）连配置项一起删。

推荐 丙：#726 要求的是「默认值等于老常量、老落点不变」，配置文件里留着它们并不违约；而仓内已有先例（卡路里 xunji.cli 就是页外键）。页面上少画 5 个「一动就丢数据」的旋钮，收益大于「配置得全」这个表面整齐。

❓ Q3 · 落点类取值要不要收形状

甲）一律只收绝对路径／纯文件名，形状不符即报错（带行号、exit 1）；乙）只对 db.dir 收严；丙）保持现状、靠体检报红。

推荐 甲：这三处（相对路径、路径分隔符、绝对路径填进 html.dir）是同一类错误——「表面生效、实际落点跑偏」，而响亮失败正是这套配置机制一贯的口径（不认识的键、类型不符都是硬失败）。

❓ Q4 · db.name／db.goals 改名时要不要给一句回执

甲）bill.config.write 回执里带一格警告（旧文件在、新文件不在 ⇒ 页面显示「旧库还在 <路径>，数据不会被自动搬过去」）；乙）只改页面 hint；丙）不管。

推荐 甲：改名的意图 99% 是「换个名接着用」，而现状会让人以为数据丢了——这是最容易伤信任的一类静默失败。不自动改名（那是动用户数据）。

❓ Q5 · 两份「库」（biscuit_accountant.db ＋ goals.json）继续拆吗

甲）继续拆，但把 bill.yaml 的写盘也改成「临时文件 ＋ 改名」（现在 goals.json 是原子写、bill.yaml 是直接覆盖）；乙）合并进 SQLite；丙）维持现状。

推荐 甲：拆的代价（备份要带影子件、体检多一条）已经付掉了；但「最小的那份配置文件反而最脆」没有道理。另外拆分本身没有裁定件——所以这一问同时也是在补一张缺失的裁定。

❓ Q6 · 体检要不要覆盖到 8 项，以及那份「第二解析器」的归属

推荐：前半 乙（体检只答「通不通」，命名类不进体检）；后半 甲（一份解析口径两处实现，正是仓规「一条实现不抄第二处」要拦的；而且六家 health.ts 全超线，拆法要六家一起裁）。

❓ Q7 · 配置文件的演进与并发
