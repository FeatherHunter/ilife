Q1为什么需要"交付信号"？

背景：旧版靠一行字解决的事

旧 SKILL.md 的强制性规定第 4 条是"HTML-First 铁则"：唤醒词命中后，只要模板清单里有对应页面，AI 必须渲染 HTML 并打开，严禁文字答；渲染失败必须给错误回执，严禁手写 HTML 兜底。

问题来了：AI 怎么知道"渲染成功了"？旧版第 6 条给了答案——CLI 的 stdout 里必须出现这一行：

⚠️ ACTION=SEND_TO_USER | HTML=D:\...\calorie_html\饮食_20260908_101530.html

这行就是交付信号：既宣布"渲染成功、这是给用户的东西"，又给出文件在哪。

新版断在哪

  • 新架构规定 stdout 只打一行 envelope JSON（SKILL.md:26，P9 契约）。
  • envelope 的字段是 {skill, key, shape, version, data}——没有 html、path、template 任何一项。
  • 全仓 grep ACTION=SEND_TO_USER = 0 命中。

后果（三条，都是真的）

  1. AI 不知道渲染成没成功，只能去猜目录、猜文件名；
  2. "渲染失败给回执"这条验收无法判定——没有信号就没有"失败"可言；
  3. 一旦 AI 不确定，它最可能的动作就是自己手写一段 HTML——正好是旧版明令禁止的反模式。

两个选项

A. 扩 envelope（推荐）

在那一行 JSON 里加 delivery:{mode:"file", path:"…", template:"…", bytes:5768}。仍是"一行 JSON"，老消费方忽略未知字段即可，面板与 agent 都能用。

B. 修订 P9

允许 stdout 出现第二行标记（照抄旧版 ACTION=SEND_TO_USER）。省事，但破掉"stdout 只一行"的纯净契约，解析方要改成两段式。

要你拍：选 A 还是 B。（推荐 A：envelope 本来就是唯一真相，加字段不新增真相。）

Q2数据库技术成熟吗？

用的是 SQLite——世界上最广泛部署的数据库引擎（手机、浏览器、飞机娱乐系统里都有它）。特点：单文件、事务完整、无需服务器进程、崩溃安全。

项实测
驱动import { DatabaseSync } from 'node:sqlite'（packages/skill-calorie/src/schema.ts:12）——Node 22.13+ 内置模块
第三方依赖零（全仓 grep sqlite 依赖 = 0；没有 better-sqlite3 之类）
版本门槛engines: node >= 22.13 就是为了这个内置模块
数据位置环境变量 SKILLS_DB_PATH（无默认值，必须设）
访问纪律只许经 CLI（calorie-cmd-read），禁止直连库；缺失数据一律阻断，不返空数组
唯一需要注意的地方：openDb() 每次打开都会建表＋跑迁移（ALTER/DROP/UPDATE），所以"只读打开真库"在这套代码里并不存在。想拿真实数据做只读对照，要么拷贝一份、要么新增只读打开路径（票 #93）。

Q3是六边形架构（Hexagonal / Ports & Adapters）吗？

是——docs/adr/0001-hexagonal-architecture.md，状态"已决定（2026-09-08，用户原话：之后用这个架构）"。

层内容
端口 Port纯契约模块：零 node: 导入、浏览器安全。放 RPC 通道/方法/键、参数与回执形状、slots 能力描述。
适配器 Adapterhost 侧：node 实现（spawn CLI、注册 RPC）；client 侧：browser 实现（loader 工厂包、slots、React、RPC 调用）。

三条铁律：① client 产物必须是 loader 校验过的工厂包，传递闭包无 node:、无 ESM 顶层语句；② 两侧只经端口对话，client 不 import host 实现、反之亦然；③ 不虚构 host API。

范围要分清：ADR-0001 管的是插件侧（跨 host/client）。技能侧不是六边形，而是分层管线：cli → fetch → analysis → render，它对外的"端口"就是进程边界 + envelope JSON。

Q6老版的"中间态 HTML"场景（填表 → 复制 prompt → 交给 AI → 出结果 HTML）能处理吗？

能渲染，但缺一条回路。先把这个场景拆开看：

Q7"方向永久单向"——插件新增数据、再调技能接口，可以吗？

可以，而且这就是设计意图。"单向"说的是代码依赖方向，不是数据方向：

  • 依赖单向：插件依赖技能的 CLI 契约（按包名解析、spawn）；技能永不 import 插件。所以技能包 grep DSH 引用 = 0。
  • 数据双向：读有 42 个读键、写有 35 个写键。插件点"新增一餐" → 走 host.call → spawn calorie-cmd-read calorie.diet.add --params '{…}' → CLI 写 SQLite → 返回回执（M5 契约要求带 id、时间戳、影响行数）。
唯一约束：插件不得直接碰数据库，也不得 import 技能的取数/渲染实现——只能走那一个进程出口。

Q8规格、token、DOM 到底是什么（白话版）

DOM

网页的"结构骨架"：哪些标签、谁套谁、有哪些属性。相当于一栋楼的房间与墙。

token（设计变量）

把颜色/圆角/字号/间距写成变量，例如 --blue:#007aff、--r:12px。改一处，全站生效。相当于装修色卡与尺寸表。

规格（spec）

文字规范："KPI 卡＝白底、圆角 12、数字 32px 主色、副标 14px 灰"。相当于施工图纸。

为什么"复用规格与 token，不搬 DOM"

HTML 页是"字符串拼装"，DSH 面板是 React 组件树，两者结构天生不同，硬搬骨架会崩。但让它们共用同一份色卡与图纸，看起来就一致——这才是稳的复用方式。

补充问答（第二轮 · 7 问）

① 没有 SKILL.md，AI 怎么知道怎么处理？

澄清：SKILL.md 不能少，它是 agent 的第一入口。我说"镜像"只针对其中那张 95 键表格（#113 由 87 扩至 95）——它由 scripts/build-help.mjs 从 src/cli/keys.ts 自动生成、带 <!-- HELP-AUTO-START --> 标记、手改会被构建覆盖。

SKILL.md 的手写部分（唯一出口、口径、环境与出 scope、HELP 说明）才是真正的行为指导；#82 正是重写这部分。AI 的信息来源是三层：

  1. 发现：读 SKILL.md 全文（未来经 #56 的技能提供方，或直接读包内文件）→ 知道有哪些能力、怎么调、什么口径；
  2. 查词：calorie.help.lookup --params '{"q":"…"}' 查唤醒词 → key；
  3. 执行：calorie-cmd-read <key>。

② 新增能力降到 3–4 处，是最佳吗？

不是理论最优。理论最优是 2 处声明 + 0 处扇出：一张 key 注册表（key + 元数据 + 取数 + 渲染引用）＋一张渲染器注册表，cmd_read.ts 的 dispatch 与 4 个测试里的 length === 95（#113 由 87 扩至 95）都从注册表派生。

代价：把 77 个静态 case 改成动态注册会牺牲类型安全与可追踪性；而且本图正要在这几个文件上做大量页面工作，重构会直接冲突。所以 3–4 处是"本图不引入大重构"下的合理值；注册表化记成二期候选。

⑤ 每次执行命令都会调 openDb() 吗？

会。cmd_read.ts:651 在 main() 里对每一个 key（读和写都走这里）都调用一次：

const db = openDb(join(dbPath, DB_FILENAME));   // new DatabaseSync + initDb + applyMigrations
… dispatch / dispatchWrite …
db.close();

openDb ＝ new DatabaseSync(path) ＋ initDb（13 张表 CREATE TABLE IF NOT EXISTS）＋ applyMigrations（PRAGMA 列检查 ＋ 幂等迁移）。所以在已迁移的库上大多是 no-op，但"读一次也写库"这件事真实存在——这就是 #93 的理由。

顺带一个和 #87 有关的事实：--html 的路径是调用方给的（cmd_read.ts:659 writeFileSync(o.html, …)），CLI 不自己算文件名。命名规范（M10）目前落在调用方——这正是 #87 要收口的地方。写盘失败有专门的 exit 5。

⑥ 技能侧要不要也改成六边形架构？

不需要，也不该现在改。

  • 六边形解决的是"跨 host/client、两侧不能互相 import"——那是插件侧的问题（#48 证明两侧直引会炸整批加载）。
  • 技能侧是单进程 CLI，它的端口已经存在：进程边界 ＋ envelope JSON ＋ 退出码。cli → fetch → analysis → render 是内部分层，改内部不影响外部契约。
  • 收益（换数据库、换呈现方式）不是当前需求；成本是重构 95 键（#113 由 87 扩至 95）的取数／渲染路径，而本图正要在这上面做大量页面工作 → 直接冲突。

折中（已在票里）：把两个接缝显式化——① 数据接缝 ＝ openDb／fetch 层（#93 的只读路径落这里）；② 呈现接缝 ＝ renderHtml(envelope)（#104 的区块组件落这里）。这就是"够用的端口化"；二期若真要换 DB 或加新呈现，再抽接口。
