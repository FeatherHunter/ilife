# 更新链路：配套不变式方案（跨件）

对象：爱生活七插件包 → 六技能包 → 公共层 `base-paint`／`base-link-core` 的「装到用户机器上的是哪一套」这件事。
归属：跨件（六技能 ＋ 七插件 ＋ 公共层 ＋ `tooling/` ＋ CI），故本件落 `docs/agents/`。
前件读数：[`docs/plugins/plugin-manager/更新能力调查-技能与公共层.md`](../plugins/plugin-manager/更新能力调查-技能与公共层.md)（现场、机理、窗口事故）。
日期：2026-09-23　工作区 `D:\ilife`

## 零、第一性原理：缺的不是更新按钮，是「安装态」这个概念

**现状机制**：用**依赖范围**表达需求，用**解析器的惰性**实现配套。

- 需求表达：技能说「`base-paint` ≥ 0.3.13」（一个**区间**，不是一个版本）；
- 落地：pnpm 看锁文件里有没有满足区间的版本，**有就不动**；
- 结果：**同一个技能版本，在不同机器上落出不同的公共层版本**。实测两种形状：

| 现场 | 读数（`.scratch/t-refresh/`） |
|---|---|
| 干净目录，一次装齐七个插件 0.3.13 | 15 个爱生活包**全是 0.3.13**，**零嵌套副本**（`dump-all.mjs` 输出） |
| 真机 `~/.dsh/profiles/web` | 顶层 `base-link-core` **0.3.7**，六个技能各带一份嵌套 `base-link-core` **0.3.13**（`probe-nested.txt`） |

⇒ 系统里没有任何一处定义「装对了」是什么样，也没有任何一处能读出「现在装成了什么样」。**缺的是不变量与读数，不是按钮。**

**三条第一性原理要求**：

1. **确定性**：同一套版本输入，在任何机器上落出同一种形状。（当刻不满足）
2. **单一真相源**：一个包要哪一版下层，只在一处声明，且该声明能被执行器**无损实现**。（当刻不满足：`^` 把决定权让给了存量）
3. **可观测**：装机结果能被一条命令读出并与期望比对。（当刻完全没有）

**关键判断**：`^` 在本仓承诺的「自动拿补丁」是**假的**——pnpm 的惰性解析让它只会停在能停的地方（真机 `0.3.7` 停在 `0.3.7`，源上早有 `0.3.13`）。它没带来好处，却制造了不确定性 ⇒ **把 `^` 换成精确声明是严格占优，不是取舍。**

## 一、不变量（系统的「应该是什么样」）

| 号 | 不变量 | 读数（谁看哪个数） |
|---|---|---|
| **I1** | **版本线唯一**：七个插件包、六个技能包、公共层取同一个版本号 X（用户心智：爱生活 X 是一套） | 探针 `check-install-state` 逐包读磁盘版本，出现两个不同值即红 |
| **I2** | **声明唯一且精确**：公共层版本只在**使用方**（技能）的 `dependencies` 里精确声明；插件只精确 pin 技能；**使用范围的直依赖里不许出现 `base-*`／`skill-*`** | 门 `check-dependent-pins`：每条 base 依赖必须 match `^\d+\.\d+\.\d+$` 且**等于**仓内该包版本；使用范围直依赖白名单（七个插件）之外的命中即红 |
| **I3** | **装机可读**：任何时候、任何机器，「三层各自版本 ＋ 是否等于应有版本 ＋ 有没有分裂副本」都能读出来，并在面板／装机读回／CI 三处出现 | 探针 ＋ 面板总账一行；宿主半逐层校验下行 pin |
| **I4** | **上架有序**：被依赖的版本必须先于依赖它的版本在 registry 可见；同一时刻只允许一趟发版 | 发版前逐包断言下层版本已可见；发版后读 registry `time` 断言序关系 |

**I2 与 I3 是一对**：只有下行 pin 是**精确值**，「磁盘 = 应有」才成为可判定的等式；在此之前只能判「有没有分裂」。
⇒ 这正是 2026-09-23 那窗事故的现场形态：`dsh-calorie@0.3.13` 先上架、它 pin 的 `skill-calorie@0.3.13` 后上架（相隔 37 秒）、公共层最后（再隔 79 秒），窗口内点更新必失败。

## 二、改动面

### 面 0｜现场清理（使用范围，非仓内）

删掉 `~/.dsh/profiles/web/package.json` 里那条 `"base-link-core": "0.3.7"`（#861 现场修复留下的直依赖）→ 在使用范围目录跑一次安装 → 重启 DSH。
**期望读数**（干净目录已实测出形状）：顶层三层全 `0.3.13`、**嵌套副本消失**、六家 `*.config.read` exit 0。
**旧形状可回退**：备份 `package.json` 与 `pnpm-lock.yaml`。

### 面 1｜声明硬化（六技能 ＋ 公共层）

- 六技能 `dependencies`：`"base-link-core": "^0.3.13"` → `"0.3.13"`；`"base-paint": "^0.3.13"` → `"0.3.13"`（六家同形，`packages/skill-*/package.json:21-22` 一类位置）。
- 门升级：`tooling/check-base-floor.mjs` 的判据从「**下界**等于仓内版本」改成「**必须是精确 `x.y.z`** 且等于仓内版本」——现在 `^0.3.13` 是能过门的（`minAdmitted` 认 `^`），这正是残留口子。
- `base-combos`／`base-render` 的内部依赖照此（`base-render` 那条是 `devDependencies`，不在门的判据内，为本地开发一致也改）。
- **加一道新门 `check-suite-version`**：断言七个插件包、六个技能包、两个落地公共层包的 `version` **逐字相等**。当刻仓内已经全等（0.3.13），门只是把「当下恰好成立」变成「不成立即红」。这条门也是 I1 的仓内半边。

**为什么精确声明不会装出多份副本（对抗式审查第一问）**：实测干净目录一次装齐七插件 ⇒ 15 包全 0.3.13、零嵌套副本。多份只在「版本线被拆开」时出现，而那正是 I1 要禁止的。

### 面 2｜装机读数（把不可见的变成可见）

新增探针 `tooling/check-install-state.mjs`（跨件工具，与 `check-base-floor.mjs`／`check-publish.mjs` 同家）：

- **入参**：使用范围目录（`--profile-dir`，缺省按 `DSH_HOME`／家目录推 `profiles/<名>`）；`--root` 供变异自证。
- **判据（按其可判定性演进，两版）**：
  - 第一版（不依赖面 1）：① 七插件＋六技能＋公共层磁盘版本**逐字相等**；② **零嵌套副本**（遍历各包 `node_modules` 找 `base-*`／`skill-*`）；③ 使用范围直依赖里除七个插件外不得出现 `base-*`／`skill-*`。
  - 第二版（面 1 之后）：再加上「磁盘版本 == 上行包清单里精确 pin 的版本」逐层等式。
- **输出**：逐包一行 `包名 磁盘 应有 判定`；末行 `INSTALL-STATE: PASS|FAIL`。判据缺席（读不到目录／读不到 manifest）一律 **FAIL**，不给肯定结论。
- **挂三处**：
  1. **面板**：宿主半（`update-host.ts` 的 `readTargets`）把「技能磁盘版本／公共层磁盘版本／套装号」交给面板（当刻 `readSkillRide` 读的是插件清单里的**声明**，不是磁盘——这是「声明冒充事实」的那处，一并改掉）；面板出**一行总账**（`三层配套：0.3.13`，或 `技能落后：0.3.12（应有 0.3.13）→ 点「装上更新」`），明细走折叠。
  2. **装机读回**：`tooling/wizard-install.ps1` 的读回段（现在只读插件版本与 LinkType）加一行探针读数。
  3. **CI**：接进已有的装机态门（`check-publish.mjs --fresh-tmp` 已有「装到仓外临时目录」先例）。
- **面板文案**：`versionLines` 那句「技能包随插件（不单独查更新）」要补两句为什么与何时：技能与公共层随插件同版发布；公共层不单独更新（理由见面 3）。

### 面 3｜收敛（把「更新」做成套装收敛，但不禁单家）

- **更新单位不变**：仍是单个插件（保留 #674 的七家交互与 #922／#926 的串行全量更新）。
- **收敛性由依赖图免费提供**：面 1 之后，插件精确 pin 技能、技能精确 pin 公共层 ⇒ 七个插件都到 X，三层必然全在 X，不需要额外动作。要做的是**用读数证明它**（面 2）。
- **中间态的定义**：只更新了 N/7 家时，机器上允许出现两个版本线并存。面板总账在这一态说「已配套 N/7 家，其余家落后」，并给「全部更新」入口。**不禁止中间态，只要求它可读、可收敛。**
- **公共层不单独更新，写进 ADR**：公共层的可见行为是技能页面，单独换公共层＝没跑过验收就换上了。它的修复通过**一次纯抬版本的齐发**到达用户（先例：`base-link-core`／`base-combos` 的 0.3.5／0.3.6「只随三包版本锁步抬号，内容无改动」）。面板文案要把这句说出来，否则用户以为能单独刷。

### 面 4｜发版纪律（把顺序从「脚本里的排序数字」变成「前置条件」）

- `tooling/wizard-publish.ps1` 加**下层可见性断言**：发某包之前，逐条断言它 pin 的每个包在该版本上**已在官方源可见**（`npm view <包>@<版本> version` 成功），不满足即停、不进入发布。
- 加**单飞锁**：同一工作区同一时刻只允许一趟发版（锁文件 ＋ 陈旧锁检测）。2026-09-23 那窗至少有两趟在跑（`.scratch/publish-log.txt` 里两条 `PKG-FAIL` 之间夹着一次完整 `STAGE 1/4 读表`）。
- 发版后守卫：逐包读 registry `time`，断言「被依赖者不晚于依赖它的人」。

## 三、对抗式审查（我先把最强的十拳打出来）

| # | 反驳 | 回答 |
|---|---|---|
| 1 | 精确声明会丢掉「公共层补丁自动上来」 | 那条路**当刻就不存在**：真机 0.3.7 停在 0.3.7（源上已有 0.3.13），而干净机取区间内最高版 ⇒ 同一技能版本两种落地。补丁只能走发版（面 3 的纯抬版本齐发）。 |
| 2 | 精确 pin 会装出多份副本、破 dedupe | 实测干净目录七插件齐装：15 包全 0.3.13、**零嵌套副本**。多份只由「版本线拆开」引起，I1 正是禁止它。 |
| 3 | 为什么不由插件 pin 公共层 | **谁 import，谁声明**。插件不 import 公共层（读它的是技能）；让插件 pin 会变成两处定义，或让技能不知道自己需要哪版（回到声明失真）。 |
| 4 | 为什么不引入「套装包」 | DSH 归并 `dsh.profile.bundles` 只扫使用范围的**直接**依赖（`docs/research/t672-install-update-survey.md` §1.2 实证），套装包 pin 的插件是传递依赖、**不会被激活** ⇒ 它只能当版本真相源，而「三层同号」已经免费提供这个真相源。不多发第 11 个包。 |
| 5 | I1 会禁掉「只更新一家」 | 不会。I1 是**收敛目标**不是硬门禁；中间态允许但必须可读（总账显示 `N/7`）且一键可收敛。 |
| 6 | 读数又会变成「声明」 | 探针只读**磁盘 manifest 与目录结构**（含嵌套副本检测），不读声明；每条门带变异自证（构造不配套夹具必须红；扫描面为空即红，照 `check-base-floor.mjs` 先例）。 |
| 7 | 三层同号的代价（任一层补丁都要齐发） | 本仓已经在这么做（0.3.13 那窗 14 包齐发），且齐发是把人机协作链（2FA／装机／重启）**走一次**，比分开发更省。 |
| 8 | 公共层紧急安全修复怎么办 | 走纯抬版本齐发（面 3），先例在册。 |
| 9 | 门会不会空转（本仓有前科：断言被死代码满足） | 每条门必须带「改坏必红、还原必绿」的变异自证 ＋ 非空扫描面断言；CI 里与既有门同列（`pnpm base:floor` 的位置附近）。 |
| 10 | 残余风险（我承认的三条） | ① 中间态期间两份公共层并存，谁被用取决于 hoisting——**已知且被读数覆盖**（探针报分裂），非禁止态；② 第三方工具（`dshmarket`／内置插件市场）会自己跑 pnpm install，绕过面板——探针能**发现**不能**阻止**，缓解＝面板每次打开与每次更新后重读；③ `base-combos` 当刻**没有任何包依赖它**（实测仓内只有它自己提到自己），它仍参与版本锁步与发版，属另一笔账。 |

## 四、验收（怎么算做到）

| 门／读数 | 红绿条件 | 变异自证 |
|---|---|---|
| `check-dependent-pins` | 每条 base 依赖**精确**且等于仓内版本；当刻 `^0.3.13` 应红（改前）→ 精确后绿 | 把某技能改回 `^0.3.13` ⇒ 红；还原 ⇒ 绿 |
| `check-suite-version` | 七插件＋六技能＋两公共层版本逐字相等 | 单抬一个包版本 ⇒ 红 |
| `check-install-state`（探针） | `INSTALL-STATE: PASS`；当刻真机应红（顶层 0.3.7 ＋ 六份嵌套） | 夹具：直依赖钉旧 base ⇒ 红；删掉 ⇒ 绿 |
| 面板总账 | 配套时一行「三层配套：X」；不配套时点名哪一层落后 ＋ 一句下一步 | 夹具把磁盘技能改旧 ⇒ 面板行必须显示差异（当刻会印声明值＝假绿） |
| `wizard-install.ps1` 读回 | 追加探针一行；不等即红 | — |
| 发版守卫 | 下层未可见即停；`time` 序关系断言 | 手工先发上层 ⇒ 前断言拦下 |

**真机终验（人/机器各一条）**：面 0 做完后探针 `PASS`、六家 `*.config.read` exit 0；下次齐发窗口后，面板总账与探针同时绿。

## 五、落地顺序（每步可独立验收，读数为先）

1. **面 2 探针先上** → 当刻真机必红（顶层 0.3.7 ＋ 六份嵌套）＝ 红基线（先能看见，后面每一步才有判据）。
2. **面 0 清现场** → 探针转绿。
3. **面 1 声明硬化 ＋ 两道门** → 仓内绿；装机形状不变（版本线没动）。
4. **面 2 的用户面**（面板总账 ＋ 明细 ＋ 技能行改读磁盘）→ 朗读测试验收（照 #740 的三态朗读表先例）。
5. **面 4 发版纪律**（可见性断言 ＋ 单飞锁 ＋ `time` 序关系）。
6. **下次齐发窗口复验**：探针、面板总账、六家 `config read` 三处同绿。
