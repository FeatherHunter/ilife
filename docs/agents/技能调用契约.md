# 技能调用契约：技能侧与插件侧各管一半

写或改 `packages/skill-*`（技能包）、`packages/plugin-*`（DSH 插件）之前先读本文。

一句话：**技能包只管「我是谁、怎么在任意 agent 环境里跑起来」；插件只管「装上插件 ＝ 技能装好，并且在 DSH 里真的调得起来」。** 两侧都不许把对方那半做进自己这侧。

## 一、技能包侧（`packages/skill-*`）

**必须做到**

1. **声明唯一出口**：`package.json` 的 `bin.<技能名>-cmd-read` 指向包内入口，同一个入口再在 `exports["./cli"]` 声明一次。
2. **说明面（`SKILL.md`）给与宿主无关的调用形态**：先按唯一出口的命令名调；名字不可解析时，用「**技能基目录 ＋ 包 `bin` 声明的入口**」调（技能基目录＝宿主加载技能时给出的那个目录，DSH 会给出 `Base directory for this skill: <路径>` 这一行）。运行时只写 Node。
   **这段口径的正文只许住一处**：本文 §七 的 `CALL-FORM` 区，由 `tooling/skill-call-form.mjs` 渲染进六份 `SKILL.md` 的 `<!-- CALL-FORM-START/END -->` 块（渲染值从各包 `package.json` 的 `bin` 声明现算）。六份里的块**不许手改**——手改会被 `pnpm gen:check` 打红（#742）。
3. **出口自足**：只依赖 Node 标准库与包内依赖（`base-paint`／`base-link-core` 一类），不依赖任何宿主的模块解析特例。

**不许做**

- 不许出现 DSH 专属标识：`dsh-`（插件包名）、`DSH_`（宿主环境变量）、cordis 上下文对象、宿主安装路径。
- **不许在说明面里提任何宿主的调用通道**：不写 DSH 的工具名、不写「宿主提供了工具就用它」这类只有某个宿主才成立的话。技能本身不知道宿主的存在（维护者 2026-09-20 裁定）——把通道告诉模型是**宿主那半边**的事：工具名与描述随工具 schema 进提示词，不靠改 SKILL.md。
- 不许把入口写成**仓内相对路径**（`packages/skill-…/dist/…`）——装机用户机器上没有这个路径。
- 不许假设「用户机器 PATH 上有自家命令名」：那条只在 npm 直装路线成立，DSH 插件路线不成立（见 §二）。

## 二、插件侧（`packages/plugin-*`）

**必须做到**

1. **装上插件 ＝ 技能装好**：技能包进 `dependencies`（精确版本，与发版窗口一致），不让用户另外装一次。
2. **在 DSH 里把技能调起来**：宿主侧提供调用通道（工具或桥），运行一律用现成的 `resolveNodeBin(process.execPath)` 算出来的运行时（Electron 宿主加 `ELECTRON_RUN_AS_NODE=1`），**不读 PATH、不要求用户装 Node**。
3. **入口按声明解析**：从技能包 `package.json` 的 `bin` 取入口路径；不许在插件源码里复制字面路径。
4. **给 agent 一条在 DSH 里能用的调用通道**：工具或等价物要能被模型直接调用，返回物与技能出口的 envelope 同形。

**不许做**

- 不许 import 技能实现：只经唯一出口 spawn（与 `docs/agents/命令事实边界.md` 同向）。
- 不许在插件里重写技能的业务口径。

## 二之二、调用顺序（三级回退，说明面只写第 2、3 级）

agent 在某个环境里要跑技能时，按这个顺序挑；**谁能提供哪一级，谁负责那一级**：

1. **宿主提供的调用通道** —— 有就用（DSH 里＝插件注册的 agent 工具）。这一级**不经会话 shell、不读 PATH、不需要用户机器装 Node**：工具在宿主进程里跑，用的是宿主自带运行时（Electron 宿主＝该二进制加 `ELECTRON_RUN_AS_NODE=1`；出处 `packages/plugin-calorie/src/bridge.ts` 的 #48 真机根因注释）。**这一级不写进 `SKILL.md`**（技能不知道宿主），它靠工具名与描述随 schema 进提示词让模型自己看见。
2. **命令名** —— `PATH` 上解析得到唯一出口的名字（npm 直装路线成立）。
3. **技能基目录 ＋ 包 `bin` 声明的入口 ＋ Node** —— 通用形态（任何**有 Node** 的 agent 环境成立）。**说明面写的是第 2、3 级这两条与宿主无关的形态。**
4. **从 npm 取运行时**（`npx -p <包名> <命令名> …`）—— 说明面里的**最后一条兜底**，只服务「**装源目录**」那一类装法：`npx skills add <repo>` 拿到的副本里没有编译产物（`dist/` 不进 git；2026-09-20 实测六家 git 跟踪的 `dist/` 文件数都是 **0**），第 2、3 级都不成立，而这条路正是 OpenCode／Codex 的官方装法（#47）。

**关于 Node 的边界（2026-09-20 维护者问出来的）**：第 2、3、4 级**都要 Node**——`npx` 自己就是 Node/npm 的一部分 ⇒ **第 4 级不是「没 Node」的兜底**。没有 Node 的机器只有第 1 级一途（宿主进程里跑，用宿主自带运行时）。**非 DSH ＋ 无 Node ＝ 不受支持**，这是本仓解决不到的边界，别把它误当兜底。第 3 级在纯 DSH 机器上同样不成立（会话 PATH 上没有 `node`）——这正是第 1 级存在、且由插件那半边负责的理由。

## 三、为什么这样分（2026-09-20 实测事实）

1. **DSH 会话 PATH 上只有宿主自己的命令**：实测只有 `dsh.cmd` 与 `pnpm.cmd` 两条。DSH 这两套命令环境在源码里的自述是「App-local command environments available to desktop Host plugins」，而且只有 dsh／pnpm 两种 kind，**没有留给插件的命令位** ⇒ 装的包的命令名在 DSH 会话里结构性不可解析。
2. **纯 DSH 机器上会话里没有 `node`**：宿主自带的 Node 在 `runtime-commands\private\node-bin`（`node.cmd` 是「Electron 当 Node」的包装），只给 `pnpm.cmd` 自用，不在会话 PATH 上 ⇒「用 `node` 跑脚本」这条在 DSH 里必须由插件用宿主运行时代劳。
3. **说明面是唯一装到 agent 手里的说明书**：技能在别的 agent 环境（Claude Code 一类）也要能用，所以只能写与宿主无关的形态；反过来，插件不接「DSH 里怎么调」这一段，用户装完插件也用不上技能。

## 四、入口路径可变吗

**可变**——它是编译输出位置，由包的 `tsconfig.json` 决定（`rootDir: ./src`、`outDir: ./dist` ⇒ `src/cli/cmd_read.ts` 编译成 `dist/cli/cmd_read.js`）。`cli/` 是仓内**按工种切**的一级目录（命令行面），与 `fetch/`、`render/`、`triggers/`、各能力目录同级；`dist/` 与 `src/` 一一对应。所以目录名不是对外契约。

**入口只许按声明找**（`bin` ＋ `exports["./cli"]`），谁都不许复制字面路径。今天有四处消费者：`bin` 声明、`exports` 声明、插件桥、仓内测试与脚本（2026-09-20 实测 `dist/cli/cmd_read` 在 `src`／`scripts`／`test` 里有 **84 处**）。把这些收到「读声明」一条路上，将来搬目录才不用满仓改。

## 五、开发时怎么自查

- **技能侧**：`Get-ChildItem packages/skill-*/src -Recurse -Include *.ts | Select-String 'dsh-|DSH_'` 应为 **0 命中**（2026-09-20 六家都是 0）。
  - 别拿 `ctx.` 当判据：技能里的 `ctx` 是各自的渲染／参数上下文变量名，会假红（实测 bill 132／memo 13／schedule 57 条全是这种假红）。
- **技能侧**：把 `SKILL.md` 的命令示例换成「技能基目录 ＋ 包内入口」，拿装机副本跑一次：`exit 0` ＋ 产物落盘。
- **技能侧／口径同源**：`node tooling/skill-call-form.mjs --check` 应绿（六份块与本文 §七 逐字同源、块外无旧写法）；`--selftest` 两条变异自证（拿掉块 → 红；写回 → 绿）。
- **插件侧**：把会话 PATH 置成不含 `node`、不含自家命令名，调用通道仍跑通。单测可判：注入 Electron 形态的 `execPath`，断言环境含 `ELECTRON_RUN_AS_NODE=1`，且入口来自 `bin` 声明。
- **插件侧**：插件源码里 `dist/cli/…` 字面路径应为 **0 处**（2026-09-20 六家插件各有一处硬编码，属待收的债）。

## 七、口径正文（唯一来源，机器生成）

**这一段是唯一来源**：`tooling/skill-call-form.mjs` 把下面 `CALL-FORM` 标记区之间的正文，渲染进六份 `SKILL.md` 的 `<!-- CALL-FORM-START/END -->` 块。占位符一律从**各包 `package.json` 现算**，不许手写路径：

| 占位符 | 取哪 | 例（卡路里） |
|---|---|---|
| `{cmd}` | `bin` 里键名以 `-cmd-read` 收尾的那条 | `calorie-cmd-read` |
| `{entry}` | 上面那条的值去掉开头 `./` | `dist/cli/cmd_read.js` |
| `{pkg}` | 包名 | `skill-calorie` |

跑法：`node tooling/skill-call-form.mjs`（写）／`--check`（门，已挂进 `pnpm gen:check`）／`--selftest`（变异自证）。**块内不许出现任何宿主字样**（维护者 2026-09-20 裁定，收口票 #742）；**块外**不许再出现 `packages/skill-`／`npm install -g`／`npx -p`／`~/.agents/skills` 这些旧写法（门会打红）。

## 唯一出口：怎么跑

入口＝本技能包 `package.json` 里 `bin` 声明的那条：`{entry}`。
`<技能基目录>`＝加载本技能时给出的 `Base directory for this skill: <路径>` 那一行。

1. 命令名解析得到时：`{cmd} <key> [--params '<json>']`。
2. 解析不到时（`not recognized`／`command not found`）＝ PATH 上没有这条命令，下面这行照样跑得起来：
   `node <技能基目录>/{entry} <key> [--params '<json>']`
3. 本目录里没有编译产物时：`npx -p {pkg} {cmd} <key> [--params '<json>']`（上面第 2 行就够，不必再取一份）。

换走法的信号只有一个：命令名解析不到。其余报错照 stderr 的报文原样交给用户。
