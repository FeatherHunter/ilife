不建基线就推的话，目的端是空库、排除集为空、整条历史都会被查，必然被点名——那是设计（那些提交确实会被一起推过去），不是误报。

三个取数坑：① `--author='x'` 这种把单引号写进参数里的写法，**直接写在 pwsh 里** PowerShell 会先把引号吃掉（实测 `--author='975559549@qq.com'` 命中 3673 条，看着像「过滤器没生效」），而经 `cmd.exe` 或脚本文件时引号原样传给 git、得到零命中——写 `--author=975559549@qq.com`，或干脆按 `%ae` 分组数；② 比对身份字符串时把两侧输出各写一个文件再比 SHA256（或直接打十六进制），别在控制台里肉眼看中文——本轮肉眼看「本地配置＝历史作者」时实际比到的是 HEAD 的 `muse-spark`，是十六进制读数把它抓出来的；③ **别用 `git shortlog -sne` 判断有没有漏网**——`.mailmap` 在位时它永远是「一行 王辰浩」，漏网的旧身份提交被归并进去、看不出来；只有按 `%ae`／`%ce`（原始字段，不经 `mailmap`）分组才数得出来。

## 五、写这两道守卫时踩过的实现坑（2026-10-18 实测）

- 本机 git（`2.49.0.windows.1`）的 `ls-remote` **不认 `--format=`**：`git ls-remote --format='%(objectname)' <url>` 直接报 `error: unknown option 'format=%(objectname)'`。守卫里用它取目的端 sha 时拿到空串＝排除集为空＝整条历史重查，表现成「明明只推一条也报 353 条」。取默认输出的第一列：`git ls-remote --quiet --refs "$url" | cut -f1`。
- 排除多个 tip 别写成一串 `--not <sha>`：`--not` 会把**后面**所有 revision 的含义翻转，直到下一个 `--not` 为止（`git-rev-list` 文档），于是隔一个 tip 就变回「包含」，把远端其它分支的整条历史拉进检查范围——实测把 `feat/1240-pixel` 的 `2b2852ce`、`fix/1254-lock-residue` 的 `092592be` 都算成了「这次要推的提交」。要么每个写成 `^<sha>`，要么整串只写一个 `--not`。
- `git hook run pre-push` **不转发 stdin**（自挂探针钩子收到 0 字节），拿它测推送侧守卫会得到假绿；要测就真 `git push` 到一个一次性裸库。
- 逐个 `git log -1 --format=… <sha>` 在本机约 0.33s／条（353 条要两分钟，一次推送卡两分钟）。改成一次问完：`printf '%s\n' $shas | git log --no-walk --stdin --format='%H|%an|%ae|%cn|%ce'`，同一范围从 118s 降到约 2s。
