# 唤醒词增补范围与路由策略裁决（#1236）

- 日期：2026-10-08；归属：地图 #1197；本票只裁决不改代码（命令关键字与既有唤醒词资产一行不动）。
- 现状（HELP 资产口径，help-pipeline）：calorie 10 组/54 子组/437 场景（路由 SoT 口径；资产 436）｜bill 7 域/20 组/74 场景｜chef 10 域/33 组/48 卡｜home 9 域/30 组/73 场景（含 link 3 登记位，渲染 70）｜memo 8 域/13 组/30 场景｜schedule 5 类别/34 唤醒词/85 场景。合计约 747 场景。命令登记面（`src/<能力>/commands.ts → cli/registry.ts、triggers/routes.generated.ts、combos.yaml 镜像段）由 `pnpm gen` 派生、`gen:check` 守（test-gates §4）。

## 裁决

1. **增补范围：首轮只覆盖常用命令（约 30 条），不做 747 全覆盖**。名单＝6 条 HELP lookup（`bill.help.lookup / calorie.help.center / chef.help.lookup / home.help.lookup / memo.help.lookup / schedule.help.lookup`）＋ 每家 3–4 条主入口（bill：记一笔/查今天/查账单；calorie：记一餐/记运动/记体重/看今日主页；chef：搜菜/看菜谱/加菜；home：查物品/录物品；memo：记一条/搜笔记；schedule：记作息/查作息/规划明天）。其余 700＋ 场景按需增补（英文用户真实触发时再加，每次加词走“唯一来源→派生→gen:check”同一条链）。
2. **路由表按语言只加载一套（采纳）**：运行时按 `language.text` 只载入一套词表（中文缺省；英文 `_en` 表）；同一意图的两套词表永不同时在内存（避免命中歧义）。生成物按语言分载：唯一来源按语言各一份 → 派生 `routes.<lang>.generated.ts`（或同文件内按语言分表＋加载器按语言单选，二选一由试点 #1202 按“插件层可达性＋结构门改动成本”裁载体，本票不定载体）→ `gen:check` 按语言分别校验。

## 被否方案

- 全量 747 英文首轮全翻：否。翻译成本（747 场景＋触发器 7085 条级字面量）与“英文按需（翻译是期权）”冲突；且 700＋ 长尾场景无英文用户实测，翻完即陈化。
- 中英双表同时加载＋双语命中：否。与票面“避免同一意图两套词表造成命中歧义”直接冲突；且 HELP 是 agent 选命令的机器可读清单（help-pipeline §2），双表会让同一短语落两个 key。
- 英文复用中文路由（只翻 HELP 页面不翻唤醒词）：否。英文用户“说一句英文”到不了任何命令，英文页即孤岛。

## 英文用户可复现验证方式（待英文表落地后跑，形状先行）

- 中文基线（现有）：中文短语 → `dispatch(key)` 落到正确命令（各包现有 lookup/routing 单测即此形状）。
- 英文对照（新增）：切 `language.text=en` 后，英文短语 → 同一 `key`（如英文 “calorie help” → `calorie.help.center`；英文 “log meal” → 记一餐对应 key）。中英各跑一遍，不混载；未切语言时英文短语不命中（路由表只有一套的证据）。
- 本票不新增英文词表，故本次无英文命中读数；首批 30 条英文表由对应迁移票承接，届时按上式逐条给出读数。
