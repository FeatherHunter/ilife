**读数结论（能／不能＋为什么）：**

1. **今天插件侧摸不到任何公共层包**：七家插件对 `base-*` 与 `skill-*` 都是 0 import；插件与技能之间是 **spawn 进程边界**，插件拿到的只有技能 stdout 的 envelope 与产物路径。**所以文本外置无论住哪层，插件都不该、也不能"直接"取词**——它要的语言效果只能经技能进程产出。

3. **住 base-render 组件层共用位：插件侧完全不可达**——插件不 import `base-paint`，且组件层共用位不在包的 `exports` 里（连线都开不出来）。这条路只能服务"已消费 base-paint 的六个技能"。

## 结论（给维护者裁的三条路）

- **路 A（试点已实测）**：机制住新公共层包，`base-render` 直接依赖它 → 代价＝上面 3 处断言 ＋ 2 行发布链表。
- **路 B**：机制住新公共层包，但 `base-render` **只收调用方注入的取词端口**（组件入参加 `entries`／`resolve` 端口，
  import 落在技能侧）→ 零红线；代价＝28 张迁移票的**每个调用点**都要显式传端口（"加一门语言＝加一个文件"仍成立，
  但"不改代码"在调用点这一层要重述）。
- **路 C**：机制住 `base-render/src/components/shared/`（组件层共用位）→ 插件侧不可达（读数①第 3 条），
  且六个已消费技能可以走 `base-paint/blocks` 取到；代价＝公共层包（base-entries）作废或降级为内部件。

读数的倾向：**路 A**。理由：今天唯一会取词的消费面是**六个技能 ＋ 页面渲染**（插件侧 0 import），
而"零运行时依赖"这三条红线的原始目的是**拦住 `node:` 与第三方供应面**（`contract-signatures` 那条同时断 `files` 覆盖发布面），
不是拦住公共层内部的相邻包；把断言口径改成"零 `node:`／零第三方，公共层边白名单"后，
"加一门语言＝加一个词条文件"在**任何一层**都仍然成立。
