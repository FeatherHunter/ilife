# 结构纪律

改代码、加能力、建目录一律照这份走。这份只管**形状**：谁住哪、对外给什么。名字见 `wording.md`，实现怎么算不归它管。

## 管辖

管 `packages/` 下全部源码：技能、插件、公共层，每个文件都管，无大小之分。

不管：测试文件、页面模板、构建产物、生成的资产、文档。

## 公开接口

一个能力对外开的门。别的能力要用它，只经这个门；门里怎么实现，外面不看。

下文说「接口」一律指这个，不指函数的参数表。

## 五条铁律

铁律是底线，不随包不同而变。五条同时成立才算达标；任何一条不成立，这次改动就没做完。

### 铁律一 · 能力自治

一个能力的代码住在自己那个目录里。要用别的能力的东西，走它对外那一个公开接口。**把对方那份抄一遍放进自己目录，不算走了接口**——抄的那份迟早和原份走散，走散之后同一件事会算出两个结果。

- 判据：这个文件里的东西，是不是都只属于一个能力？
- 违反的样子：两个能力的文件互相引用内部件；把对方那份抄一遍；一个文件里同时改两个能力的逻辑。

### 铁律二 · 概念唯一

同一个东西——常量、类型、公式、口径——在整个管辖范围内只有一个定义地，别处引用它。

**清单另有一套规矩**：规矩里出现的清单，要么标出处并说明它只是外部观察、没有规定力，要么换成一个指向权威出处的指针。会过期的清单不进规矩。

- 判据：把这个名字搜一遍，定义只出现一次；规矩里的每份清单都指得出出处。
- 违反的样子：同一个常量在两个文件里各写一份；两个文件各抱一套同名字段；把一份会过期的清单抄进规矩里当规定。

### 铁律三 · 改动可预告

动手前把「会碰哪些目录」写出来，交付后对得上。类型上写得出具体形状：不出现 `any`，不出现说不出形状的 `unknown`。

- 判据：事前清单与事后对账逐行对得上，偏差为零。
- 违反的样子：干完才说碰了什么；碰了没说；说只碰一个目录结果碰了三个；类型一糊，这次改动的影响范围就说不出来了，这条跟着一起废。

### 铁律四 · 名字取自 HELP

能力目录名取自 **HELP 的一级分组**；目录里的文件名与公开接口名取自**下一级**（子功能）。名字只许从 HELP 的现成说法里取，不许自创。

- 判据：把目录名念给用户听，他能在 HELP 里指出这是哪一组；文件名同理。
- 违反的样子：按工种或角色起名（`utils`、`helpers`、`common`、`misc`、`core`、`types`、`base`）；名字带 `2`／`3` 的第二次追加；自造一个 HELP 里没有的词。

### 铁律五 · 接口小、里面厚

对外给的东西少，藏在里面的活儿多。一个文件对外给的东西不多于五个，一个类型的字段不多于八个，其中至少一个真正干活。

**只做汇总的能力另有一条**：一个能力如果只是把别家的结果拼起来，它不许重算别家的口径，只许调别人的公开接口。

- 判据：数得出一个文件对外给的东西有几个；删掉一个转发函数，外面说不出少了什么，那它就是白占一层；对汇总能力，问一句「删掉它，别家会不会各算一遍」——会，说明它在干活；不会，说明它在抄。
- 违反的样子：一个接口二十个字段；一个文件导出九个平级函数；一层只做转发的包装；汇总能力在自家目录里把别家的公式又写了一遍。

## 结构标准

标准随包不同，按各包自己的情况定；与铁律冲突时铁律胜。

- **能力目录**：`src/` 下第一层必须是能力名，不能是工种名。
- **能力内部**：按这个能力自己的活分，一层到两层即可。分层依据是**变化频率**——同一批改动一起改的东西放近，不同批改动改的东西分开。内部每一层只许往下用，不许反向。
- **依赖方向**：能力只往下用东西，不许反向。共用位里不许出现任何一个能力的名字。
- **共用件**：能力之间要共用的东西放共用位，并且写得出**哪两个能力在用**。写不出来的，留在那个能力的目录里。**共用位是从第二个用法里长出来的，不是预先设计的。**
- **就地摆正**：旧代码与新规矩不一致时，在本次改动里把它摆正，不另开票，也不顺手扩大范围。
- **一次性脚本**住包内 `scripts/`，与源码目录分开。
- **文件行数告警线**：具体数字由各包自己定，写在各包自己的地方。超线即触发第五步，不是拦路。

## 必报五步

五步是**动作**：改管辖范围内任何一件的源码时，按序做，每步报给用户。

### 第一步 · 影响清单

动手前报：新增或改动哪些目录、哪些文件，每个文件一句话，以及碰它的理由。用户看过再动。

- 判据：每行指向**一个**能力目录；一行里出现两个能力名，就是这一步没做对。
- 一行要给两个能力时，写明理由：走的是哪个公开接口，或者为什么属于共用件。

### 第二步 · 结构设计

报出这次要新增的目录树、每个文件的职责、每个文件的公开接口给什么（导出几个、各一句），以及共用件被哪两个能力用。

- 判据：目录名与文件职责都念得出用户的话；每个文件对外给的东西数得出不超过五个。
- 新建目录层级、或者要碰三个以上能力时，等用户点头再动。

### 第三步 · 写代码

- 跨能力引用写对方的公开接口。
- 常量与类型只写一处，别处引用。
- **只有出这个目录才算对外**：目录内互相用的东西不必对外给，接口自然就小。
- 旧代码与新规矩不一致时，在本次改动里就地摆正。

### 第四步 · 超线报警

任何文件超过本包定的告警线，当场报一句：**「已超线，需要根据规则进行重构。」** 后头接一句为什么超，再给拆法或说明这次为什么先不拆。

- 只有告警线这个数字触发报警；五条铁律随时可查，不靠行数触发。

### 第五步 · 交付对账

交付时报：实际碰到的目录，逐行与第一步的清单对。有偏差标出来。

- 完成判据：第一步每一行都有着落；报完这一步时偏差为零。**这是整套纪律唯一的机械验收点**——前面几步是过程，这一步是账。

## 来源

铁律取自已成规模的 TypeScript 项目的公开规矩，按本仓情况裁过。

- **VS Code**（[copilot-instructions](https://github.com/microsoft/vscode/blob/main/.github/copilot-instructions.md)）：干活的能力按 `contrib/<能力>/` 一能力一目录；不许用别的组件的存储键去改那个组件，必须造出正确的接口；依赖方向单向；不需要跨组件共用的类型和函数不对外导出。它的能力内部按**运行环境**分层（`browser/`／`common/`／`node/`），那是它跑三种环境才需要的，只有一种环境的包不必抄。
- **bulletproof-react**（[project-structure](https://github.com/alan2207/bulletproof-react/blob/master/docs/project-structure.md)）：跨功能互相 import 不是好主意；依赖单向（共用 → 功能 → 应用）；共用件与功能**并列**，不在功能里面。
- **Node.js 最佳实践**（[按组件组织](https://github.com/goldbergyoni/nodebestpractices/blob/master/sections/projectstructre/breakintcomponents.md)、[分层](https://github.com/goldbergyoni/nodebestpractices/blob/master/sections/projectstructre/createlayers.md)）：组件之间**不共享文件**，只经公开接口消费；组件内部按关注点分层。

**没有取的**：代码风格（缩进、引号、异步写法、注释格式）、测试断言的形状、运行时模式（依赖注入、配置分离、日志与错误处理）、构建发布口径——那些属于别的题材。
