④ 对抗式审查：我原来的判断被戳了七下

攻击点结论
1. 「六家缺口径」的判据是我自己写的契约 ⇒ 自证循环？ 部分成立 判据站得住（你审过、#734 也记了「路线②必做兜底」），但「做不做」是产品判断，契约推不出来
2. 这个缺口真的会造成故障吗？ 被压缩 只有两个窗口，主路径不受影响 ⇒ 上次的措辞给了它过高的紧迫感
3. 有没有更本质的解法（宿主侧把形态喂给模型）？ 已排除 可行但无用；反倒证明「磁盘现读」是说明面改法的独有优势
4. 删掉 npm/npx 会不会堵死一条路？ 会 改为降级＋去钉版号，而不是删除
5. 补口径会不会把模型从「工具」引回 shell？ 真实风险 可控：口径只写「命令名不可解析时」用，上线后再抽验一次会话行为
6. 成本估对了吗？ 我低估了 还有各包版本钉、旧向导、示例门、逐包测试门
7. 方案有没有看守？ 原来没有 必须补一条门，否则改完就会烂（见 §⑤ 第 3 条）
三条关键推理（为什么这么判）
  • 为什么「磁盘现读」值钱：用户装完插件、还没重启时，跑着的是旧插件代码——但技能正文是每次调用现读文件的，所以只有「改说明面」这条路能在这个窗口里生效。
  • 为什么宿主侧注入被排除：那段说明住在插件代码里；旧进程加载的是旧代码，天然没有它；非 DSH 宿主更是根本看不到插件。
  • 为什么必须配门：六份说明面是各自独立的文件，靠人自觉保持同一句口径一定会走散（仓里已经有一批「说明面与行为对不上」的旧账）。门要能变异自证：拿掉一块 → 红，写回 → 绿。

⑤ 修正后的方案（若选「做」）

  1. 单一来源：口径正文住在 docs/agents/技能调用契约.md（这套规矩的家），由一个仓库级生成器写进六份 SKILL.md 的标记块。
  2. 清脏读数：卡路里（第 28 行仓内路径；第 554-556 行＝钉 @0.2.6＋自称 @0.2.4 的自相矛盾）、居家（第 159 行「这两条现在必失败」；第 164 行 shell 里仓内路径）。npm/npx 两句降级为最后兜底、去钉版号。
  3. 配门：断言六份都有该块且六份逐字相同；全仓 SKILL.md 里 packages/skill-／npm install -g／npx -p 命中 0；挂进 pnpm gen:check，带变异自证。
  4. 一轮发布：六技能统一 0.3.0 → 六单品 pin 同步抬 → 发单品 0.3.1（顺带把欠着的 ^0.3.2 范围发出去）；总管不动。
  5. 验收：六家各跑 pnpm gen ＋ 包门；用装机副本真跑一次 node <技能基目录>/dist/cli/cmd_read.js <key>（exit 0 ＋ 绝对路径回执）；最后你在会话里说一句抽验。
