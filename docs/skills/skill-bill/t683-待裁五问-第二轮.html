Q9 域内部：平铺还是分层

前因：Q8 定完，write/ 是 25 ＋ 20 ＝ 43 件，会成为全仓最大的域目录。仓规说「能力内部按变化频率分一层到两层即可」，但没说什么时候该分。兄弟件的答案是平铺：卡路里 10 个域全部平铺（diet 30 件／workout 29／photo 27；只有 analysis 带 1 个 anomaly 子目录）。

A · 先平铺，同时写死一条触发条件

  • 利：与兄弟件同形（30 件仍平铺）；scene-*、collectBody 这类前缀已自带分类，先加一层属于「预先设计」——仓规写明分层是从变化频率里长出来的。
  • 弊：43 件确实是全仓最大，得靠写死的触发条件（例如「某域超 50 件、或出现两个明显变化频率族时再分层」）而不是自觉来兜。

  • 利：职责一眼分明，43 件的目录变 27 ＋ 16。
  • 弊：为一件还没发生的变化预先分层；与兄弟件不同形，看两个包要多一套心智。

  • 利：最灵活。
  • 弊：7 个域各拿一个答案，正是本票第 1 条要防的「走完 7 域各长一套」。
➡️ 推荐 A：平铺 ＋ 触发条件写进文档（触发条件本身就是这条规矩的可查部分）。

Q10 命名与分工三条细则

前因：铁律四只管「能力目录名取自 HELP 一级分组、目录内文件名取自下一级」。可 shared/、render/、cli/ 这些盒子不对应任何 HELP 组，它们的文件名按什么立？不写清楚，下一位会拿铁律四去质问共用位文件名。另外两个盒子（triggers/ 与 help/）的分工、以及三处同名不同物，也都要落纸。

A · 三条照写

  • (a) 命名：域内文件名取自 HELP 场景 id 的 slug（老侧 write_expense → expense，这是「下一级」的可执行版本）；共用位与外壳件用技术名（commandSpec／docPage／envelope），铁律四不适用——这条要写进文档。
  • (b) 分工：triggers/＝触发与路由的机器面（派生记录面 ＋ routeWakeword 这类查询逻辑）；help/＝交付面（SKILL 速查、HELP 页装配、bill.help.lookup 声明）。照卡路里「声明住域、记录面住 triggers/」。
  • (c) 同名不同物三条写死：write（域名）vs kind:'write'（命令种类）；analysis（域名）vs shape:'analysis'（页形状）；目录旧名 record vs 命令 key bill.record.*。

B · 命名细则留给各域票

  • 利：本票少写一节。
  • 弊：每个域票都会各答一次，答案不保证同形；改名后「目录 write／key record」的疑惑会反复出现。

C · (c) 只进 ADR，不进技能文档

  • 利：ADR 更全。
  • 弊：ADR 分工已定为「只放规则」，同名不同物是读这份技能文档时才需要的对照，放错地方等于没放。
➡️ 推荐 A：三条都是执行者第一次翻文档就要查的东西，散到各域票里等于没有。
