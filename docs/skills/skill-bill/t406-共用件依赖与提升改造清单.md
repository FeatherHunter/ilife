## 三、提升到 base 的改造清单

先说公共层的一条硬边：`base-render` 不许反向 import 技能包（现状核对——`base-render/src/index.ts` 全篇 40 行只导出自身模块，无任何 `skill-*` 依赖）。所以凡是「收据对象」这类参数，公共层只能收结构，形状定义必须一起搬。

### 1. `commandSpec.ts` → **不上移**

- 新增 base 导出：无。
- 要加的参数：无（不上移）。
- 会不会改到卡路里现有页面产物：**不会**——它一个 HTML 字符都不产生，只定义类型。
- 理由与依据：`CommandSpec` 是「命令事实的唯一定义地」，而命令事实按仓规住各能力目录（`docs/agents/命令登记纪律.md`，「一条命令的事实只住它自己的能力目录」）；本件自己写的两个用法（各能力 `commands.ts` 与出口分派索引 `cli/registry.ts`，`commandSpec.ts:4`–`:5`）全在卡路里包内。饼干的命令事实已另有住处（`packages/skill-bill/src/policy/wakewords.ts:5` 的 `BillKey`）。

### 2. `writeParts.ts` → **拆开：机制上移，字段表与两处字面量留技能包**

- 新增 base 导出（5 条）：`countChanges(db)`（＝今天的 `totalChanges`，`writeParts.ts:38`）／`deleteStatus` 与四条删除措辞常量（`writeParts.ts:19`–`:27`）／`receiptShell({ skill, slotPrefix, scene, summary, op, recordId, items })`（＝今天的 `receiptHtml`，`writeParts.ts:83`）／`commandLineOf({ cli, key, params, flagPrefix })`（＝今天的 `commandLine`，`writeParts.ts:101`）／`writtenFieldNames(input)` 与 `definedKeys(input)`（＝今天的 `provided`／`definedKeys`，`writeParts.ts:70`／`:75`）。`R`／`out` 与收据形状一起上移（依赖第 4 条的 `CrudReceipt`）。
- 要加的参数（把卡路里专有的东西参数化）：
  1. `skill: string` ＋ `slotPrefix: string`——替掉 `writeParts.ts:87` 里逐字写死的 `data-skill="calorie" data-slot="ilife:calorie:receipt"`；
  2. `cli: string` ＋ `paramsFlag: string`——替掉 `writeParts.ts:102` 里写死的 `'calorie-cmd-read ' + key + " --params '"`；
  3. 字段表：`F`／`COL_CLI` 两件（`writeParts.ts:45`／`:56`）按仓规搬回各能力目录（字段事实归能力），公共层只留 `provided`／`definedKeys`／`cliNames` 三个纯函数；`cliNames(cols, table)` 多收一个表参数。
- 会不会改到卡路里现有页面产物：**会（若不改造就上移）**，依据——回执片段的那行属性是产物断言钉死的：`packages/skill-calorie/test/profile-doc-179.test.mjs:279` 要求文件以 `'<section class="ilife-page" data-skill="calorie" data-slot="ilife:calorie:receipt">'` 开头，同批反面断言在 `test/profile-doc-179.test.mjs:5`。**改造后不会**：只要卡路里侧继续传 `skill='calorie'`、`cli='calorie-cmd-read'`，逐字节不变（机理由第 3 行的参数化保证）。
