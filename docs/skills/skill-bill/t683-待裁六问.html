当刻 src/ 一级 9 个目录 ＋ 3 个根件 ＝ 11,738 LF，但只有 2 个目录是 HELP 里的域（record/ query/）；policy/ 一个盒子装着 7 个域的口径，其余 6 个是工种名（cli fetch render shared triggers help）。仓规 docs/agents/structure.md 要求「一级必须是能力名」，而兄弟件 skill-calorie 的实况是域目录与横切层并存——本票要把「并存」升成可查的规矩，并给出逐件归属。

走查发现三处「票面判据／盘上实况」对不上

① 判据 vs 真共用件

判据写「共用位里不出现任何域的名字」，但 shared/pageShell.ts:22 的眉标表就是 Record<'write' | 'query'>，而它是 write＋query 两家在用的真共用件。

Q1 一级目录的三类准入（最顶上的一条）

前因：仓规只写「src/ 下第一层必须是能力名，不能是工种名」，但没人说过域之外的那些层该怎么立、凭什么留。兄弟件卡路里是域与横切层并存：10 个域 ＋ cli/fetch/render/shared/triggers 5 个横切层 ＋ db/migrate/xunji 3 个例外。不把「并存」写成准入判据，7 个域走完就是七套形状。
关键读数：一级 9 目录里，policy/ 483 LF 是唯一「7 个域的口径共用一个盒子」的目录；两个超告警线（350）的件都在横切层：triggers/wake-assets.ts 986、cli/cmd_read.ts 485。

A · 立三类准入

  • 利：每类都有可查判据（名字取自 HELP／说得出两个域在用／说得清为什么不是域也不是共用位），新目录加不进来；与卡路里实况同形，看两个包不用两套心智。
  • 弊：多一层「解释成本」，13 个一级目录要逐个写明身份；policy/ 的 483 LF 要散回各处（动作在别的票）。

B · 只留「域 ＋ 共用位」两类

  • 利：目录数最少；triggers 并 help、cli 并包根。
  • 弊：把「没人用的出入口」和「两家在用的共用件」塞进一类，下一位执行者分不清谁依赖谁；cli 是 Node 入口，并进包根会让包门与入口混一层。

C · 不分类，只列名单

  • 利：这一票最小、最快。
  • 弊：等于没定规矩——「为什么留 render/」答不出来，下一票就会来问同一件事（#682 台账已为此记过教训）。
➡️ 推荐 A：结构标准 只写了「能力目录」一条，A 是把卡路里的既成实况补成规矩；B／C 的省事要用后面每一票重新讨论来还。

Q2 record/ 是否改名 write/

前因：铁律四的判据是「把目录名念给用户听，他能在 HELP 里指出这是哪一组」。HELP 一级分组的 7 个 id 是 write query analysis goal account link setup（对应中文 写入／查询／分析／目标／账户／联动／开始使用），没有 record；反而代码里已经用 write 当域名（shared/pageShell.ts:22 眉标表键值）。
改名触面（当刻实测）：src/**/*.ts 里 73 行引用 record/、测试 5 行，命中 47 个文件；packages/skill-bill/AGENTS.md 两张表与多份证据件的行号锚点会漂。
不能动的：bill.record.* 这 6 条命令 key 是跨技能契约（#682 §4.A-2 A2-1「key 字符串后续票落表时冻结」）——只改目录名，key 不动。

A · 目录改 write/，key 不动，执行交 #689

  • 利：铁律四成立（write 直接指向 HELP「写入」组）；改名与 write 域自身的重构同窗做，不额外开窗。
  • 弊：73＋5 行改动与 47 个文件触面；「目录 write／命令 key record」两套名字并存，必须在文档里写明这不是一件事。

B · 目录留 record/，文档里记例外

  • 利：零改动、零风险。
  • 弊：让本票正要立的「名字取自 HELP」对自家第一个域就失效；下一票会来问凭什么。

C · 连 key 一起改成 bill.write.*

  • 利：名字彻底统一。
  • 弊：破跨技能契约，要同步 plugin-bill-ilife 与 base-combos（且插件侧有別席在途），出本图范围。
➡️ 推荐 A。顺带一件必须在文档里写死的：write（域名）与 kind:'write'（命令种类）、analysis（域名）与 shape:'analysis'（页形状）是同名不同物——不写，下一位执行者会把它们当成一件事。

Q3 help/ 的身份怎么立

前因：今天 help/ 3 件 172 LF（lookup.ts 55＝SKILL 速查 77 行；writeWire.ts 115＝写域 16 词接线对账；index.ts），而 HELP 页面不由它出——出页面的是 cli/cmd_read.ts 的 help 分支 ＋ render/helpFile.ts(185) ＋ triggers/wake-assets.ts。
两头压力：HELP 不是 7 个一级分组之一 → 铁律四下立不住；但命令登记纪律（docs/agents/命令登记纪律.md:8）说「一条命令的事实只有一个定义地，就是它自己的能力目录」，而 bill.help.lookup 是 16 条 key 里的一条。
兄弟件参照：卡路里没有 help/ 目录，它的 HELP 命令 calorie.help.center 挂在 src/photo/commands.ts 里。

A · 立 help/ 为非域一级目录（第三类）

  • 利：命令有家，命令登记纪律不破；render/helpFile.ts ＋ helpPaths.ts 搬进来后，HELP 的交付面集中一处。
  • 弊：非域目录要常驻一句「为什么它不是域」，否则下次走查又会被当违规；与卡路里形状不一致。

B · 照卡路里挂进一个域（本包最贴 setup/）

  • 利：与卡路里同形，一级少一个目录。
  • 弊：setup 域凭空背上 HELP 的所有权（HELP_INIT_SCENE_ID='setup_init_wizard' 只是「引导语取自哪条场景」，不等于 HELP 属 setup）；卡路里那条是历史遗留而非设计。

C · 不立目录，命令声明挂 cli/

  • 利：不动目录结构。
  • 弊：直接违命令登记纪律（命令事实进了共用位），正是「冲突为何消失」要解掉的那种形状。
➡️ 推荐 A：help/ 的定位写成「交付面——用户可点的一级入口，不持账目事实」；render/helpFile.ts 与 helpPaths.ts 随本决定搬入。

Q4 shared/ 25 件的分档（归属律 ＋ 读数）

前因：票面写「共用位里不出现任何域的名字」，但没说怎么判一件是不是共用件。仓规的判据是「写得出哪两个能力在用」，且「共用位是从第二个用法里长出来的，不是预先设计的」。按这条一量，当刻 shared/ 的分档是：
5 件真共用（423 LF）：commandSpec(74 ← cli+query+record)、copyArea(159)、pageIdentity(36)、pageShell(65)、writeParts(89)（后四件 ← write+query）。
2 件间接（184 LF）：docPage(130 ← pageShell)、errorReceipt(54 ← blockedSlots)，只被 shared/ 内部用。
18 件（2,038 LF）只被 record/ 用：recordPicker(247)、photoEscape(181)、installmentPreview(170)…

A · 按律搬：18 件下沉 write/，shared/ 只留 5 件

  • 利：shared/ 回归「跨域公共件」的本义；下一票（analysis）写页时在 shared/ 找到的都是真公共块。
  • 弊：18 件搬家有触面（引用行、测试）；2 件间接件随 pageShell 的处置走，要单独裁一次。

B · 全留 shared/，等各域票自己来搬

  • 利：本票零动作。
  • 弊：把「找错块」的坑留给下一票；每个域票都会重议一次同一条判据。

C · 只留真共用，其余先记债务清单不搬

  • 利：不动代码就把账记清。
  • 弊：清单本身会过期（#682 §1 已记过这个坑），下次仍然要逐件重判。
➡️ 推荐 A，并把它写成四条归属律：①只属于一个域 → 住那个域；②说得出两个域在用 → 共用位；③说得出是外壳或派生件 → 第三类；④三条都说不出的件不许存在。搬的执行不在本票（票面已划出「命令的搬迁动作」），归 #689。

Q5 四个没被点名的疑难件落点

前因：票面的归属表只点了 6 件（analysis/goals/accounts/record.ts、helpFile、wake-assets），实际还有四件说不清，其中两件是「两个域经它对话」的口径件：

(a) policy/category.ts 125 LF —— 分类表 ＋ 金额/时间/日期校验

  • 消费者 4 处：record/*（写入校验）、query/read.ts:24、render/views.ts:6（l1Of）、shared/* → 两域在用。
  • 它管的是用户念得出的词表（餐饮/居家/…/借贷/分期/转账）＋默认值，属「口径」而非某个域的私产。

(b) policy/record.ts 91 LF —— 一半写域、一半是日期

  • 写命令 params 校验（parseRecordOp/validateAddInput/validateUpdateInput）→ 属 write/。
  • 日期与时间窗口（resolveQueryDate/resolveRange/monthRange/weekRange/yesterdayStr，#411 搬进来，消费者 query/read.ts）→ 与 (a) 的 normalizeDate/normalizeMonth 合成一处日期口径。

(c) policy/wakewords.ts 142 LF —— 77 词 → 16 key 的整表

  • #684（T3）已定「域声明住域目录、唤醒词唯一」→ 本票只定「不留 policy/，T3 把这 142 行拆进 7 份域声明」，不预定最终文件名。

(d) render/views.ts 125 LF ＋ render/helpFile.ts 185 LF

  • views.ts 里拴着 7 个域的东西：calcKpi（write/query 两家用）、buildOverview/buildCompare/buildTrend（analysis）、buildGoalQuery（goal）、buildAccountQuery（account）、buildRecordReceipt（write）、buildHelpItems（help）。
  • helpFile.ts 整个是 HELP 交付 → 随 Q3 回 help/。

A · (a)(b) 长成共用位；(c) 交 T3；(d) 域属回域、calcKpi 留共用位

  • 利：分类表与日期口径各只有一个定义地，第 3、第 4 个消费者（analysis 域 25 场景）一到就复用，不重算。
  • 弊：新建两个共用件（建议 shared/category.ts、shared/dateRange.ts，名字可再谈），views.ts 要按域切开。

B · (a)(b) 整体归 write/（谁校验谁持有），别的域经 write 的门取

  • 利：不新建共用件，写入路径最简单。
  • 弊：query 为了校验一个分类要去引 write 的门，语义错位；analysis 一到就变成三方耦合。

C · (a) 归 write/、(b) 的日期半归 query/

  • 利：按当下消费者就近放。
  • 弊：日期口径横跨 write/query/analysis，挂在一个域下就是等着被抄第二份（铁律一）。
➡️ 推荐 A。风险提示：(d) 的拆件与 T4（#685「页面装配深模块的接口与 7 域页型清单」）天花板撞车——views.ts 的最终去处要在 T4 落地后复核一次，本票只定方向（各域票执行）。

Q6 决定怎么立住：接缝分工 ＋ 守卫 ＋ 留存载体

前因：本票是决定票（票面产出的是决定、不是改动），所以真正的风险是「决定写完没人执行、或各票各理解」。需要一次把「谁搬、谁拆、谁守、写在哪」说清。

接缝（建议）

  • 改名 ＋ shared/ 下沉 → #689（write 域：形状重构与 parity 优化）
  • 域声明 ＋ 唤醒词表拆分 → #684（T3）；页面装配形状与 views.ts／helpFile.ts 终局 → #685（T4）
  • 机器守卫 → #686（T5「机器面照卡路里装齐」，它的定位就是落门）

守卫四条（#686 落，白名单取自本票文档）

  • ① 一级目录 ∈ 白名单，只许删不许加；② 域之间零直引，只经对方 index.ts；③ shared/** 不出现 7 个域名（含 pageShell 那条眉标改成「域自报 eyebrow 参数」）；④ 每个域目录恰一件 commands.ts。

A · 载体＝技能文档 ＋ 新 ADR-0003（推荐）

  • 利：三类准入是跨技能通用规则（卡路里 #699 那条整改线在做同一件事），一份 ADR 供两边引；逐件归属只住技能文档，分工写死。
  • 弊：多一份要同步的文档；ADR 与技能文档必须分工明确，否则同一件事两处定义。

B · 只写技能文档 docs/skills/skill-bill/t683-目标src形状.md

  • 利：一件交付物，最省。
  • 弊：跨技能通用的规则被埋在本包文档里，卡路里线要么引一份别的包的文档，要么自己再写一份。

C · 直接改仓规 docs/agents/structure.md

  • 利：规则离读者最近。
  • 弊：仓规的分层表写明「结构标准由维护者改，AI 报理由后可提改」——本票只提请、不代改。
➡️ 推荐 A（接缝）＋ A（载体：技能文档 ＋ ADR-0003）。本票零源码改动，交付物＝docs/skills/skill-bill/t683-目标src形状.md ＋ issue 正文结论 ＋ ADR-0003。
