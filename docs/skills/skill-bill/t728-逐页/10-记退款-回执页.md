## 3 设计方案：这一页该长成什么样

### 3.0 先说这一页**是什么**

这是一张**回执**（`data-key="record.add"`，`status: ok`）。回执的第一读物是「**多少钱、进了哪、能不能反悔**」，不是一块 8 格的仪表盘。现在的页子把「票据」当成了「看板」：8 张等权读数卡 + 两张同构的表 + 一条满列红条，**没有主角**。

### 3.1 版式：把「8 张读数卡」换成「1 张票据头 + 1 组键值行」

- **改哪一个件的哪一条**：`packages/skill-bill/src/write/template-flow.ts` 的回执支路里，`kpiCards` 的序列从 8 项收到 **2 项**：`金额`（值 `+20.00`，字号由 `--kpi-value` 那一档抬到 32px）与 `状态`（渲染成 `ilife-status-badge-ok`，不再占一张卡）；其余 6 项（分类／账户／账本／币种／时间／记录编号）**下沉进 `#sec-detail` 的键值表**，不再各占一张卡。
- **为什么好看**：390 档现在 850px 的卡片墙压成一张约 120px 的票据头，页面从 2142px 收到约 1200px，**主次立刻分出来**（用户第 3 条：像 UI 设计师做的版）。信息一条不少 —— 8 个值全部仍在，只是从「8 张同重量的卡」变成「1 个主角 + 1 张明细」。
- **顺带治 D8**：那 3 条 `不填就记…` 的 detail 在 `template-flow.ts` 里删掉（回执页不写填表提示）。

### 3.2 明细改成「键值行」，窄屏不再逐行印列头

- **改哪一个件的哪一条**：`packages/skill-bill/src/write/` 里产出这张表的那一支，**窄屏形态不给「键」格写 `data-label`**（键名本身就是层级，不需要再印一遍列头文字）；同时在值缺省时渲染 `—`（D6）——`renderDataTable` 侧只做「值不存在就落一个占位符」这一件事。
- **为什么好看**：用户第 5 条的原话是「该用这些符号简化 UI 展示的设计」——现在的做法正相反：**该由版式出的层级，被 20 行重复文字顶替了**。去掉后 390 档表体从 490px 收到约 250px，而且每一行变成「键（`--fg2`）左、值（`--fg` 加粗）右」的一条干净键值行。桌面端（≥820）把这张表排成**两列键值网格**（一行放两组），878px 的列宽从「每行 72% 是白」变成实际用得上的四格。
- **顺带治 D3**：表不再靠「值列吃掉余宽」来撑满，而是靠列数分组用掉宽度。

### 3.3 桌面：把 2128 条那条死规则救活

- **改哪一个件的哪一条**：`template-flow.ts`（及同族模板）**不要**在块外面再包一层 `<section id="sec-kpi">`，把 `id` 直接挂到块自己身上（`<div id="sec-kpi" class="ilife-block-kpi-card-grid">`、`<div id="sec-detail" class="ilife-block ilife-block-data-table">`）。
- **为什么**：公共层 ⑧ 条的 `> :where(…)` 才会命中，`grid-column:1/-1` 才会生效 —— 1280 档从 878px 可用变成 1240px（每边收回 175px 死白），读数卡从 209px 变约 298px，`时间` 值不再折行，两行卡等高（治 D2）。**改的是本包模板，公共层一行不动**，不触碰「32 页共用一张表」的红线。
- 若维护者更想留在公共层收口：在 ⑧ 条的候选清单里补「带 id 的 wrapper 层」（`#sec-*`），但那要新造选择器形态，不如上面那一行干净。
