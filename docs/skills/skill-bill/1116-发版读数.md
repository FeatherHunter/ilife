### 三、`--pre` 那条红：是什么、怎么处置（据实记，防陈化）

1. **它是什么**：`packages/plugin-manager/package.json` 写 `dsh-plugin-update: ^0.2.0`，而 registry 上该包已到 **0.3.0**——**`^0.2.0` 这个范围本身不含 0.3.0**。`pnpm-lock.yaml` 里锁的是 `dsh-plugin-update@0.2.0`，门禁就读作「更新器落后」；它给的那句修法（`pnpm up dsh-plugin-update@latest`）**在这个范围下必然不生效**。
2. **窄口径试过（Lead 授权 (a)）**：留底 `.scratch/1116-发布/pnpm-lock.bak`（`git show HEAD:pnpm-lock.yaml`，1342 行）→ `pnpm up dsh-plugin-update@latest` → 工具回 **`Already up to date`**、exit 0；**但锁文件确有改动（32 增 40 删）且越出授权面**：除把 16 份 `package.json` 的 specifier 反映进锁，还把 6 个插件的 `dsh-life-pack` 从 `version: 0.3.30`（registry）改成 **`version: link:../plugin-manager`**（工作区链接）。
3. **处置**：按 Lead「宁可回退走 (b)」——**用留底文件 `Copy-Item` 回退**（非 git 命令），回退后 `git status -- pnpm-lock.yaml` 干净、锁回到 HEAD 内容；**未触发** `ERR_PNPM_MODIFIED_DEPENDENCY` 那条已知陷阱；**未手改** manifest 范围（以工具行为为准）。
4. **裁决**：Lead 2026-10-04 **裁 (b) 带这条已知红发**——理由：改 `^0.2.0`＝动更新器插件的依赖策略（用户侧会跳到 0.3.0），该单独立项、不该塞进这次「版本对齐」；按负责人新入仓的「遗留先记文档、聚合后限量开票」纪律，本段即文档落点，**不另开票**。
