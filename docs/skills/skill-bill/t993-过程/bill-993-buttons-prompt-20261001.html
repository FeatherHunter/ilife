#993 · 详情三钮 + 撤销 prompt

改记录最值钱，返回最鸡肋，撤销要配 prompt

结论先行，细节在下面。

详情三按钮的价值

按钮价值理由
改记录最高 ★★★详情页主任务就是“看见错→立刻改”。7222 本来就是账户记错了才改的，详情看到账户不对，下一步一定是改。删了它等于断了主流程。
返回低 ★浏览器自带返回；只有从列表点进来时才顺手。静态原型里它根本没地方可回，属于占位。建议缩成幽灵小字，不占主位。
删记录低频危险 ★一个月用不了一次，且不可逆手感（虽是软删可恢复，用户仍怕）。不应与改记录并列三等分，建议收进次级确认或折叠。
建议排布：改记录主按钮 + 返回小字 + 删记录收进“更多/危险区”。原型里三等分只是占位，不是定稿。

撤销这一笔的 prompt 设计

按钮负责点，prompt 负责让 AI 一次跑对。形状固定三行：人话一行 + 可执行命令一行 + 口径一行。

撤销这一笔（7222：餐饮／咖啡奶茶 -40.80 元）
bill-cmd-read bill.record.update --params '{"op":"undo","id":7222}'
口径：撤销只打标、可恢复，原记录保留痕迹
  • 通用模板把 7222 换成记录编号即可，命令名取自 HELP，不自造。
  • 按钮本身不带复制载荷冒充复制（之前的同病不再犯），真正的载荷走复制数据。
  • 恢复的 prompt 对称：{"op":"restore","id":7222}，文案“恢复这一笔”。
