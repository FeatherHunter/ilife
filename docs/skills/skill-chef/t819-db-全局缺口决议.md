# t819 数据库层两处全局缺口决议

MAP：parity 图（`map-chef-parity-body.md`）。Destination＝48 卡逐卡事实正确＋双端 HTML。
本票只裁定、不改 schema、不碰真库。全部读数出自副本库。

## G1 重名判定

结论：应用层唯一校验＋出图 schema 票（双轨）。

口径：`name.trim()` 后精确相等、大小写敏感（与未来 `UNIQUE` 的 BINARY 语义一致，不做归一化）。

对抗式审查：允许重名→`mustRecipe` 的 `WHERE id=? OR name=?` 在重名时取哪一行不确定，违背事实正确，否决；
仅立 schema 票、本期不拦→在 schema 票落地前 `#773/#774` 仍可写入重名，窗口期不正确，否决；
应用层先拦＋DB 后加固→即时正确＋ durable 保证，唯一同时满足 MAP 目标与老 schema 权威的方案。

落点票号：应用层校验落在 `#773`（录入按名新增）与 `#774`（修改按名改名），含 `mustRecipe` 同名多行报错收紧；
durable 加固另开出图 schema 票（parity 图外，见遗留出口），本票不建索引。

判真假命令（副本库）：`SELECT COUNT(*) FROM recipes WHERE name='辣椒炒肉'`，0 行不存在、1 行唯一通过、≥2 行撞名应拦；
未来索引判真：`SELECT sql FROM sqlite_master WHERE name='ux_recipes_name'` 有行即生效。

正例读数（应用层能拦）：副本库已有 1 行 `辣椒炒肉` 时 `SELECT COUNT(*)` 得 2（在 dup 试验后）， verdict=`撞名应拦`。

反例读数（缺口存在）：向副本库直插同名 `辣椒炒肉` 成功，`G1_dup_insert=OK(缺口存在)`，`G1_same_name_rows=2`。
复现：复制真库到临时库后执行与 `db.ts:210` 同形 `INSERT INTO recipes (…) VALUES (…,'辣椒炒肉',…)`，不报错；
实跑：`node tooling/run-locked.mjs --ticket 819 -- node .scratch/t819/probe2.mjs`。

## G2 外键开关

结论：统一开（显式化）。

落点票号：只改 `packages/skill-chef/src/fetch/db.ts` 的 `openChefDb` 一处，加 `PRAGMA foreign_keys=ON` 一句；
不搬 `synchronous`／`cache_size`，不碰读命令的 SQL，读对外行为不变。

对抗式审查：按调用点开→同一约束散在多处，违背概念唯一，否决；
明确不开→与老件每连接 `PRAGMA foreign_keys=ON` 分叉，`CASCADE/SET NULL` 失效、孤儿行可写入，违背事实正确，否决；
统一开→与老件同语义，且实测当前运行时默认虽已为 1（`A_default_fk=1`），但属隐式依赖，显式一句才可移植、防回退。

判真假命令：`PRAGMA foreign_keys` 得 1 即开。

正例读数（开了拦得住）：`PRAGMA foreign_keys=ON` 后插坏子行失败
`G2FIX_mode=ON pragma=1 badchild=FAIL:FOREIGN KEY constraint failed`；
删父行级联 `G2CASCADE_mode=ON ing_before=11 ing_after_delete=0`。

反例读数（不开拦不住）：`PRAGMA foreign_keys=OFF` 后同句插入成功
`G2FIX_mode=OFF pragma=0 badchild=OK(未拦)`；
删父行留孤儿 `G2CASCADE_mode=OFF ing_before=11 ing_after_delete=11`。
复现：复制真库到临时库，`PRAGMA foreign_keys=OFF/ON` 后执行同形
`INSERT INTO ingredients (…) VALUES ('g2-bad-1','不存在的recipe-id',…)`；
实跑：`node tooling/run-locked.mjs --ticket 819 -- node .scratch/t819/probe3.mjs`。
现网安全：16 组孤儿计数全 0（12 张子表＋4 组关联表），可直接开、无需清洗。
