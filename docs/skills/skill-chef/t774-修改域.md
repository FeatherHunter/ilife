## 二、语义裁定（本票定，依据 769 对账 ＋ 818 定案）

1. 步骤重排：`from`／`to` 都是第 N 步序号，同菜两行存在且不等，三语句经 `-1` 中转、`BEGIN/COMMIT` 包裹（老件 `step_manager.py:reorder` 同形），失败即 `ROLLBACK`，不留半条。
2. 步骤改内容：按第 N 步或步骤编号定位到同一道菜，只改内容列，不碰顺序列。时长在追加一路必填，改内容一路缺省沿用旧值，给了就必须是有限数字。
3. 食材改用量：按食材名或食材编号定位到同一道菜；`quantity` 给了就必须是有限数字（818 定案甲，老库 `NOT NULL`，缺值取数层抛 `CHEF_BAD_QUERY` 即 CLI exit 4，不写半条）；纯文字修正可不带动数字。改名走专用键 `new_name`（`name` 是菜定位键，不可复用——自测抓到过一次复用导致改名串菜，当场改掉）。
4. 食材添加：走既有 `op=add-ingredient`（录入域实现，同样数字用量必填）。
5. 食材关联步骤：本期不开。`step_ingredients` 无写路径且 `quantity_used/introduced_at/unit` 另有必填；传 `step_id` 类参数即口径失败 exit 2，不静默丢掉。
6. 废弃：只置 `status=已废弃`，无物理删除；默认查询剔除，按状态可查回，查看页展示已废弃徽章。

入口注册表不动：`parseWriteOpCompat` 仍只认原 op 名；`target=step/step-order/ingredient` 是修改域内的子动作键（`src/update/run-write.ts` 内分流），不进 CLI 兼容集，不碰共用位。
`修改步骤`／`修改食材`唤醒词仍不可路由（#767 逐条影响表：实现前补入会误路由到主信息修改），本票走拟用命令直调；路由与说明面的同步归 #841。
