## 二 · 页族与 mode 分流

- `receipt` 一族吃四条（3-2／3-3／3-4／3-8）：回执消息前缀即 mode
 （已移动／已变更数量／已变更状态／已更新标签），族内分流标题与变更行，
  其余四段（当前状态／标签变更／处理明细／收尾语）按 mode 换文案。
- `tag_manage` 一族吃两条（4-1 总览／4-3 整理建议）：消息前缀分流
 （标签总览／相近标签／无相近标签），整理建议逐对给合并与忽略按钮。
- `confirm`（3-5）与 `undo_select`（3-6）是破坏性操作页，各单列一族，
  没有压成通用回执：前者有变更前、变更后、影响说明三段，后者有可撤销
  列表、勾选交互与通用操作分组。

## 四 · 必需块落点（机审可读 ＋ 人可读对照）

每族的必需块原文（契约附录逐字）落在隐藏追溯位的 `data-need` 属性里，
四组 `data-block` 齐全：`test/scaffold.test.mjs` 的逐族对账与
`audit-page-blocks.mjs` 都只认原文在位，直接读属性即可命中。
可见正文是打磨后的中文小节（标题如变更结果、当前状态、标签变更），
与原文一一对应，不另起一套说法（对应关系见 §三）。

这样做的原因：原文里带英文与斜杠并列写法（`before→after`、
`名称/ID/分类/位置×数量/状态/标签/备注`），逐字上屏会被文案机审
记为英文裸词；藏进属性、屏上用中文，是追溯惯例不是藏拙，
本节即对照表。
