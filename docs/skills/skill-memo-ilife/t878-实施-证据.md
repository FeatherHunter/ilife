## 三、形状决定的对抗式审查（为什么是键值行、为什么居中）

**对手盘一：换标点更省事（`·` 换 `｜` 或换成别的点）。**
裁决：**否**。判据原文（`separator-probe.mjs` 件头引的用户裁定）是「当一个内容需要通过 `；` 和 `·` 分割时，代表需要进行 UI 上的设计」—— 符号要换成**版式**，换标点是把同一件事再做一遍。#880 票面也逐字写着同一条。

**对手盘二：用公共层的口径行（`renderCaliberLine`，12px 灰字旁注、槽间一条细线）比事实条更贴原来的 12px 灰字观感。**
裁决：**否**。口径行分槽靠**版式**，但每槽不是**具名字段**；本内容是「时刻」「场景」两个字段，`t849-视觉基准.md` §3 表里「`·` 串**单实体的多字段**」一行明写出口＝**键值行**，举的实例正是「心愿快照行」（本票两页就是心愿页）。键值行在本仓的既有件就是事实条（`renderFactStrip`／`.ilife-block-fact-strip`；卡路里域 #523／#544／#452 都走它）。

**对手盘三：往公共层加一个浏览器侧产出者（`buildSharedHelpersJs()` 出一份），比在备忘录包里再写一份类名干净。**
裁决：**否（本票不做）**。代价是**公共层串行窗口** ＋ 五家技能全部产物的运行时体积一起变，收益只是省掉一处类名引用；而「公共层给出类名与样式、域侧拼标记」正是本件里空态卡与错误回执卡既有的口径。真要做，属于公共层的独立票，不夹在本票。

**对手盘四：状态卡是居中版式，键值行左对齐会不会跟卡片的版式语法打架。**
裁决（**实测后定**）：**会**，故**居中**。改前那句 `22:35 · 同步飞书` 是**居中**的（由 `.status-card{text-align:center}` 继承）；本票只该换**形状**，不该顺手改这条带的版式语法。做法是在页面自己的 `.status-meta` 规则上加 `display:flex;justify-content:center`（**页面自己的容器规则；不新增样式块、不新增字面色值**，六列机审 ③ 仍 0）。两版都铺过墙、都看过屏：左对齐那版短行贴在卡片左沿、右侧空一片；居中版与卡片上半（图标／标题／说明）同一条中轴。**向导两页不动**：那两页的页头本来就是左对齐，键值行左对齐与它同语法。

**对手盘五：`fmtTime` 把同步页的 `generated_at` 截成 `10:04`，而向导页给的是完整时刻 —— 同一个标签两种粒度，要不要顺手统一。**
裁决：**否**。那是**值的内容**、不是形状，属本票之外；且截短是改前就有的取舍（状态卡是紧凑结论卡）。本票的边界是「形状换掉、事实一条不减」。
