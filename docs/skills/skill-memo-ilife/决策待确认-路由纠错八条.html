已在票里坐实 · 危险缺陷

「删心愿」「删打卡」「删情绪日记」三条路由行都指向 memo.update，而 update 只做字段改写、不删除。注入进技能说明的那一行逐字就是 memo.update --params '{"category":"心愿","id":…}'。

⇒ AI 照表执行会把这条笔记的顶层分类改成「心愿」，而不是删除它。真正的删除只有 memo.remove（须二次确认）。这条不在原票面上，是调查席翻出来的。修法已定（改指 memo.remove），不用你裁 —— 只是底下第 7 条要你把「确认从哪来」定死。

八条待裁

1
「飞书授权」这条唤醒词留不留

你定的规则是「HELP 里没有的我们不开发，除非老技能也有」。卡就卡在「也有」这两个字。

按词和场景读：老技能 21 个子命令里没有 auth，HELP 里也没有「飞书授权」这个场景 ⇒ 该移除。
按能力读：老技能确有 scripts/feishu_auth_helper.py（init_app／poll_auth），技能说明还自述「本 SKILL 自带」⇒ 该保留。

两种读法下，路由表计数从「保留 10 ／ 移除 1」变成「保留 11 ／ 移除 0」。

A按「词／场景」读 → 移除推荐
你的原话整句是「HELP HTML 中有的场景……HELP HTML 中都没有的 我们不开发」，主语是场景
与另一条已坐实的结论同向：老技能里「授权」只是「首次使用」流程里的一步，不是独立入口
授权这件事本身仍要做 —— 它归「首次使用」场景，不是丢掉功能
B按「能力」读 → 保留

但它没有对应的 HELP 场景卡，只能挂在别处，入口会变得没有来历

新仓的 memo.auth 这条命令保留（首次使用流程要用），只是不作为独立唤醒词出现在总表上。

2
「废弃提醒」这条词保留后挂在哪

按规则该留（老技能有对应的子命令）。但 HELP 里没有「废弃提醒」这个场景卡，所以它没有别名位可挂。

A并进「看提醒」场景的「已废弃」状态说明，行撤掉推荐
词还在（用户说得出、AI 认得），只是不当独立入口
要在「看提醒」场景里补一句状态说明
B留在链路总表当次级词
不用改场景
与「别名不出现在链路总表」的定义互相别扭，两个口径打架
推荐 A

并入「看提醒」的状态说明后撤行。

3
别名到底上不上总表（现仓说明与本次口径冲突）

本次对账按「别名不出现在链路总表」做。但现仓技能说明里写的是「其余唤醒词是场景别名，住上一节索引块」—— 也就是说现仓把别名放进了总表。两个口径只能留一个。

A照本次口径：别名不上总表，说明那句一起改掉推荐
链路总表是给人看的导航，一行一个场景最干净；别名多了会稀释重点
别名不会丢 —— 它们仍住在 HELP 资产的 aliases 里，AI 照样认得
要顺手动技能说明里那句话
B照现仓：别名上总表
不用改说明
总表行数从 29 涨到 40 上下，且同一场景出现多次
推荐 A

总表按场景一行，别名回 HELP 资产里待着。

4
「首次使用」落到哪条命令上

这是唯一必须新开一条命令的场景：新仓 12 个命令键里没有初始化类，初始化报告页 init_report.html 也零接线。

A新开一条渲染型命令推荐

照老技能 init-report --data <JSON> 的形状。

与老技能一一对应，行为有对照基准
初始化报告是一份独立产物，职责单一
多一个命令键要登记
B复用「看 HELP」那条开库前出页的口子
不加新键
两件事挤一条命令，参数面会互相污染；且 HELP 入口你已裁定「只认一条」
推荐 A

新开一条渲染型命令，照老技能的 init-report 形状。

5
「按时间搜备忘」的时间参数是什么形状

现表的示例值给的是月份形（2026-09），而 HELP 的场景字段是 start ＋ end 两个日期。更麻烦的是：场景原文写的是「按创建时间倒序」，而现实现能过滤的只有排期日期。

A照 HELP 的 start ＋ end，按创建时间过滤推荐
HELP 是官方源，字段以它为准
场景原文写的就是「按创建时间」，按这个做才对得上用户预期
要新增一条按创建时间过滤的通道（今天只有排期日期的）
B照现表的月份形 2026-09
示例值已经是这个形状，改动最小
与 HELP 的字段名对不上；月份形表达不了「某个区间」
推荐 A

认 HELP 的 start ＋ end，语义按创建时间过滤。

6

这个场景今天根本走不通：记录命令只走「先建新笔记、再给这条新笔记挂提醒」，全包没有任何「给某条既有笔记挂提醒」的入参通道。老技能是有的 —— remind [note_id] 一个可选位置参数。

职责最干净

C补到「看提醒」那条命令上
复用已有键

7
用户说「删备忘」，算不算已经确认了

新仓口径是「交互动作换成显式参数」—— 真删必须带确认标记。那么用户自己开口说「删」，AI 是该照做，还是该先反问一次？

不定死，实施的人会在「报错要确认」与「AI 自己补确认」之间摇摆。

A用户原话说了「删」＝已确认，AI 直接带上确认标记推荐
与老技能体验一致（老侧就是一句话删掉）
删是用户的明确意图，再问一次是多余交互
误删风险靠「一次只删指定的那些 ID」兜住，不靠反复确认
BAI 必须先反问一次
最保险
与老技能体验不符；用户已明确表达删除意图时再问一遍会显得迟钝
推荐 A

用户按唤醒词说要「删」即视作确认；批量删仍旧先出清单页再执行。
