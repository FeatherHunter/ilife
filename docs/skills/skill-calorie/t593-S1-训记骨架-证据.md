### 第二步 · 结构设计

```
src/xunji/
  index.ts        能力门（对外恰五件：声明表／库路径／读库／动作名校验／分派）
  subcommands.ts  8 条子命令的声明（名字／职责／用法／参数／退出码／示例／状态／归属票）＋ 按声明解析
  catalog.ts      库读取（读到什么／为什么读不到）＋ 动作名校验（老三态 ＋ 候选一族）
  run.ts          分派：verify 真跑；其余七条明确拒绝（非 0 ＋ 点名归属票）
  cli.ts          命令行入口（stdout 一行 JSON ＋ 退出码）
  data/训记官方动作.json   预置快照（事实源）
```

能力门对外五件，各一句：

- `XUNJI_SUBCOMMANDS`：8 条子命令的对外面（名字／用法／参数／退出码／实现状态／归属票）；
- `XUNJI_CATALOG`：库路径两档（`preset`＝包内预置快照，`machine`＝老的机器路径，只作显式覆盖）；
- `readMovementCatalog(path?)`：读库，返回「读到／读不到 ＋ 人话原因 ＋ 名表」，缺文件不抛错；
- `verifyMovements(names, opts?)`：批量校验（`valid: true／false／null` ＋ `catalog_loaded` ＋ 候选）；
- `runXunjiCommand(argv)`：按声明分派一条子命令，返回 `{ code, message, data, stderr }`。

**共用件**：本票没有新建共用件（`XUNJI_CATALOG`／`verifyMovements` 只被本模块与 `fetch`／`render` 那两个既有消费者用，且都走能力门）。

## 三 · 票内定的三条口径

### 1. 动作库路径（票面「要不要，票内定并写口径」）

- **默认（唯一口径）**＝包内预置快照 `src/xunji/data/训记官方动作.json`。`verify` 子命令、编辑器库面、计划级审计（`audit`）**都走这一份**——同一句动作名在任何一台机器上算出同一个结果。
- **显式覆盖**＝调用方把路径传进来（子命令读法 `verify --catalog <路径>`；函数层 `{ catalogPath }`／`{ catalog }`）。老的机器路径 `%USERPROFILE%\.minimax\训记官方动作.json`（`XUNJI_CATALOG.machine`）**只是可传的一个值**：模块**不隐式读它**——隐式读会让「这台机器放没放库」变成第二套口径，与编辑器库面分叉（#593 R3 记的正是这条分叉）。
- 该文件在盘上**不复制**（`tsc` 不复制资源，见 `tooling/check-publish.mjs:10`），故按**源布局**定位；安装态随包发属 [#601](https://github.com/FeatherHunter/ilife/issues/601)，不在本票写集（见 §八·2）。

### 2. `verify` 的退出码

| 码 | 什么读数 | 与老实现的关系 |
|---|---|---|
| 0 | 全部动作名都在库 | 同 |
| 1 | 用法错（缺动作名／未知参数／未知子命令）／**库读不出、无法验证** | 用法错同老（老 argparse 退 2 与鉴权码撞车，**不照抄**）；**库缺失老实现退 0，是缺陷（#595 附带发现），新仓退 1** |
| 4 | 有动作名不在库（`invalid_count > 0`） | 同 |
| 2／3 | 未用到（鉴权／接口错，归 #607／#608／#610） | — |

读数里带 `catalog_path`／`catalog_error`／`unverifiable_count`，让「库缺失」与「动作不合法」分得清；老 `verify_many()` 的五键（`catalog_loaded`／`total`／`valid_count`／`invalid_count`／`results`）原样保留。

## 四 · 有意偏离清单（与设计件／老实现不同，逐条给理由）

1. **声明件叫 `subcommands.ts`，不叫 `commands.ts`**：`scripts/gen-cli.mjs:80-104` 把 `src/<能力>/commands.ts` 当**卡路里命令**的权威声明读（六字段 `kind／key／shape／title／example／run`），且根测试 `test/calorie-routing-81.test.mjs:122-126` 要求每条声明命令都有可执行入口（`covered.size == DECLARED_KEYS.length`）。设计件 §2.1 的树里写的是 `commands.ts`，照搬会逼出「注册一条命令 → 转一条路由」——那是 #614 的写集（票面交付物路径也只给 `src/xunji/**` ＋ `test/**`）。
2. **本票不注册卡路里命令、不动路由**：8 条子命令是**模块自己的对外面**（#597 裁定 ②「对外面与老 `xunji_bridge` 一模一样」），不是卡路里命令面。业务面那两条薄命令（同步到训记／拉训记实绩）＋ 五条路由转 `exec` 归 #614；`pnpm gen:check` 在本票**保持绿**（生成物一字未动，能力 10 个与改动前同）。
3. **老 `loadCatalog()` 的 `String()` 强转去掉**：新读法只收非空字符串。官方库 1092 条全是字符串，故这一档只影响坏输入（老写法会把数字／对象也变成「合法动作名」）。
4. **老 argparse 的「用法错退 2」不照抄**：与鉴权码 2 撞车，本仓用法错一律退 1（退出码含义表见 §三·2）。
5. **`fetch/cli.ts` 的 `catalog-verify` 退出码从恒 0 改成按读数 0／1／4**：老实现这一格既不报「库缺失」也不报「不在库」（#595 §六记的缺陷位），本票按模块读数给。
6. **计划级审计（`audit`）与运维 `catalog-verify` 的默认库从「各机 `~/.minimax` 那份」改成「包内预置」**：与 §三·1 同一口径（#593 R3 记的两处分叉就地摆正）；`--catalog <路径>` 仍可显式指回机器上那份。
7. **库文件按源布局定位**（不读 `dist/` 下的拷贝）：`tsc` 不复制资源是本仓既定形状（`tooling/check-publish.mjs:10`「只靠 files 随包发」）；安装态能否读到由发件清单决定，归 #601。
