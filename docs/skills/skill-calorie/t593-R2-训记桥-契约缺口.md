## 二、推送链（一次推送的完整请求形状）

### 2.1 请求体（一个 session＝`res[]` 的一项）

```

Content-Type: application/json
Authorization: Bearer <REDACTED>                                      # upsert.py:101-104
{
  "schema_version": "train_open_api_v2",                              # upsert.py:91
  "client_request_id": "2026-07-13_上肢_1a2b3c4d",                    # push.py:153
  "dry_run": false,                                                   # upsert.py:93
  "include_full_data": false,                                         # upsert.py:94（push 不传 ⇒ false，push.py:162-166）
  "res": [{
    "datestr": "2026-07-13",                                          # push.py:104
    "localid": 0,                                                     # push.py:105（新建）
    "title": "<session_label 原样>",                                   # push.py:106
    "start": 0, "end": 0,                                             # push.py:107-108（恒 0，避训记 BUG，见 :84-89 注释）
    "movements": [{ "name": "<动作名原样>",
```

### 2.2 动作名怎么报

- 【事实】动作名原样放 `movements[].name`，取自计划里的 `movements[].name`，只过一层 `_safe_str` 标量化：非标量（list／dict／其他）退成 `""`（`push.py:91-101`、`:32-43`）。
- 【事实】`push.py` **不做动作库校验**（该文件不 import `catalog`；`catalog.verify_*` 只被 `__main__.py:63` 的 `verify` 调用）。"推送前先审计动作名"是调用链的第一步，不是推送本身的能力（老链自述见 `__main__.py:8`、`t350-external-five-verdict.md:14`）。
- 【事实】`sets[]` 每条**写死** `done:false`（`push.py:96`），重量/次数/单位各自标量化（缺省 `"0"`／`"0"`／`"kg"`，`push.py:97-99`）。

### 2.3 日期怎么报

- 【事实】日期只走 `res[].datestr`，格式 `YYYY-MM-DD`，与 CLI `--date` 同串（`push.py:104`、`__main__.py:270`）；**不转时间戳**，`start`／`end` 恒 `0`（`push.py:107-108`）。
- 【事实】同一串还进 `client_request_id` 前缀（`push.py:153`）。日期本身不做时区/今日推算：`push-plan` 只认传入的 `--date`（`:270`）；`backfill` 才在缺省时取本机今天（`backfill.py:92-93`、`:182-185`）。

### 2.4 45 秒限频守在哪一行

- 【事实】常量：`RATE_LIMIT_SECONDS = 45`，注释写"训记写 API 限频要求（应用层策略）"（`push.py:29`）；函数入参缺省取它（`push.py:113`，"守"的那一行是 `push.py:156-158`）：

  ```python
  if i > 0 and not dry_run:              # push.py:156
      print(f"  ⏳ 等待 {sleep_seconds}s 限频...")   # push.py:157
      time.sleep(sleep_seconds)          # push.py:158
  ```

- 【事实】**不守的位置**（逐处点名）：
  1. 当天**第一个** session 前不睡（循环 `i=0` 不进分支，`push.py:149-158`）；
  2. **跨天不睡**：`run-sync` 逐天起子进程，两天的 push-plan 之间没有任何 `sleep`（`run_sync.py:178-190`）；
  3. `--dry-run` 不睡（`push.py:156` 的 `not dry_run`）；
  4. `overlay-plan` 完全不守：多 session 合成**一次**调用、无 sleep（`overlay.py:161-174`，注释按"训记 API 单次最多 4 条"，`overlay.py:10`）；
  5. 读侧另有 15s/30s 一套（`auth.py:43-44` 的 `RATE_LIMIT_LIGHT_SECONDS=15`／`RATE_LIMIT_FULL_SECONDS=30`、跨进程状态文件 `~/.mavis/xunji_bridge_rate.json`，`auth.py:40`），但**缺省不守**：`fetch_trains(..., respect_rate_limit=False)`（`fetch.py:47`），`backfill` 不传该参（`backfill.py:94`）。
- 【推断】跨天/多次调用是否真被训记拒，本票不调接口、无法证实；老仓自己把 45s 标成"应用层策略，不是单次 API 约束"（`push.py:8`、`:29`）。

### 2.5 失败重试怎么定

- 【事实】`retry_with_backoff(_do_call, max_retries=2, sleep_base=5)`，`fetch`／`upsert` 两处同参（`fetch.py:112-113`、`upsert.py:134-135`）⇒ **最多 3 次调用**；退避 5s、10s；限频优先用服务端 `retry_after`（`errors.py:276-282`）。
- 【事实】不重试的类：`auth`、`vip_required`（`errors.py:270-271`）、`validation`（`errors.py:273-274`）；其余（`rate_limit`／`server`／`network`／`unknown`）重试。
- 【事实】错误分类是集中件：7 类 `ErrorType`＋软错误（HTTP 200 但 `success:false`／含 `error` 字段／`res` 是 "too frequent" 字符串）统一走一套分类（`errors.py:39-46`、`:79-103`、`:128-180`）；限频缺省值也是 45s（`errors.py:50`）。成功响应返回前会 `gzip` 解压（`upsert.py:112-114`、`fetch.py:89-91`）。
- 【事实】只有 `attempts > 1` 时才把 `attempts` 写回响应（`upsert.py:136-137`、`fetch.py:114-115`）。

### 2.6 幂等怎么定

- 【事实】幂等键＝`client_request_id`（训记要求 "unique-id-from-agent"，`upsert.py:27`、`push.py:151-153`）；缺省自动 `uuid4().hex`（`upsert.py:77-79`）。
- 【事实】`push-plan` 每个 session **现生成一个新键**：`f"{date}_{session_label}_{uuid4().hex[:8]}"`（`push.py:153`）；`overlay-plan` 每次调用一个新键：`f"overlay_{date}_{uuid4().hex[:8]}"`（`overlay.py:164`）。
- 【事实】`localid=0` ＝ 新建；有值＝更新（`upsert.py:16`、`push.py:105`）。`overlay-plan` 是唯一走"更新"语义的子命令：`res_item["localid"] = localid`（`overlay.py:118`）。
- 【推断】新键＋`localid=0` 的组合下，**同一天重复 `push-plan` 很可能在训记侧再建一遍**（键每次都新，老仓没有任何"今天已推过就跳过"的判据）。这条要实测才能定，本票不调接口。
- 【事实】推送回执不可全信：响应 `res.trains` 常为空数组而 `truncated` 仍为 `false`（`upsert.py:30-35` 自述实测；`push.py:173-175` 同述），因此 `push` 只给一个 `verified` 布尔（响应里真看得到 train 才 true），真值以 `fetch --full` 为准（`push.py:176-184`、`fetch.py:19-22`）。

## 三、回写链

### 3.1 拉取范围怎么给

- 【事实】CLI 只有"结束日＋天数"两参：`--date`（缺省今天）与 `--days`（默认 0）；`days = max(args.days, 1)`（`__main__.py:101`、`:263-266`）。
- 【事实】区间＝`[end-(days-1), end]`，逐日**倒序**循环（`backfill.py:190-193`）；单日与范围共用一个 `backfill_range`（`backfill.py:13-16`、`:165-203`；`__main__.py:99-102` 注释同述）。**只能向后回溯，给不出起止两端**。
- 【事实】每天固定 `full_data=True`（回写要拿 `done` 标记，`backfill.py:76`、`:94`）。
- 【事实】写库前取 `weight_log` 最新一条体重供热量推算，取不到为 `None` 且不阻塞（`backfill.py:50-68`、`:111`）。

### 3.2 幂等键怎么算（本票的复核重点）

- 【事实】文档口径写两列：模块头 "幂等键:xunji_localid + set_index"（`backfill.py:7`）；旧裁定件照抄了这一句（`t350-external-five-verdict.md:15`）。
- 【事实】**代码实际是三列**（`xunji_adapter.py:98-101`）：

  ```sql
  SELECT id FROM exercise_log
  WHERE xunji_localid = ? AND exercise_type = ? AND set_index = ?
  ```

  即 `xunji_localid + exercise_type + set_index`。命中→`UPDATE`（`xunji_adapter.py:104-115`），未命中→`INSERT`（`:116-127`）。
- 【事实】键的三段来源：`xunji_localid = str(train['localid'])`（`xunji_adapter.py:29`、`:65`）；`exercise_type = movements[].name`（`:33-34`、`:58`）；`set_index = sets[].index`（`:60`，训记若不给就是 `None`）。
- 【推断】`set_index` 为 `None` 时三列键会把该动作所有缺 index 的组收敛成一行（`NULL` 在 SQLite 比较里不相等，逐行是否命中要看实测）——本票不跑老脚本，不下定论。

### 3.3 冲突怎么处理

- 【事实】只同步 `done` 为真的组，未完成组直接跳过（`xunji_adapter.py:37-39`）。
- 【事实】命中行的 `UPDATE` 覆盖 7 列＋时间戳：`exercise_type, reps, load_kg, calories_burned, category, difficulty, xunji_title, updated_at`（`xunji_adapter.py:105-114`）；**`date` 与 `note` 不在 SET 列里** ⇒ 训记侧改了日期不会回写、手写备注被保留（与 `xunji_adapter.py:77-79` 自述一致）。
- 【事实】单行 SQL 失败只记 `errors` 并继续下一行、不抛（`xunji_adapter.py:128-134`）；`_backfill_one` 只要没抛异常就 `commit()`（`backfill.py:130-137`）⇒ **部分行失败照样落盘**，失败明细只在返回体的 `errors` 里。
- 【事实】单位/热量口径：`convert_load_kg(weight, unit)`（lbs→kg）、`estimate_calories_from_training(volume, body_weight_kg)`、`_infer_category(name)`（`xunji_adapter.py:41`、`:62-63`、`backfill.py:8-10`）；`reps` 允许 `"12-16"` 这类范围值，取最大值（`xunji_adapter.py:42-53`）。
- 【事实】**写库失败退 0**：DB 失败那一支返回 `fetch_ok: True` ＋ `err: "DB 写入失败(已回滚):…"`（`backfill.py:138-148`），而 CLI 只按 `r.get("fetch_ok") is False` 判非零（`__main__.py:108-111`）⇒ 该错误进不了退出码。
- 【事实】每天一次 `fetch`，任一天拉取失败 → 整体退 **3**（`__main__.py:107-111`）。

## 四、密钥

> 纪律：本件**只写位置与形状，一个密钥值都不抄**。以下不出现任何真值；`key status` 本票也未运行（属"跑老脚本"）。

### 4.1 `key` 子命令怎么拿 KEY

- 【事实】`key status` **不读也不打印完整 KEY**：只回报两个名字各自"设没设"、当前生效的是哪个、以及一个预览（`auth.py:166-184`）。
- 【事实】`key set <值> [--legacy]` 把 KEY 写进**用户级环境变量**；`key clear [--legacy]` 删掉它（`__main__.py:131-145`）。
- 【事实】程序内部统一走 `auth.get_key()`（优先权威名、空则回退旧名）／`auth.require_key()`（没有就抛）（`auth.py:47-55`、`:187-197`）。

### 4.2 存哪（位置与形状）

| 项 | 值 | 出处 |
|---|---|---|
| 存放形态 | **用户级环境变量**（不是文件） | `auth.py:5-14`、`:110-134` |
| 权威名 | `XUNJI_TRAINS_KEY` | `auth.py:35` |
| 兼容旧名 | `XUNJI_API_KEY`（无权威名时才回退读；`key set` 不给 `--legacy` 不写它） | `auth.py:36-37`、`:47-55`、`:125` |
| Windows 落点 | 注册表 `HKEY_CURRENT_USER\Environment`，`REG_SZ`；写完广播 `WM_SETTINGCHANGE` | `auth.py:71-90`（`SetValueEx` 在 `:81`） |
| 非 Windows 落点 | 子进程跑 `[Environment]::SetEnvironmentVariable('<名>', <值>, 'User')`，值走 base64 传参防注入 | `auth.py:93-107` |
| 当前进程 | 写完同步进 `os.environ`（"新开终端生效"的提示与这件自洽） | `auth.py:132-134`、`__main__.py:137` |

### 4.4 失效怎么表现（三态，逐处点名）
