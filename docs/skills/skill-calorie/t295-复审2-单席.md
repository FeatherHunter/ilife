## 五、N1 的诚实边界（我给编排者的判断）

**印记缺失时打 `GEN-STAMP WARN` 且判 0** —— 我的实测：删掉 `dist/.gen-inputs.json` ＋ 内容真变 → `gen:check` **exit 0 ＋ `GEN-CHECK PASS` ＋ `GEN-STAMP WARN` 在场**（与返修席读数一致）。

- **谁会踩**：① `pnpm build` 跑挂（`tsc` 红，`&&` 使 `--stamp` 不执行）后直接跑 `gen:check` → 这一格与守卫无关，`gen:check` 本来也因 `dist/` 缺失报红；② 「先单独 `tsc -b`／拷 `dist/` 进树」再跑 `gen:check`；③ **最现实的一条**：老旧树上加了新能力目录、只单独编译它、没再跑全量 `pnpm build`。
- **踩了会怎样**：③ 我实测（仓外克隆 `D:\_t295r2\repo`，用后即清）——新能力源改了而 `dist` 未跟上时，守卫**不报 `GEN-STALE`**（印记里没这条 ⇒ 放行），改由下一步的 `GEN-CHECK FAIL` 兜住（`键 102（写 35 ＋ 读 67）；能力 2 个…`）。即**假绿方向没开**，但守卫对这一格不设防、红是靠下游门出现的。
- **CI 上会不会踩**：**不会**。`build-test` 里 `pnpm build` 在 `gen:check` 之前，且 `"build": "tsc -b && node … --stamp"` **无条件重打印记**（真 CI 实测 `gen:check success`）。

**结论：这条取向可以接受**（「不假红优先」换掉的是第一轮的恒红＋自锁，代价值得，且 CI 面被次序钉死）。但请把它记成**已知的判据覆盖面**而非「守卫完备」：无印记时判 0 与「印记里没有这条就放行」是两处**放行面**，后者的可达性我实测到了（见 六·新缺陷）。
