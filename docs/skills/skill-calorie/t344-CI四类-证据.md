## 4 · ④ macOS `/private` 软链（#83 ⑥／#133 ⑭）

CI 原文（run `35090373195`，`build-test (macos-latest, 24.x)`）：

```
✖ #83 ⑥ 相对 --html：exit 0 ＋ 绝对 delivery.path（写的就是回传的那个路径）
  AssertionError: 回传路径＝实际写入路径（resolve 归一）
  + actual   '/private/var/folders/36/…/T/t83-relout-8ICjut/nested/rel.html'
  - expected '/var/folders/36/…/T/t83-relout-8ICjut/nested/rel.html'
```
`#133 ⑭` 是同一条机理（期望值 `join(resolve(root), relDb, …)` vs 回执里的真实路径）。

机理：`os.tmpdir()` 在 macOS 返回 `/var/folders/…`，而 `/var` 是指向 `/private/var` 的软链；子进程的
`process.cwd()` 拿到的是**真实路径**，它 `resolve('nested/rel.html')` 得到 `/private/var/…`——同一份文件
两个名字，字符串比对必不等。

修：期望值改用 `realpathSync` 归一（`delivery-83.test.mjs` 的 `#83 ⑥`、`help-paths-133.test.mjs` 的
`#133 ⑭`）。Linux／Windows 上 `realpathSync` 是恒等变换，断言强度不变（比的是「回执 ＝ 产物真实所在」）。

**本机（Windows）不可复现**，实测给出「为什么」：`:344` 探针（`.scratch/t344/cwdprobe.mjs`）用 junction
造一个软链根，`spawnSync({cwd: link})` 的子进程 `process.cwd()` **不解析**（仍是 link 串），而 macOS 的
`getcwd()` 会解析 ⇒ Windows 造不出「父进程 link 串 vs 子进程真实路径」的分歧。本地能给的只有：
改后这两个用例在 LF 树仍绿（`A1-A4-repo-targeted.txt`：三个件 25 条里 3 条红全是 `#91` 的 437）。
