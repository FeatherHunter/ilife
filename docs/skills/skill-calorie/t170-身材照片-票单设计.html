Q1

照片要不要真的出现在页面里？

最重

为什么问

这不只是好看不好看：老技能写死「HTML 默认 base64 嵌图，飞书／IM／任意环境打开都能看照片」，而你验收的方式是把 HTML 拷到交付目录双击打开——引用文件路径的做法一拷就瞎。删身材照的「快照确认」也必须有照片才成立。反过来，本包现在没有任何图像依赖，内嵌是一条新能力。

判断依据

  • 老实物是内嵌的（photo_data_base64／gif_data_base64，PIL 800×1200 q85）。
  • 「不读照片字节」是新仓有意写下的决定（render/photo.ts、render/wizardPort.ts 顶注）——要改就是推翻它，按惯例由你裁定。
  • 真库有货：22 行身材照、65 张图 ⇒ 验收有真材料。
A 内嵌缩略图（照老技能）B 引用照片文件C 维持现状
页面里看得见看得见看得见看不见
拷走／发飞书照样看得见图会丢—
快照要求交得出同机交得出交不出
代价新增一件图像能力＋体积上限很小零

推荐

A 内嵌缩略图，单列成票 2（定体积上限：每张 ≤120KB、画廊页总量设上限），B 留作退路。

理由：老技能的理由（换环境也能看）正好命中你的验收方式；且不内嵌，删身材照的快照这一条永远交不出。

Q2

「生成身材照GIF」算跑到哪一步？

为什么问

这条词的命令现在只出一段任务描述，页面里没有 GIF；老技能是真出 GIF 的。图的 Destination 只要求「拿到结果型 HTML 落盘」，按这个口径它已经算跑得通——但你心里要的多半是「真的拿到一个动图」。

推荐

本图按「任务描述页」判它跑得通，同时把真出 GIF 单列成票 5（规划页与坐标 schema 都现成，差的只是合成这一步）。

理由：合成要引入图像依赖，属命令补齐性质的新风险；与页面改版分开，红了知道是谁。

Q3

10 个场景的工作流写在哪？（你的核心思想 1）

关键信息

  • SKILL.md 是每轮都在上下文里的常驻材料：新仓现在 211 行；老技能那份长到 158 KB（把所有场景工作流都塞进正文的结果）。
  • writing-for-agents 的做法：常驻只放常驻规则 ＋ 一条指针，逐场景细节下放成披露文件，命中指针才读。
  • 披露文件必须随技能包安装（安装器只装 packages/skill-calorie/ 这一层，docs/ 进不了 agent 读得到的范围）。

推荐

SKILL.md 只留常驻规则（标签必填逐张追问／改加删语义／保留 1 个／发图双模式与分离到达／删的候选与快照）＋ 一行指针；10 个场景的逐词工作流放 packages/skill-calorie/workflows/09-身材照片.md。

理由：常驻材料每轮都花代价；分开放同时解决「SKILL.md 越来越长」与「AI 不知道从哪一步走」。老技能的 HTML 交付协议（必须主动 send 到飞书）不继承——新仓口径是落盘 ＋ 回执绝对路径（场景 07 就是这么验收的），send 归桥／面板那条线。
