### 1.1 一条具名事故（据实记账）：第一版重出器落到了真实家目录

第一版只传了 `SKILLS_DB_PATH`——**#676 起库落点已改成配置文件**（`~/.ilife/calorie.yaml` 的 `db.dir`，
`ILIFE_CONFIG_DIR` 才能整体改基座），于是 CLI 按默认落点去开 `C:\Users\<用户>\.ilife\data\calorie_data.db`，
并在 `~/.ilife/data/calorie_html/` 落下两页「操作失败」单据。**处置与核实**：

- 两页 `操作失败_20260918_120000[_2].html` 已删（mtime 即本次运行，名字带冻结时刻）；
- 那份库经只读探头核查：**11 张表全 0 行**（本次运行建的空 schema 库，无任何真实数据），**未删、未改**；
- 重出器随后加了硬闸门（配置目录必须在 `.scratch/` 下）＋ 写死 `calorie.yaml`（`db.dir`／`html.dir`／`photos.dir`／
  `xunji.stateDir` 全部指到 `.scratch/t708/`）。

### 1.2 另一条具名限制：种子库的时间列曾让判据出假红

`user_profile.created_at`／`daily_goal.created_at` 会直接上屏（看档案页的「档案创建」、看目标状态页的「创建时间」），
而 SQLite 的 `CURRENT_TIMESTAMP` 让同一份种子库在两次运行里差出分钟数（实测 `16:14:59` vs `16:30:07`，**字节数不变**）。
**处置**：判据工具里把播种时间列写死（`2026-09-01 08:00:00`），并重跑 A/B 自证。
开窗那一份基线铸在修工具**之前**，故它那两页按「时间戳规整后比」——**规整后 71/71 逐字节相同**（读数见 §三）。
