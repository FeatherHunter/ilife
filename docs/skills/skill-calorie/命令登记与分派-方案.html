命令登记与分派：并发冲突的最佳解法

对象：packages/skill-calorie/src/cli/keys.ts · cli/cmd_read.ts · cli/write.ts　｜　方法：第一性原理推导 ＋ 与成熟 TS 项目横向对照　｜　2026-09-13

结论（一句话）：在这套仓库的既定约束下——单一工作树、单一 master、多张地图的 session 同时开工——唯一能把冲突降到零的做法是「命令的声明与实现搬回各自能力的目录（第一级）＋ 把所有汇总改成由声明确定性生成（第二级）」。第一级是行业标准形状（VS Code 同形）；第二级在常规仓库里可选，在这里是必需，因为常规仓库靠的「分支 ＋ 合并队列」在本仓不存在。

一、问题：这三个文件为什么必然冲突

它们今天都是手工维护的巨型枚举，而且同一件事实在太多地方各写一遍：

文件今天的形状谁要改它
cli/keys.ts101 条命令登记（key／形状／标题），手写每加一条命令的每一张图
cli/cmd_read.ts66 个 case 的巨型 switch，1140 行同上
cli/write.ts38 个 case，879 行同上

再加两处同一事实的副本：packages/base-combos/combos.yaml（手写的键镜像）与 scripts/build-help.mjs 的 REPR 表（key → 代表唤醒词）。也就是说「一条命令叫什么、长什么形状、谁处理它、代表哪条唤醒词」这一组事实，今天有三到四份手写副本。

判据只有两个量：① 一次改动要写几个文件；② 这条事实归谁。写的人越多、文件越共用，冲突面越大；归属错了，就是多个人抢同一支笔。在单一工作树里，两个 session 同时写一个文件不是「git 合并冲突」（那还能解），而是后写覆盖、编辑交错。

二、方案：两级阶梯

第一级 · 能力自治（命令的声明与实现搬回能力目录）

packages/skill-calorie/src/
├── weight/
│   ├── commands.ts   ← 权威源：体重全部命令的声明（只有体重这张图改它）
│   ├── index.ts      ← 对外那道门
│   └── log.ts / edit.ts / history.ts / curve.ts / volatility.ts / notes.ts / compare.ts / review.ts
├── goal/commands.ts  ← 目标线的权威源（只有目标线改）
└── …
├── cli/
│   ├── registry.ts   ← 索引：一能力一行（只在“新增能力”时改一行）
│   ├── cmd_read.ts   ← 薄分派：查表 → 校验 → 调 handler（1140 → 几十行）
│   ├── write.ts      ← 薄分派：同上（879 → 几十行）
│   └── keys.ts       ← 第二步后改为生成物

// src/weight/commands.ts —— “加一条命令”要写的全部就是这一行
export const COMMANDS = [
  { key: 'calorie.weight.log',          shape: 'receipt', title: '记体重',   run: logReceipt  },
  { key: 'calorie.view.weight-history', shape: 'stat',    title: '体重历史', run: historyDoc },
] satisfies readonly CommandSpec[];

第二级 · 汇总改为生成（消灭最后的手工面与所有副本）

scripts/gen-cli.mjs 扫各能力 commands.ts → 确定性排序生成 keys.ts（导出名不变）、registry.ts、combos.yaml 镜像、SKILL.md 的速查表（REPR 手写表退役）。生成属于构建动作，本来就在 gate 锁里；配 pnpm gen:check（生成物 ≠ 生成器输出即红），手改生成物会被机器抓住。

三、第一性原理：为什么只能是这个方向

把「避免冲突」这件事推到不能再推，只剩四条定律。

定律一 · 归属：一个事实只能有一个主人，别人只能读。
命令的 key／形状／标题／处理函数，是某个能力的事实（体重的事实在体重那儿）。它今天住在通用分派文件里，就是归属错位——五个图的 session 抢同一支笔是这条的直接后果。
定律二 · 汇总：若一个文件的内容是若干各自独立拥有的事实的汇总，那它必须是派生的，不能手工维护。
这一点是纯逻辑：独立拥有意味着这些事实之间没有需要人协商的关系，那么把它们写下来的动作就是机械的；机械的动作交给脚本，写的人就不必是唯一的那个人。
定律三 · 少写者：一次改动要写的文件数，就是它的冲突面。
把「加一条命令」从「写 3 个共用文件」压到「写 1 个私有文件」，冲突概率不是变小，而是结构性归零——因为两个人不可能同时改各自的私有文件。
定律四 · 可验证：派生必须能被机器验真，否则它会退化成第二份手抄。
确定性排序（同一份输入必然同一份输出）＋ 哈希锁 ＋ CI 检查（gen:check）三件配套是成立要件，不是装饰：少掉任何一件，「生成的」文件就会重新被人手改，于是又回到定律二被违反的状态。

由四条定律得到的必然结论：① 命令的声明与实现必须搬回能力目录（定律一）；② 共用位必须是派生的（定律二）；③ 这件事的目标是把每次改动的写入集合压到 1 个私有文件（定律三）；④ 派生要配确定性 ＋ 哈希锁 ＋ CI（定律四）。所以本方案不是若干做法的组合里挑一个，而是这四条定律的唯一解。

四、横向对照：成熟 TS 项目怎么做，我们能照搬哪一层

项目做法它凭什么可以这么做我们照搬哪一层
VS Code 一个功能一个 src/vs/workbench/contrib/<feature>/ 目录，功能自己注册命令与动作（registerAction2／CommandsRegistry）；扩展则在新版 package.json 里声明式贡献命令（contributes.commands） 有分支 ＋ PR 合并队列；聚合处的「贡献清单」即便有冲突，也能在合并时解掉 第一级全照搬：一能力一目录、自己拥有命令与实现、分派层变薄。第二级他们没做（也不需要）。
TypeScript 编译器 诊断信息写在 diagnosticMessages.json，脚本生成 diagnosticInformationMap.generated.ts，生成物入库、CI 校验 单一主人（维护者少）、生成器稳定 第二级的模板：权威数据 → 生成物 → 哈希锁 ＋ CI 校验。我们只是把权威数据从 JSON 换成各能力的 TS 声明。
ESLint 一条规则一个文件，外加手写索引 lib/rules/index.js 索引只在「加规则」时动；冲突靠 PR 与评审消化 照搬「一文件一单元」；索引这一层我们用生成替换——因为我们的索引有三份副本、且没有人给它们做评审门禁。
tRPC ／ NestJS 组合根：appRouter 一行挂一个子路由；Nest 用装饰器 ＋ 模块发现 子路由各自独立，组合根只在新增模块时动 我们的 registry.ts 同形；差别是它由生成器写，连「新增模块」那一行也不需要人加。
yargs（commandDir()） 扫目录自动装载命令模块，不写索引 运行时扫描；代价是丢掉静态可枚举 思想照搬（用目录当注册表），但改成构建期扫描生成静态表——因为我们的测试要穷举全部键（99／100 的计数断言）。
行业主流（一般 TS 仓库） 分支 ＋ PR ＋ 合并队列；共用文件冲突在合并时解决 工作树隔离 不可用：本仓是单一工作树、单一 master，没有隔离设施。这正是第二级在这里从「可选」变成「必需」的原因。

五、那么，它是 TS 项目的最佳方案吗？—— 条件化结论

是当「多写入者 ＋ 单一工作树」成立时

此时没有任何机制能在写入时刻隔离两个 session 改同一文件，所以唯一出路是让共用文件退出改动路径。锁只是排队（降低概率、牺牲并行）；分支在这里不存在。派生聚合是唯一解。

部分常规仓库（有分支与 PR）

第一级（能力自治 ＋ 薄分派）仍是行业标准形状（VS Code 同形），值得做；第二级可选——它的价值从「避免冲突」变成「消灭三份手抄副本」（keys.ts／combos.yaml／REPR）。这也是 ESLint 至今保留手写索引而 TS 编译器选择生成的原因：看的是副本数与单一主人，不是并发。

不适合命令面极小的项目

像 tsc 只有一组选项：一张中心数据表 ＋ 通用解析最省。要注意：我们的问题从来不是「表」，而是「表有多个主人」——所以不能照抄「一张中心表」。

反例什么情况下这套会变糟

① 生成器本身被频繁改（不稳定源）；② 生成物没有 CI 校验（于是被手改，退化成第四份手抄）；③ 跨能力共享了本该私有的东西（生成器变成新的争抢点）。三条都要在落地时堵住。

一句话判据：这套方案的成立要件不是「用了生成器」，而是三条同时为真——确定性输出、哈希锁、CI 校验。缺任何一条，它就从「最佳方案」变成「多了一层会骗人的中间产物」。

六、落地顺序与代价

步骤内容代价／风险
