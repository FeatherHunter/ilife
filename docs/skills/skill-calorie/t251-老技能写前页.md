# t251 老技能「营养目标／饮水目标」族的写前页

取证范围（只读这 5 个文件，各读一次）：

- `scripts/render_goal_config.py`（11006 B）
- `scripts/render_goal_recommend.py`（6035 B）
- `templates/goal_config_nutrition.html`（23191 B）
- `templates/goal_config_water.html`（14012 B）
- `templates/goal_recommend.html`（9805 B）

用途：新仓要照这三张页重写一张「预检确认页」。

## 1. 两张配置页（nutrition／water）

### 1.1 版块（有序）

**goal_config_nutrition.html（营养配置页）**

1. 页头（小标签「卡路里 · 目标配置」＋ 标题 ＋ 副标题一行目标概况）
2. 每日营养目标 (5 项)——5 条 slider 行；提示语「拖动 slider 调整 · 实时显示改前 vs 改后」
3. 📊 改前 vs 改后（小条形对比图；首次设定时标题自动变成「📊 昨日 vs 新目标」）
4. ⚠️ BMR 低值提示（热量目标 ≥ BMR 时同一块转成绿色「✅ BMR 安全确认」）
5. 体重目标进度（有 `weight_progress` 才出）
6. 改前 vs 改后（明细行版，有 `diff` 才出；每行后面跟一句「影响: …」）
7. 更改配置（复制区：说明文字 ＋ 一个主按钮）

### 1.2 吃的数据位（真实占位符名或字典键 ＋ 一句含义）

`goal_config_nutrition.html` 全文只有一个占位符 `<!--INJECT-DATA-->`（写在 `<script id="payload" type="application/json">` 里），另有 `<!--SHARED-CSS-->`、`<!--SHARED-HELPERS-->` 两个公共块。所有数据从 `DATA.data.*` 取：

| 键 | 含义 |
| --- | --- |
| `data.meta` | 排障信息，页面上不显示，只由「复制日志」带出 |
| `data.page_title` | 页头标题，由脚本按场景下发（`营养目标` / `营养目标 · 修改`） |
| `data.current_goal.calorie_goal` | 当前热量目标（卡），slider 初值 |
| `data.current_goal.protein_goal` | 当前蛋白目标（g） |
| `data.current_goal.carbs_goal` | 当前碳水目标（g） |
| `data.current_goal.fat_goal` | 当前脂肪目标（g） |
| `data.current_goal.water_goal` | 当前饮水目标（ml） |
| `data.yesterday_actual.calorie / protein / carbs / fat / water` | 昨日实际值，用于「昨日 vs 新目标」和对比图上的灰色小字 |
| `data.weight_progress` | 体重目标进度，含 `target / current / days_left`；页面上算「距离 = 当前 − 目标」 |
| `data.diff.items[]` | 改类专有：每项 `{key, label, unit, old, new, impact}` |
| `data.bmr_warning` | `{bmr, calorie_goal, below, text}`；`text` 直接当整段提示文字用 |
| `data.fields` | 字段声明数组（渲染端下发）；缺省时模板回退成硬编码 5 键 |

模板自己还有一张单点权威表 `FIELD_META`，给每个字段配上 `label / unit / min / max / step / yesterdayKey`：热量 max `4550` step `5`、蛋白 max `300` step `1`、碳水 max `500` step `1`、脂肪 max `150` step `1`、饮水 max `6000` step `100`。

### 1.3 可交互的东西

- **5 条 `input[type=range]`**（热量／蛋白／碳水／脂肪／饮水）。热量与三个宏量双向联动：拖热量按锚定比例分配宏量，拖宏量按 4/4/9 反算热量（step 5 取整）。饮水滑块独立，不参与宏量联动。
- **一个主按钮「✏️ 更改配置」**（`id=btnAdopt`）。它复制的是 `buildConfigPrompt()` 拼出的**一段给 AI 的指令**，不是数据原样：开头「我已调整目标配置，请按「<唤醒词>」流程写入数据库。」，随后列 5 个营养目标值、再列 5 行「目标 X · 昨日 Y · 差 ±Z」，结尾带「数据来源: 目标配置 v2 · render_goal_config.py · <日期>」。复制成功按钮变绿 `✓ 已复制配置指令,粘给 AI 即可`。
- **页面底部 `actionbar-zone`**：由公共 `window.actionBar(window.__P__)` 注入的操作条（大概率是「复制数据／复制日志」两个口，模板里只剩注释）。
- 没有文本输入框；所有输入都是拖动滑块。

### 1.4 饮水配置页 goal_config_water.html

**版块（有序，4 块，比营养页少）**

1. 页头（小标签「卡路里 · 目标配置」＋ 标题「饮水目标」＋ 副标题「目标日 饮水 X ml」）
2. 每日饮水目标——**只有 1 条 slider**；同样的提示语「拖动 slider 调整 · 实时显示改前 vs 改后」
3. 📊 改前 vs 改后（首次设定时标题变成「📊 昨日 vs 新目标」，无记录时显示「昨日无饮水记录,暂无对比数据」）
4. 改前 vs 改后（明细行，有 `diff` 才出）
5. 更改配置（复制区）

**没有** BMR 提示块，**没有**体重进度块。

**吃的数据位**：同样只有 `<!--INJECT-DATA-->`；取 `DATA.data.meta / page_title / current_goal.water_goal / yesterday_actual.water / diff.items`。`FIELD_META` 只声明一个字段 `water_goal`（label 饮水、unit ml、min 0、max 6000、step 100、yesterdayKey water）。`data.fields` 缺省回退成 `['water_goal']`。

**可交互的东西**：1 条饮水 slider（`oninput` 只做同步显示和刷新对比图，**没有宏量联动、没有比例锚定**）＋ 主按钮「✏️ 更改配置」。它复制的是 `buildConfigPrompt()`：开头「我已调整目标配置，请按「<唤醒词>」流程写入数据库。」，中间只有一行「饮水 X ml」，再一行「饮水: 目标 X ml · 昨日 Y · 差 ±Z」，结尾同营养页。复制后按钮变绿 `✓ 已复制配置指令,粘给 AI 即可`。底部同样有 `actionbar-zone`。



## 2. 推荐页（goal_recommend.html）

### 2.1 版块（有序）

1. 页头（小标签「卡路里 · 目标管理」＋ 标题 ＋ 副标题）
2. 推荐方案——标题右侧 `profileHint` 显示「方案: <方向> · 每周 X kg」；上面是 KPI 卡片（TDEE／BMR／每周速率／饮水 旧→新，缺值的不出），下面是 5 行目标值
3. 推荐依据——每行一个蓝点 ＋ 一句理由，没理由就不出
4. 档案缺（橙色小块，`missing` 非空才出）：「⚠️ 档案缺: X / Y — 已用默认值估算,建议先设置档案」
5. 采纳推荐——复制区：说明文字「确认无误后,复制下方指令发给 AI,AI 会调用写库。」＋ 一个主按钮 ＋ 一个 `copy-preview` 预览框
6. 页脚「卡路里 Skill · 目标推荐 · 2026-08-02」

### 2.2 吃的数据位

同样只有一个真占位符 `<!--INJECT-DATA-->`，另有 `<!--SHARED-CSS-->`、`<!--SHARED-HELPERS-->`。全部从 `DATA.data.*` 取：

| 键 | 含义 |
| --- | --- |
| `data.title` / `data.subtitle` | 页头两行；营养档副标题带「<方向>方案 · 基于档案(身高/体重/年龄)」，饮水档带「按体重 X kg × Y ml/kg(Z季)推荐」 |
| `data.current_goal.{calorie,protein,carbs,fat,water}_goal` | 推荐出来的目标值（注意：这里装的**不是**数据库当前值，是推荐值） |
| `data.old_water_goal` | 饮水旧目标，用来出「饮水 旧→新」KPI |
| `data.recommend.profile` / `profile_label` | 方案代号与中文名，`profileHint` 用 |
| `data.recommend.tdee` / `bmr` | 两个 KPI |
| `data.recommend.weekly_rate_kg` | 每周体重变化速率 KPI |
| `data.recommend.plan_reasons[]` | 推荐依据列表，也进复制预览 |
| `data.recommend.missing[]` | 缺哪几项档案，走橙色提示并说明用了默认值 |
| `data.meta` | 排障信息，页面不显示；复制指令里的唤醒词取自 `META.wake_word` |
| `data.old_goal`（可选） | 模板留了 compatibility：有旧值时行内先灰字显示「旧值 →」再显示新值，当前渲染器没下发这个键 |

### 2.3 可交互的东西

- **一个按钮「✓ 采纳全部推荐」**（`id=btnAdopt`）。复制内容是 `buildAdoptPrompt()`：开头「我已确认推荐目标，请按「<唤醒词>」流程写入数据库。」，随后按有无宏量写「营养目标:」或「饮水目标:」，逐行列目标值（热量 卡／蛋白 g／碳水 g／脂肪 g／饮水 ml），再跟「推荐理由:」逐条列出 `plan_reasons`。复制后按钮变绿 `采纳指令已复制,粘贴给 AI 即可写入 ✓`。
- **一个只读预览框 `copy-preview`**：加载时就等于上面那段指令的原文，用户可以先看再点按钮。这是推荐页独有的——两张配置页没有预览框（它们要拖完滑块才知道内容）。
- 底部同样有 `actionbar-zone` 操作条。
- 没有任何 slider 或输入框：推荐页是**只读＋两个动作（看清、采纳）**。

### 2.4 是否两段式，确认文案

**是两段式，但两段印在同一张页上。** `render_goal_recommend.py` 的文档头写明「呈现数据: TDEE/推荐值/每周减重速率/4 项 + 依据 + 方案理由」，对应 `goal_recommend.html` 的块顺序就是：先给推荐（推荐方案 ＋ 推荐依据 ＋ 档案缺提示），再给确认（采纳推荐区）。

确认那一步的文案，逐句如下：

- 区块标题：**采纳推荐**
- 说明：**确认无误后,复制下方指令发给 AI,AI 会调用写库。**
- 按钮：**✓ 采纳全部推荐**
- 预览框初值：**预览将复制给 AI 的内容**
- 复制成功：**采纳指令已复制,粘贴给 AI 即可写入 ✓**

所以「确认」没有第二张页、也没有单独的确认页；它就是一个按钮加一段预览，靠复制出来的那句话把确认带回对话。与之对照，两张配置页的对应文案是「更改配置」＋「拖动滑块调整目标,点击「更改配置」复制指令,粘到 AI 对话框即可按新配置写入。」——**配置页偏「我去改」，推荐页偏「AI 给我算的，我认了」。**



## 3. 写前／写后怎么分

`render_goal_config.py` 一共 4 个场景，全靠命令行开关分流（`main()` 第 176–183 行）：

| 开关 | 场景名 | 模板 | 输出类型 |
| --- | --- | --- | --- |
| 无（默认 `--live`） | 定营养目标 | goal_config_nutrition.html | `receipt` |
| `--water-only` | 定饮水目标 | goal_config_water.html | `receipt` |
| `--modify-nutrition` | 改营养目标 | goal_config_nutrition.html | `receipt` |
| `--modify-water` | 改饮水目标 | goal_config_water.html | `receipt` |

定下之后由脚本往数据里塞两个开关，模板据此分块：

- `data['diff']`：只有 `--modify-*` 才有。`diff.items` 每项是 `{key, label, unit, old, new, impact}`，`old` 取数据库当前值，`new` 一律是 `None`，`impact` 一律是字符串「由 AI 按新值给出影响预估」——**老技能自己不做对比表算数，只把「改前基准」摆给 AI/用户看**。
- `data['water_only']`：只有 `--water-only` 才是 `True`。
- `data['bmr_warning']`：只要热量目标存在就出，`{bmr, calorie_goal, below, text}`，`below=True` 时文案「热量目标 X 卡低于基础代谢 BMR Y 卡，长期可能影响健康，建议上调或咨询专业意见」。

其余全局字段：`data['page_title']`（按场景取值：`营养目标` / `营养目标 · 修改` / `饮水目标` / `饮水目标 · 修改`）、`data['scene']`（场景名）、`data['meta']`（`build_meta(wake_word, source, chain)`，脚本注明「meta 不进 UI，复制日志带出」）。

**写前／写后的真实分界不是 `output_type`——4 个场景它全是 `receipt`。** 分界是「有没有 `diff`」：定了没改 = 纯展示现状与推荐（写前对照），`--modify-*` = 多出改前／改后对照块（写后回执的形态）。

同一张模板两种用途时分块如下（两页一致）：

| 块 | 只在写前出 | 只在写后出 | 两种情况都出 |
| --- | --- | --- | --- |
| 页头／slider 区／📊 对比图／配置复制区 | | | ✅ |
| 改前 vs 改后（明细行） | | ✅（有 `diff` 才显示） | |
| ⚠️ BMR 低值提示（仅营养页） | | | ✅（只要 `current_goal.calorie_goal` 有值就出；首次设定热量为空时不出） |

三个细节：

1. 页头标题是**场景名**决定的，不是 `diff` 决定的：`定营养目标` → 「营养目标」，`--modify-nutrition` → 「营养目标 · 修改」。所以「写前／写后」这件事在标题上表现为多一个「· 修改」后缀。
2. slider 区在两种情况下都在，但含义不同：写前它的初值是当前目标（首次设定时为 `min`，即 0），写后它的初值仍是当前目标。**页面从不区分「我要设一个新值」和「我要改一个旧值」，它只区分「要不要多显示一张改前／改后对照表」。**
3. `--water-only` 只用来选模板（饮水单字段页），不改变写前／写后。饮水页没有 `bmr_warning` 这条旁路，所以饮水页写前／写后的差别**只有**那张「改前 vs 改后」明细块。另外脚本里 `data['water_only']` 这个键其实没人读了——模板里的 `water_only` 旁路已经在 2026-08-04 ADR-0009 被删掉（模板第 123 行注释原文：「营养配置页固定 5 字段，不再有 water_only 旁路」）。

`render_goal_recommend.py` 那边没有写前／写后开关：`--profile`、`--water-only`、`--full-kit` 只换标题与数据，`output_type` 一律 `receipt`。它整张页都是「写前」——把 AI 算出来的东西摆给人看，等人点采纳。

## 4. 不确定

- `data.fields`（字段声明契约）在两张配置页里都读了、也写了回退值，但 `render_goal_config.py` 的 `normalize()` 里**没有**这个键——也就是说实际下发时恒为 `undefined`，模板永远走回退的硬编码 5 键（或 `['water_goal']`）。是渲染器还没补上，还是靠 `_base_render.render_template` 偷偷塞进去，我没读 `_base_render.py`，读不出来。
- `--full-kit` 模式下体重目标「由 AI 确认后写入」——文案在 `render_goal_recommend.py` 第 113 行，但页面上**没有任何体重目标的输入位或确认块**，`current_goal` 里也不带 `weight_goal`。这条确认在页面上怎么落到人眼前，读不出来。
- `weight_progress` 在 `build_live_data()` 里被写死 `None`，所以营养页的「体重目标进度」块在当前版本**永远不显示**。这算遗留还是待接，说不准。
- 页面底部那句注释「R2 双按钮:复制数据(用户口径)/ 复制日志(排障口径)」对应的两个按钮**没有写死在模板里**，靠 `window.actionBar(window.__P__)` 在底部注入。这两颗按钮到底叫什么、分别复制什么，我没读公共层脚本，读不出来（模板里只剩注释和空行）。
- `render_goal_recommend.py` 的 `build_data(profile, water_only)` 支持 `water_only`，但 `--full-kit` 只改标题不下发饮水单独数据；一键全套时 `current_goal` 里的饮水值取的是 `recommend_nutrition_goal()` 返回的那个 `water_goal`，与 `recommend_water_goal()` 是否一致，我没读 `nutrition_goal.py`，读不出来。
- `data.old_goal`（行内「旧值 →」）在模板里有分支，但渲染器没下发；这是给谁用的兼容口，读不出来。
