## 二、读命令缺失阻断被改软（本次勘查发现的真缺陷）

### 2.1 现象

### 2.3 归因（本票引入，非「既有红」）

| 时刻 | 事实 |
|---|---|
| 2026-09-14 12:23 | `docs/skills/skill-calorie/t349-close-ready-20260914.md` 记录该测试 `exit 0，pass 1／fail 0` |
| 2026-09-14 13:40 | 提交 `5255b01`「撤销后读验证空态页195-verify及计划看复制区接线」**引入了那个 catch** |

绿在前、catch 在后 ⇒ 回归由 `5255b01` 引入。该 catch 分支是 `buildPlanDeleteVerifyDoc` 的**唯一**调用点（全仓只 `workout/plan.ts:13,36` 两处）。

### 2.4 为什么必须改回

1. #349 的验收判据逐字写着「撤销后读验证应为 exit 4 缺失阻断」——冻结判据不许靠改测试迁就实现。
2. `packages/skill-calorie/SKILL.md` 正文：「缺失阻断不返空：空库／空窗／无目标一律 `missing-data`（调用方走 fallback，**不静默空页**）」。吞掉 `missing-data` 正是它禁止的做法。
3. 实质害处：读命令再无法区分「没有计划」与「有计划」，调用方的 fallback 全部失效。
4. 动机存疑：该空态页是**为了让 195 有一条好看的证据产物而把读命令的契约改软**——产物驱动的设计让步，不成立。

**处理**：恢复缺失阻断；`render/planDeleteVerifyDocs.ts` 随之成为无调用方的死件，按结构纪律删掉（或找它该在的正确调用点），不许留死代码。「已撤销」这一状态不会丢——撤销的回执页本就出「写后现值」表（`workout/receipt.ts` 的 `currentPlanTable`），写明「计划已撤销（配置＋会话均为空）」。
