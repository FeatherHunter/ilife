### (b) 字号阶梯：正文／标题／次级文字；手机档最小字号；有没有掉到 12px 以下

**② 专答：`renderDataTable` 在 ≤640 到底做什么**（`blocks.ts:1638`–`1657`，规则原文逐条）

```css
  .ilife-block-data-table td { padding: 7px 8px; font-size: 12px; overflow-wrap: anywhere; }

```

**它做的事：收字号（表头 12→11px、单元格 13→12px）、收内距（10/14→6/8、12/14→7/8）、
放开 `th` 的 `nowrap`、给 `td` 加 `overflow-wrap:anywhere`。**
设计意图（`blocks.ts:1630`–`1635` 注释原文要点）：
- 标题是「**不靠左右滑动看全**」；
- `th` 的 `white-space:nowrap` 是「表宽唯一的硬来源：表头不换行 → 最小宽度＝各列整词宽之和」，放开它＋
  `td` 的 `overflow-wrap:anywhere`（「把单元格的最小内容宽度压到 1 字符」）⇒ 「**7 列表在 390 宽里放得下**」；
- 容器仍留 `overflow-x:auto` 作兜底，「列数极多的表仍可滑，但**常态不再触发**」。
- **不塌卡片、不折叠、不横滚（常态）。** 只有「列数极多」才回落到 `overflow-x:auto`。
- 与桌面档的硬碰点（`blocks.ts:1621-1623`）：`nowrap` 与 ≤640 的「靠折行换不横滚」冲突，
  故行首列规则**只加在桌面侧** `min-width:641px`，窄屏段「一字不动」。

**③ 专答：KPI 卡网格 `repeat(auto-fit,minmax(150px,1fr))` 在 ≤640 会不会真出现「3＋1 孤行」**

**不会。已在 #507 修掉。** 关键注释原文（`blocks.ts:1488`–`1499`）：
- 成因：「`auto-fit minmax(150px,1fr)` 只在容器有效宽 ≥474px 时排 3 列（3×150 ＋ 2×12 间隙），
  而手机端页壳 `padding:20px 16px`…… **512 视口下栅格有效宽仅 480px ⇒ 正好卡在 3 列下沿，
  第 4 张卡单独占一行、宽度只有前三张的 1/3**（`grid-auto-rows:1fr` 又让它与前三张等高），看着像漏了一张。」
- 修法：`@media (max-width: 640px)` 内**显式 2 列** `repeat(2, minmax(0,1fr))` ⇒ 「4 张卡排成整齐 2×2」，
  `minmax(0,...)` 的下限 0「是下限（不是 `auto` 那种取内容最小宽），长值卡不会被撑破」。
- 选择器写成 `.ilife-block-page-shell .ilife-block-kpi-card-grid`（**祖先类 + 基座类**），
  理由（`:1498`）：本仓 CSS 纪律测试 `test/ui-fix-154.test.mjs` 的 `declsOf` 按「某类名的**基座规则**恰 1 条」判账，
  同名再起一条会被数成 2 条而红。
- **残留区间**：修法只在 ≤640 生效。**641–767 之间**（480px 有效宽那条推导的临界带）没被这条管，
  该档是否仍会出现 3＋1，本件未实测 ⇒ 进第 5 节。
