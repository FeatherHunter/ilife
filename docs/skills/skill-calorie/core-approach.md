## 三、每个场景怎么开发（三步走）

### 第 1 步 · 唤醒词：先看这个场景有哪些唤醒词

**开发期从这里出发：读老技能的 `SKILL.md`**（154.3 KB / 2196 行），它每个场景都有一张
**「唤醒词 ｜ 功能 ｜ CLI」**表格——「功能」那列就是第 2 步「流程走向」的现成起点。

### 第 2 步 · 流程走向：用户触发唤醒词之后往底层走流程

在这个流程中，**因为工作需要，可能会返回一些过程型的 HTML 给用户**。

### 第 3 步 · AI 执行：用户复制 prompt 提示词模板给 AI

**AI 靠 prompt 提示词模板里的「后续唤醒词」完成任务，然后返回结果型 HTML。**

> 关键点（最容易漏）：**prompt 提示词模板里带着后续的唤醒词**——AI 是拿这个后续唤醒词去干活的，
> 不是靠别的协议。这解释了为什么「复制 prompt」这一步就够用。

## 四、公共组件怎么来：不是先建，是「打通流程的过程中长出来」

用户原话：**「我的核心是把整个工作流程打通。在打通的过程中，慢慢把我们的 HTML 或页面封装成卡路里技能使用的公共组件，甚至进一步变成整个 Base 库的公共组件，方便后面我一个场景一个场景过的时候可以复用，更高效地进行开发。」**

- **公共层 ≠ 页面。** 公共层是**组件**。页面是组件的调用结果。
- 顺序是：**先打通流程 → 过程中把反复出现的 HTML／页面抽成组件 → 先做卡路里技能内的公共组件 → 成熟且跨技能通用的再上移到 Base 库。**
- 复用机制：**过一个场景时，能复用的就复用**，这让下一个场景更高效。

## 五、为什么这样能保证不遗漏

用户原话：**「我们把唤醒词流程从上到下打通，在这个过程中慢慢就补全了公共组件。你发现的所有可能被遗漏、被疏忽的点，都会在这个过程中被补足。因为我们的唤醒词场景是全面的，当所有的唤醒词全部打通，公共组件也封装好了，这个时候就已经是一个很优质的东西了。」**

**机制（拆开说）：**

1. **分母是全面的** —— 436 条唤醒词覆盖了 10 个场景的全部流程。
2. **主语是明确的** —— 「谁负责抽组件」的答案就是**正在做那个场景／那张票的人**；不存在无人负责的公共品。
3. **不遗漏的保证来自覆盖面** —— 只要每条唤醒词的流程都走到尾，中途需要的组件必然被碰到。
4. **不必现在敲死细节** —— 按需判断、按实际情况定，**不要一开始就规定必须怎么做**。

## 七、验收怎么算「打通」（用户 2026-09-11 明确）

用户原话：**「我先去看一眼生成的 HTML，然后我自己会亲自拿一个 prompt 提示词，去到一个全新的空白 session 里面去问，拿到 HTML 之后，我再看。」**

**这就是「打通」的验收方式——用户在环，两步：**

1. **先看一眼生成的 HTML**（用户自己看）。
2. **用户亲自拿一个 prompt 提示词，去一个全新的空白 session 里问**；拿到 HTML 之后**再看一次**。

> 先例：卡路里 help.html 与饼干记账 help.html **都是这样打通的**。
> **所以「打通」不是程序自测通过，而是用户在两处亲眼看、并在一个干净 session 里真跑一遍。**

## 八、票怎么规划：一张图内拆多张票，一张票可跨多次 session

用户原话：**「比如饮食，它有饮食的 map，里面有大量的 issue 票。我们可以把它拆成 5 个票、10 个票，分门别类地去推进。那么一个票可能会在多次 session 里面多次去处理。只要我们把票规划好了，这个不需要你担心。」**

- **一张图（一个场景）可以拆成 5 张、10 张票**，分门别类推进。
- **一张票可以跨多次 session** 反复处理。
- **把票规划好是 agent 的责任**，不需要用户担心。

## 九、不必现在敲死的事（留到推进中判断）

用户原话（关于新发现的词）：

> **「在推进过程中，我发现那些具体的词是什么，到时候我再判断要不要做。这个不是我们一开始就要把它全定死的，它是在推进中慢慢被解开的雾。」**

**所以：**

- **不预先为所有情况定死规则**——包括预检确认页的形态、新拟词的处置、组件的边界。
- 到具体的那条唤醒词时，按实际情况判断：**有可复用的就复用，没有的就重新开发**。
  「这不影响。不需要现在就把决策做得太细，而是在 map 推进的过程中让它变得完善。」
- 预检确认页的**来源会很丰富**（老实物改造／新设计／用户当场定），**不要现在规定必须怎么做**。

### 但有一条已经查出来的、具体到「哪条唤醒词」的事实（2026-09-11）

**有些唤醒词的 prompt 已经在要求 AI「先问用户 / 先确认」，但它们的模板是「写完之后的回执页」——中间没有预检确认页可渲染。**

扫描 436 条的 `prompt_template`，命中 **14 条**在让 AI 先问／先确认；其中 **12 条**的模板是写后回执（另 2 条已是写前页：
场景 05 `定训练计划` → `plan_builder_wizard.html`、场景 08 `记体脂（皮褶钳）` → `body_composition_wizard.html`）。
剩下 2 条（场景 04 `看今日运动（vs 目标）`、`看本周运动（vs 目标）`）是**读类**，说的是「目标未设时先问」——不是写前确认。

**最典型的两条就在第一张图（场景 07 基础信息）：**

| 场景 | 唤醒词 | prompt 里的要求 | 现有模板 | 缺什么 |
|---|---|---|---|---|
| 07 | **设置档案** | 「如果我没说全，请**一项一项问我**，并根据我的日常情况推荐合适的活动量」 | `crud_receipt.html`（**写完之后**的回执） | 缺「收集 4 项＋推荐活动量」的写前页 |
| 07 | **改档案** | 「改之前请**先确认我原来的值**」 | `crud_receipt.html`（**写完之后**的回执） | 缺「改前/改后对比＋确认」的写前页 |

补一条细节：这两条的 prompt 里本来就留着**空位（`____`）**——
`设置档案` 4 个空位（我的身高/年龄/性别/日常活动情况）、`改档案` 5 个空位（身高/年龄/性别/活动量/备注的新值）。
**空位就是预检页要摆出来的字段。**

**对照证据（说明这条路走得通）**：同批里被正确标成 `output_type=process` 的 6 条（如**批量导入食品** → `batch_import_preview.html`），
prompt 写的是「**先给我看导入预览**（导入条数/跳过条数/失败明细），**我确认后再真正写入**」——**那才是有预检页的那条路**。

> **结论：不需要现在定形态，但到每条唤醒词时，要检查「prompt 让 AI 先问/先确认」与「模板是写前还是写后」是否对得上。**
> 对不上就在那条唤醒词上补一张写前页——**来源按本节：有可复用的就复用，没有就新设计。**

## 十、由这份思路直接推出的执行纪律

1. **一张图 ＝ 一个场景**，顺序按第一节的表，**不再讨论顺序**。
2. **验收基准是 HELP HTML**（唤醒词／场景／prompt 全都要支持）；老 `SKILL.md` 是开发期参考。
3. **每条唤醒词走「三步走」**：取唤醒词 → 跟流程（含过程型 HTML）→ 确认 prompt 里的后续唤醒词能让 AI 完成任务并出结果型 HTML。
4. **过程中抽组件**：反复出现的 HTML／页面，抽成卡路里技能内公共组件；成熟且跨技能通用的上移 Base 库。
5. **验收按第七节**：用户先看 HTML → 用户拿 prompt 去全新空白 session 真跑 → 再看 HTML。
6. **票由 agent 规划**：一张图多张票，一张票可跨多次 session。
7. **不确定的事不预先敲死**：到那条唤醒词时按实际情况判断。
8. **用词**：公共层 ＝ 组件；「页面」与「组件」不混用。详见 `docs/agents/wording.md`。
