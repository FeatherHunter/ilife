已定（契约五问）

问结论
契约单位「ensure 型合成写」：被调方一条命令把一条业务事实对齐到「本地库 ＋ 它的外部平台」两侧；两侧各按自然键判重；远端 id 回写本地；回执分字段报两侧状态
判重归谁两侧各自判重，责任全在被调方；调用方永不碰对方的库与第三方平台
部分失败回执分字段 ＋ 退出码非 0（两者都要）
远端 id 落位算契约的一部分
#598 范围只定契约形状、不管具体命令，与 #599／#600 并行
追加一条（本轮新证据）→ 已答的「远端 id 落位」要扩成两件 ① 远端 id 存回本地（幂等锚、改删目标）；② 远端对象上带可反查的归属锚（归属判断、反向关联）。
老代码两家都用这手法：作息把 "作息管家自动同步" 前缀放进飞书日程描述（schedule_db.py:1137），diff 靠它决定「这条远端日程是不是我管的、敢不敢删」；备忘把 "原备忘 #<id>" 放进飞书任务描述（feishu_sync.py:329），反向对账用正则从飞书反查本地 id。新仓两边都丢了。

Q2 · 三处冲突以谁为准

前因后果

你上次答「拆开：降级语义照老、报告语义照新」。这条在调查里被证实是对的——老代码几乎全走「降级继续」，唯一「远端不可用即阻断」的入口只有 cmd_feishu_resync。但本轮又挖出第三处冲突，需要你补一刀。

冲突老口径新仓／迁移件口径
① 远端不可用降级继续：本地照样成，返 None，不抛错阻断：四门全绿才同步，否则 exit 4（迁移件 schedule-migration-split.md:41 已冻）

③ 新增：写 op 的形态不统一：ensure-plan-event ＝合成写；upsert-plan-events／update-event／deactivate-event ＝ 本地写 ＋ 询问后同步（_maybe_sync_after_write 88 行 ＋ ask_callback）已定「ensure 型合成写」，但其余 op 未定
统一到合成写（推荐）利：契约只写一套；调用方不必先判断「该用哪个 op」；正好消灭我们想消灭的那种不确定

➡️ 推荐
① 降级照老：远端不可用不拦住本地写（本地那条日程该落还得落）；② 报告照新：最终没达成要非 0；③ 写 op 全部统一成合成写，并在口径里写死「覆盖 vs 跳过」由哪个参数表达。

Q3 · 「逻辑一致」用什么判据验

为什么这问必须先定 「逻辑一致」是句空话，除非它有一个可机器跑、或可比对的判据。而老代码本身有结构缺陷（cmd_help 两份同名定义、_iso_to_hhmm 两份副本、feishu_sync.py:931-1005 一段死代码残块、ensure_plan_event:1118 的短路是死代码因为 FeishuStatus 对象恒真）——逐字对拍会把缺陷一起搬。
(c) 不变量清单为主 ★推荐把老脚本行为逐条写成断言：幂等键（本地侧／远端侧各是什么）／查重字段／失败行为／id 回写／归属锚／远端不可用时降级还是阻断。新实现逐条过。
(a) 老 py 测试逐条翻成 TS 测试老仓 tests/ 作息约 35 件、备忘约 35 件。

Q6 · 飞书层移植深度（这问最影响工作量与价值）
