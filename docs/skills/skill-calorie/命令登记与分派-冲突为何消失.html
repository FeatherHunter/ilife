冲突是怎样消失的

对象：cli/keys.ts · cli/cmd_read.ts · cli/write.ts（＋三处同源副本）　｜　配套文档：命令登记与分派-方案.html　｜　2026-09-13

一句话：这套方案不靠"协调"避免冲突，而是靠把共用文件从改动路径里拿掉——每条命令的事实（叫什么、长什么形状、谁来处理）都住在它自己那个能力的目录里，而所有"汇总表"改由脚本从这些声明确定性生成。没有人写共用文件，就没有可冲突的地方。

一、先看清冲突长什么样

本仓是单一工作树、单一 master：五张地图的 session 同时在同一个目录里改文件。这种前提下，两个人同时改一个文件不是"git 合并冲突"（那种还能解），而是：

情形 A · 交错写入

甲把文件读进内存 → 乙读同一版本 → 甲写回 → 乙写回。乙的写回基于旧版本，甲那一整段改动被无声抹掉。没有报错，没有冲突标记。

情形 B · 区域交错

两人改的是同一个大文件的不同段落，看起来"各改各的"，但写回的是整份文件——先写的人的所有改动，对后写的人不存在。

所以真正要消灭的不是"冲突提示"，而是"同一时刻两个 writer 命中同一个文件"这件事本身。锁只能让命中变成排队：概率降低、并行度归零，而且要求每个 writer 都守规矩——它治的是症状。

二、把冲突面写成一句话

冲突面 ＝ 一次改动要写的文件里，有多少是"别人也可能同时写"的。

今天"加一条命令"要写 6 处共用文件（三个 case／登记文件 ＋ 三处同源副本）。本批并行 5 张图 ⇒ 潜在交叉 6 × C(5,2) = 60 对。只要这个乘积不为零，冲突就只是时间问题。

五、为什么"派生"能把冲突变成不可能

性质一确定性 ⇒ 不需要"谁先谁后"
生成器的输入是若干份互不相干的声明，输出只由输入决定（按能力名、键名排序）。谁跑、什么时候跑、跑几次，结果逐字节相同。冲突的前提是"两个结果要人挑一个"——确定性让这个前提消失。

性质二单一权威源 ⇒ 不存在"同一行两个主人"
命令的每个事实只在一处写下来（那个能力的声明）。别的文件里出现的同一事实都是它的投影。冲突的必要条件是"同一行被两个人写"——权威源让这个条件无法成立。

性质三可验证 ⇒ 派生不会退化成第二份手抄
配 pnpm gen:check（生成物 ≠ 生成器输出即红）与哈希锁：手改生成物会被机器当场抓住。少了这一条，生成物就会重新被人手改，冲突只是从"三个原始文件"搬到"三个生成文件"，白折腾。

为什么不是"锁"：锁把"冲突"换成"排队"——概率降低，不归零，还要求每个 writer 都守规矩。而这里的方案不要求任何人的自觉：共用位没有人写，就不存在抢。锁在改造期仍要用（见第七节），但它是过渡，不是答案。

七、改造期的过渡（三条，今天就能生效）

  1. 共用位白名单 ＋ 抢锁：keys.ts／cmd_read.ts／write.ts／combos.yaml／routing.ts／SKILL.md 改前抢 gate.lock，改完立刻 commit ＋ push。
  2. 一次委托：本图建骨架那次就把体重分支改成调 src/weight/index.ts 那道门 —— 此后第 3–7 张票对共用位接触为 0。
  3. 票面写集：跨图撞车时停下报告，不自行改别人的行。

八、怎么证明它真的有效（可复跑）

  1. 写入集合对账：两个 session 各自"加一条命令"，跑完 git status --short —— 应只见各自的路径，零交集。
  2. 生成物一致：任一 session 跑 pnpm gen 后 git diff 为空（确定性）；手改生成物再跑 gen:check 应变红（鉴别力）。
  3. 既有断言不退化：路由与键的穷举断言（每键恰一次、键集合与路由集合一致）保持绿——它们是把"生成错了"变成"立刻可见"的网。

九、与本图（#154 场景 03 体重）的关系

  • 第 2 张票（骨架）＝ 建 src/weight/ ＋ 一次委托；第 3–7 张票只在各自子功能文件里干活，共用位零接触。
  • 第 8／9 张票只剩 routing.ts 的体重段与 SKILL.md 体重侧；改造落地后它们也变成"写自己那一段"。
  • 结论：本图不等改造——改造票（并入 #181）与本图的页面／命令开发可以并行，只要在改造落地前守第七节那三条。
