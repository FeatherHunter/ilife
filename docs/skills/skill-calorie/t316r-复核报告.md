### 3.3 为什么现在的机制抓不住

`pnpm build` = `tsc -b && node scripts/gen-cli.mjs --stamp`。两道防线各有职责：

1. **`tsc -b` 是增量编译**，判据是 `tsbuildinfo` 里记的文件版本（mtime＋size）。mtime 被 `Copy-Item` 拉回原值时，`tsc -b` 认定「源没动」⇒ **不重编** ⇒ `dist/<能力>/commands.js` 仍是旧声明。
2. **内容印记 `dist/.gen-inputs.json` 是「源文件的 sha256」**，它在 `tsc -b` **之后被无条件重打** —— 这里记的是「源现在长什么样」，**不记「dist 是不是这份源编出来的」**。攻击下源哈希变了、`dist` 哈希没变，印记照样"一致"。
3. `pnpm gen:check` 比的是**「盘上生成物」vs「生成器此刻的输出」**两面，而生成器读的是 `dist`。两面都源自同一份**陈旧 dist**，自然相等 ⇒ PASS。

所以：`GEN-STALE` 守的是「源改了、**没**跑 build」；它**不守**「源改了、build 跑了、`tsc -b` 却跳过」。

### 3.4 建议修法（对编排者设想的一处独立判断）

编排者的设想是「印记记**源↔`dist` 配对哈希**，`gen:check` 校验配对是否仍成立」——**成立，且是最省的落法**，我认可并把它具体化：

- 把 `.gen-inputs.json` 的每一条从 `{src: sha256(src)}` 改成 `{src: sha256(src), dist: sha256(dist/<对应编译产物>)}`；
- `gen:check` 开头加一步**配对校验**：重算现刻 `sha256(src)`，与印记里的比对（现有行为），**并**重算现刻 `sha256(dist)` 与印记里的 `dist` 比对；两者任一不等 ⇒ 报**新的一类** `GEN-PAIR FAIL`（措辞区别于 `GEN-STALE`：这一次是「dist 与它声称的源不是同一次产物，请重跑 `pnpm build` 并确认 `tsc -b` 真的重编了」）。
- 为什么这条够：攻击下源哈希变了而 `dist` 哈希没变 ⇒ 配对不成立 ⇒ 红。它同时覆盖「`tsc -b` 因 mtime／`tsbuildinfo` 被误判而跳过」的所有变体，不依赖任何时间戳语义（与现有设计「不看时间戳」的取向一致）。
- 更省的一步兜底（可与上面并用）：`--stamp` 那一步在打印记前**自检 `tsc -b` 是否真的产出过新 `dist`**（比对打印记前后 `dist/**` 的哈希集合，未变而源哈希已变即报红）。这条只多一次目录哈希，但把「跳过」这件事从"沉默"变成"出声"。
- **不建议**的修法：把 `pnpm build` 改成强制 `tsc -b --force`。它把每次全量重编的代价摊到所有 ticket 上，且下次有人写个「复制源文件」的脚本仍会重演；病根在**印记的语义**，不在编译开关。
