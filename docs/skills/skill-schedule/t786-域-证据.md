## 五、本票自己裁的几处（都写进了代码注释与票面）

1. **一族一张页**：查日程这一族四支（缺省／标题搜／时段查重／含已软删）共用 `renderPlanDayPage` 一张页——四条路都落在 `schedule.plan.today` 这一枚 key 上，出口只按 key 分派（路由表没给它们各自的预设），下游分不出是哪一支。各自的**查法**写在页头与结论条上（「按标题『开发』搜到 1 件」「09:00 至 11:30 这一段里有 1 件」），不让读者猜这一页为什么只有几件。全天的读数（色带／空档／读数卡）仍按**活跃事件**算，只有列表换成命中集合。
2. **已软删不另立一张页**：软删事件上同一张页、行尾标「已软删」、结论条报条数；缺省档一颗不上屏（探针两面都断言）。理由是页型是 #782 人裁冻结的件序列，多一块就是改形状。
3. **查日程那一份口径仍住 `plan` 侧**（`src/plan/planDocs.ts`）：它的「空档推算」是 `plan` 与 `query` 两边都在用的口径（f10 查日程页 ＋ #787 商量计划的空档提示），抄一份到 `query` 就走散了；本票只把它的**文案**改过分隔符门 ＋ 补两支数据，并经能力门（`src/plan/index.ts`）转出给 `query` 侧用（不深引用）。**这一处是越界报备**（别域能力目录），见第六节。
4. **时段查重的窗口边界不借 `normalizeTime`**：它把 `24:00` 改写成 `23:59`（飞书 ISO 的口径），拿来做窗口上界会把 23:00 至 23:59 那一条漏在窗口外——本件另写 `minutesOf`，并在处理函数里只说清「校验走它、返回值不用」。
5. **详情页 11 个字段的分工照老侧**：老侧 `render_records_detail` 自己列的 11 个字段（id／date／time_start／time_end／duration_minutes／activity／category／source_contents／source_timestamps／analysis_reasoning／created_at），前十个落事实格（老侧页的字段名照抄：消息原文／消息时间戳），`analysis_reasoning` 落它自己那一段的全文；空的那一条写「（无）」（老侧页同一个写法），**这一段恒在**，字段不因缺内容少一块。
6. **`split` 判行的读法**：空档那几行与事件卡走同一个行列表类（公共层的 `renderListRows`），探针按 `<details>` 的起点切一刀只数事件卡——这是「件序列由 #782 冻死」的直接推论，不另加类名。
