Q1

老 HELP 里新仓没有的那 5 个词，算不算「所有唤醒词」之内

老侧 34 个唤醒词里有 5 个新仓既没有命令也没有页面。其中准备消息／同步作息／增量同步背后是语取消息库（daily_recorder.db），仓里早就裁过「以外置为准，不迁」，而且老侧这三条本身也只出 JSON、不产 HTML。另外两条不一样：周视图（7×24 全分类热力图）与首次使用（6 步向导）在老侧是真有页的（record/week/查作息周视图_*.html、setup/首次使用_*.html），也是这一代 HELP 才加进来的新词。

推荐

补「周视图」与「首次使用」两条；语取三条维持出 scope，在链路页的「有意不出」一节写明原因。

A
补 2 条（周视图、首次使用） 两条都是纯本库能力，补完 34 词里除语取三条外全部有页；HELP 里那 3 条词的「待开发」标记继续挂着，但链路页会说清为什么。 「全部唤醒词」字面上仍缺 3 个，需要你在 HELP 文案上认可这个例外。
B
5 条全补 字面 100% 齐。 要做外置消息库的取数与游标链，超出本技能边界，且老侧那三条本来就不产页，等于新造三种页。
C
5 条都不做 最省事。 周视图是你真用过的页（一周作息一眼看全），砍掉会让「查作息」这一族少掉唯一的跨天视图。
Q2

交付单元：一格是一个唤醒词，还是一个场景

老侧 85 个场景里，60 个产 HTML，另外 25 个只出文本或 JSON（非法分类、缺字段、按标题搜索、飞书对账、无记录空态这类）。墙的一格＝一次人的肉眼验收，格子的切法决定了这面墙要铺多长。

推荐

按唤醒词切格：34 个唤醒词各出一份代表产物，别名同页；边界与错误态由机检判据钉住，不进墙。

A
按唤醒词（约 34 格） 与仓里两处先例同口径（记账 #403 的 18 格、卡路里场景02 的 83 格）；一格对应一句人话，你滚一遍就知道哪句话的页不好看。 边界态（空库、无记录、坏分类）不出现在墙里，得信机检判据的读数。
B
按场景（85 格） 覆盖最全，错误态也看得见。 其中约 25 格注定要么无产物、要么内容雷同（三条「无记录」长一个样），墙会膨胀到两倍而信息不增。
Q3

「老作息管家是权威来源」包不包括它的视觉

老页面是 Python 渲染的单文件 HTML，样式内联、控件是老 Base 库；它确实有一套不错的移动端手法（640 单断点、安全区、折叠三层、44px 触摸目标）。新仓有公共层 base-paint：21 个区块件（指标卡、数据表、图表、列表行、空态…）、移动端配方 pageUi、以及卡路里／记账正在用的同一套样式表。

推荐

内容的权威性照老（页面清单、场景语义、字段口径），视觉走新仓公共层，跟卡路里、记账同族。

A
内容照老，视觉走公共层 双端自适应、复制／折叠／触摸目标、打印样式全部现成；六家的页面长得像一家人，后续改样式一处生效。 老页面某些专属版式（比如 7×24 热力图的老画法）要重画成公共层的图表件，不是逐像素照搬。
B
视觉也照老页面复刻 与你过去看惯的样子完全一致。 要把老模板那 17 条移动端手法与全部内联样式搬进来，与「解耦、照卡路里架构」这件事方向相反；公共层的共享控件也用不上。
Q4

解耦做到哪一层：只摆页面，还是连命令登记一起搬

仓规要求「一条命令的事实只住它自己的能力目录 src/<能力>/commands.ts」，共用位由 pnpm gen 派生、gen:check 守。今天做到这件事的只有卡路里（10 个能力）与记账（6 个）；作息这边一条命令的事实散在六个地方（形状表、模板表、唤醒词表、分派 switch、载荷装配、设置页 key）。两年前的结构裁定已经写明：五个能力目录（写入与同步／查询与浏览／日程与计划／分析与洞察／辅助与管理）与该目录的第一件东西同时建——至今没建。

推荐

两件都做：新页面按 HELP 五域住进 src/<能力>/；命令登记搬进 commands.ts 并接进 pnpm gen／gen:check。这一步单独一张票，开头先推一次建立 CI 基线。

A
目录 ＋ 命令登记，都搬 「同一个口径两处各算一遍」这类病只有一处定义才能根治；后面再加唤醒词是改一行声明、跑一次生成，不再动六个文件。 要动生成链（会进 CI 面），多一张票、多一次独立验证；短期看是「为了以后」付的代价。
B
只摆页面，命令登记维持现状 票数少一张，风险低，页面照样能出。 每条命令的事实继续散在六处，下一个域加词时继续踩同一个坑；你说过「代码架构需要解耦」，这一半就还是没做。
Q5

飞书链与「商量计划」这种多轮链，做到哪一步

「日程管家同步」「飞书探测」要本机 lark-cli 四门全绿才能真跑；「商量计划」是人机来回：先出预览页，你确认后写库，再出回执页。老侧这两类里，只有一部分产 HTML，另一部分自己就只打文本。

推荐

交互链做到三段都能独立跑、页都出得来（预览页与写库回执页分开）；飞书链做到探测页与同步回执页出得来，本机能跑就真跑，跑不了的在票面写清外部确认出口（谁触发、看哪个读数、失败怎么办）。

A
都出页，跑不动的写明外部出口 35 个唤醒词的页面面闭合，不留洞；不把「待确认」当完工。 飞书那两格的验收分两段：本地那段可判，远端那段要靠你那边的一次真实同步确认。
B
飞书链本轮不做 本轮全部判据本地可判，收口干净。 「日程与计划」域留两个洞，链路页上要写「有意不出」，等于你这轮验收看不到飞书那一块的样子。
Q6

页面用什么数据、最终打分怎么算、产物落在哪

你机器上 ~/.ilife/data/ 里只有卡路里与记账的产物，没有任何作息产物——真库是空的，直接跑只能看到空态页，「生动形象」无从谈起。另外现在的配置把所有 HTML 都塞进 schedule_html/help 这一个子目录，页面产物会和 HELP 混在一起。最后，最终视觉审查的打分口径要先定死，收口时才有真假。

推荐

造一份隔离的种子库（固定锚点日期、覆盖五域场景，不碰真库）；打分按逐页 ≥90，取最低那一页；页面产物落 schedule_html/ 根，HELP 仍留 schedule_html/help/。

A
种子库 ＋ 逐页 90 ＋ 产物分家 数据可控可复现（同样的库能重出同一批页，读数可对账）；逐页 90 让最差的那一页必须修，不拿均值糊过去；产物分家后你平时找页不用翻进 help 子目录。 要多写一份种子数据脚本；页面产物落点变了，需要你认可这个新习惯。
B
真库 ＋ 均值 90 ＋ 落点不动 不造数据、不改配置，最省事。 空库下大半页面只有空态，验收看不到真实版式；均值 90 允许个别页 70 分蒙过去，正是你现在要防的那种「看起来过了」。
