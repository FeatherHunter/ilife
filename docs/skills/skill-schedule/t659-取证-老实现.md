## 三 · 查不清／矛盾（如实记）

1. **题面与代码不符（`feishu` 的取值集合）**：题面写 `feishu` 可能有 `None`，代码里不可能——`feishu_result or "unavailable"`（`schedule_db.py:1066`、`schedule_db.py:1083`）把 `None` 兜成字符串；且第一个 `found` 分支（`schedule_db.py:1062`）**整个键都不存在**。消费方若写 `r["feishu"]`，在「本地已有且已有飞书 ID」这条最常见路径上会 `KeyError`。
2. **「归属标记」有两套拼装规则（自相矛盾）**：ensure 写侧是前缀 `作息管家自动同步 · {notes}`（`schedule_db.py:1137`）；diff 写侧是后缀 `[{类别}] | {notes} | 作息管家自动同步`（`feishu_sync.py:1018`）。判定侧只用 substring（`feishu_sync.py:900`），所以不炸，但「逐字前缀」在两条写路径上不是同一个东西——若要复刻「字面一致」，必须选一条并以写路径为准。
3. **「单次返回上限 20 条」只是注释**：`feishu_sync.py:414`、`feishu_sync.py:511` 写了 20，但代码里没有常量、没有 `[:20]` 截断，无任何运行期可校验点；分片窗口数越多，总量线性增长（跨月范围会打出很多次 CLI 调用）。
4. **「孤儿清理」没有独立函数/命令**：三文件 grep `orphan|孤儿` 在飞书语境零命中；职责等于 `feishu_sync.py:889` Phase C 的删除动作。若裁定件点了「孤儿清理」这个名字，需以 Phase C 为准。
5. **`op=upsert`／`op=ensure` 无字面参数**：老仓是两条独立命令（`upsert-plan-events`／`ensure-plan-event`），不存在一个 `op` 开关；语义（覆盖 vs 缺则补）如 S-14，但「复刻 `op` 字段」的说法在老代码里没有等价物。
6. **死代码不止一处**：`schedule_db.py:1119`（S-06，`not is_feishu_available()` 分支）与 `feishu_sync.py:931`–`1005`（S-16 附注，旧 diff 实现残留在 `return` 之后）都是不可达代码；前者会误导后来人以为「远端不可用会提前 return」，实际靠 `except Exception` 兜。

## 四 · 硬结论（可直接引用）

- **`is_feishu_available()` 恒真**：`FeishuStatus` 是纯 `@dataclass`（`feishu_sync.py:75`），无 `__bool__`／`__len__`；`schedule_db.py:1118` 的 `if not is_feishu_available():` **永不成立**，`schedule_db.py:1119` `return None` 是死代码。降级实际由 `schedule_db.py:1143` 的 `except Exception: return None` 实现。
- **`create_event` 没有幂等键**：签名 `feishu_sync.py:288`–`295` 只有 `start/end/summary/description/calendar_id/dry_run`，全文无 `idempotency`／`client_token`；写前查重全靠 `search_events`（远端四元组，`schedule_db.py:1123`–`1132`）。
- **分片＝6 小时、单次上限＝20 条（仅注释）**：`window = timedelta(hours=6)`（`feishu_sync.py:522`），20 条只见于 `feishu_sync.py:414` 与 `feishu_sync.py:511` 注释，代码无强制。
- **`feishu-resync` 是阻断**：`schedule_cli.py:1496`–`1499` 在 Phase 0 之前 `return`，远端不可用即整条命令不做；对照 `_maybe_sync_after_write`（`schedule_cli.py:857`）是降级。在这份快照内是唯一阻断入口。
- **退出码几乎无信息**：只有「无参数」时 `sys.exit(1)`（`schedule_cli.py:648`）；所有失败路径打印后 `return`，退出码 0（`schedule_cli.py:488`、`schedule_cli.py:1526`、`schedule_cli.py:1561`）；「部分失败」只能靠 `diff_and_sync` 回执的 `errors`／`duplicate_groups` 文本解析。
- **旧入口 `upsert_plan` 必抛错且被吞**：写 `hour_N_planned`（`schedule_db.py:666`）而新表无此列（`schedule_db.py:801`），异常类型是 `OperationalError`，只接 `IntegrityError`（`schedule_db.py:673`），最终被 `cmd_upsert_plan` 的 `except Exception` 吞成一行提示（`schedule_cli.py:488`）。
