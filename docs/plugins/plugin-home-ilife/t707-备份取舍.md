# #707 居家「备份导出／导入恢复」：与老技能实现的差异与取舍

票面第 1 条的遗留出口。老技能那套实现在 `D:\2Study\StudyNotes\SKILLS\居家管家\scripts\开始使用\ops.py:434-597`（Python 线），
本仓没有直接搬，理由与代价记在这里。

## 修之前是什么样

HELP `scenarios.yaml` 有整组两个场景（`SM8-3 备份导出`／`SM8-4 导入恢复`），但出口只有两句回执：

- `packages/skill-home/src/cli/cmd_read.ts:696-697` —— `backup-list` 恒返回 `备份： home.db`（一件、字节数写死 1）；
- `packages/skill-home/src/cli/cmd_read.ts:723-731` —— `backup`／`export`／`import-preview`／`import` 只 `buildReceipt` 一句人话，**零文件产出**。

所以设置页要做「备份目录」那一项时，没有任何可接的落点。

## 取舍一 · 不做照片（只装库与清单）

老家 `_do_backup()`（`ops.py:528-538`）把 `DB_PATH` 与 `PHOTOS_DIR` 一起打进去，照片落在 zip 的 `photos/` 下。

本仓**不做**。依据是本包源码的实况：`HOME_PHOTOS_DIR` 在 `packages/skill-home/src` 下**零命中**
（`docs/env.md:12` 已登记的「照片变量不适用（无该变量）」），照片这一路根本没迁过来。
装了也用不上——恢复时没有消费者。

代价：**物品照片不在备份覆盖范围内**。哪天 `HOME_PHOTOS_DIR` 真的迁进本包，备份要同时扩 `photos/` 条目，
这份文档与 `test/backup.test.mjs` 的「两件」断言都要跟着改。

## 取舍二 · 快照走 `VACUUM INTO`，不照抄 `zf.write(DB_PATH)`

老家直接写库文件本身。本包**不能照抄**：`db.ts:66` 开库即 `PRAGMA journal_mode=WAL`，
直接拷 `home.db` 会把还留在 `home.db-wal` 里的内容漏掉，产出一份**看起来正常、实际少数据**的备份——
正是本票要修的那类「假绿」。故快照走 `VACUUM INTO`：SQLite 自己出一份包含 WAL 的一致副本，
再读进来装进 zip。临时快照 `.snapshot-*.db` 在 `finally` 里删。

配套：**恢复前清 `home.db-wal` 与 `home.db-shm`**。不清的话，旧 WAL 会在下次开库时盖掉刚恢复的内容。

## 取舍三 · 只做整库恢复，不做物品级合并

老家 `import_preview_payload()` / `import_payload()`（`ops.py:648` 起）做的是**物品级合并**：
读 JSON 导出 → 按同名物品算冲突 → 让用户选「跳过／合并／覆盖」。

本仓**只做整库恢复**：`kind=import` 收 `.zip` 备份，把里面的 `home.db` 整体覆盖回去。
理由两条：

1. 物品级合并要先定义「同名算不算同一件」，那是口径问题，不属于本票（本票是缺陷票，不是设计票）；
2. 整库覆盖是**破坏性**动作，所以配了两道闸：`kind=import-preview` 预告（报「备份含 N 件／当前 M 件／会整库覆盖」，
   不落盘）＋ `kind=import` 必须显式 `confirm:true`，否则 `exit 2`。

代价：**JSON 导出目前只出不进**。`kind=export` 产出的 JSON 能被人拿走看，但本包不认它做导入源。

## 一致的几处（照搬老家的口径）

| 项 | 值 | 出处 |
| --- | --- | --- |
| 备份目录 | 库目录下 `backups/` | `ops.py:26` `BACKUP_DIR_NAME = "backups"` |
| 文件名 | `home_backup_<YYYYMMDD_HHMMSS_mmm>.zip` | `ops.py:530`（老家用 `%f` 六位微秒，本仓毫秒） |
| 保留份数 | 5 | `ops.py:25` `BACKUP_KEEP_N = 5` |
| 覆盖前二次备份 | 有 | `ops.py:500-501`「防误撤销后找不回导入后状态」 |
| 备份历史字段 | `file`／`size`／`created_at`／`days_ago` | `ops.py:571-588` |
| 导出 CSV 列序 | 与 `ops.py:620-621` 逐列相同 | — |

文件名解析**兼容老家的六位微秒后缀**（`parseStamp` 认 `_1`～`_6` 位尾数），所以老仓导出的备份文件
放进本包 `backups/` 目录也能被 `backup-list` 认出来。

## 遗留（另起票，不在本票）

1. **照片进备份**——等 `HOME_PHOTOS_DIR` 迁进本包。
2. **物品级合并导入**——若要恢复老家那套「跳过／合并／覆盖」三选，得先定「同名是不是同一件」的口径。
3. **`backup-list` 的字节数塞在 `count` 字段**——`buildCareList` 的形状只有 `{name, count}`，
   现在把字节数借住在 `count` 里（`已备份：...（4.1 KiB，0 天前）` 的人话在 `name` 里）。
   要让列表真的分列显示，得先给 care 列表加一个通用形状。
