# 更新能力调查：更新一个插件，能不能带到它底下的技能与公共层

调查问题（用户 2026-09-23 提）：爱生活插件的更新能力，能不能做到「更新插件底下的技能」以及「技能底下依赖的 `base-*` 公共层」？记忆里装技能会默认把公共层抬上去，但看代码像是「公共层一个都不会更新」。

调查时间：2026-09-23　工作区 `D:\ilife`　真机使用范围：`~/.dsh/profiles/web`
本文只记事实与读数，不含改动。探针脚本清单见第八节。

---

## 一、结论（三句话）

1. **插件底下的技能：能更新。** 插件包对技能包是**精确 pin**（`packages/plugin-calorie/package.json:34` 一行 `"skill-calorie": "0.3.13"`），装新插件时 pnpm 必须换到那一版技能；`test/skill-pin-lockstep-129.test.mjs` 把「声明必须逐字等于技能包当前版本、必须是精确 `x.y.z`」钉成了门。
2. **技能底下的公共层：能跟上，但只在技能声明的下界动过的时候。** 技能对公共层是 caret 下界（`"base-paint": "^0.3.13"`），而 `tooling/check-base-floor.mjs`（CI 里是 `pnpm base:floor`，`.github/workflows/ci.yml:54`）把这条下界钉成**逐字等于仓内那个 base 包的版本**。技能一换版，锁里那份旧公共层就不再满足下界，pnpm 必须抬——**这是能跟上的唯一机制**。
3. **两个口子仍然成立，用户看到的现象是真的**：① 使用范围自己声明了一条 `"base-link-core": "0.3.7"`（#861 现场修复留下的直依赖），**任何更新动作都不会改它**，顶层因此常驻旧版；② 面板的版本行里那行技能号读的是**插件 manifest 里那条声明**，不是磁盘上那份，面板里**一个字都没有公共层**。

## 五、仍然成立的口子

1. **使用范围里那条直依赖没人管。** 面板的七个更新目标里没有 `base-*`（`update-targets.ts:29-37`），执行器只发「装插件」一条命令；`pnpm add --save-exact <插件>@<版本>` 不会去动使用范围自己的依赖表。那条 `base-link-core: 0.3.7` 是精确版，**永远**不会被任何更新动作改写。
2. **面板答不出「技能／公共层是不是真落后了」。** 面板给那一行的技能号来自插件 manifest 的声明；磁盘上那份技能（以及全部公共层）它不读。也就是说：技能或公共层真的落后时，面板照样会说「已是最新版本 X」。设置页里的两行版本号读的是磁盘真值，与本处口径不同。
3. **公共层单独发版不跟。** 公共层只在技能下界动过时才走（第一节第 2 条）。若公共层单独发了补丁版而技能不跟版，用户这边点「检查更新」永远拿不到那一版——面板只会说插件已是最新。这不是缺陷，是现行机制的边界，但用户侧「刷新公共层」这个诉求它答不了。

## 六、顺带逮到的一处窗口事故（发版侧，非代码侧）

0.3.13 那一窗上架顺序与依赖顺序相反（registry 原始时间戳，UTC）：

```
base-combos        0.3.13 = 2026-09-23T08:12:11Z     （= 本地 16:12:11）
base-link-core     0.3.13 = 2026-09-23T08:12:27Z
dsh-calorie        0.3.13 = 2026-09-23T08:13:07Z     ← 插件先上
skill-calorie      0.3.13 = 2026-09-23T08:13:44Z     ← 它 pin 的技能后上（相隔 37 秒）
base-paint         0.3.13 = 2026-09-23T08:15:03Z     ← 两者都要求的公共层最后上（再隔 79 秒）
skill-bill         0.3.13 = 2026-09-23T08:15:09Z
dsh-life-pack      0.3.13 = 2026-09-23T08:15:36Z
```

复现：`node -e "fetch('https://registry.npmjs.org/base-paint').then(r=>r.json()).then(j=>console.log(j.time['0.3.13']))"` 逐包读 `time`。

含义：这 ≈116 秒的窗口里，点「检查更新 → 装上更新」必定失败——16:13:07–16:13:44 之间 pnpm 找不到 `skill-calorie@0.3.13`，16:13:44–16:15:03 之间找不到 `base-paint@^0.3.13`（技能声明要求 ≥0.3.13）。**这正是「公共层装不上／装不上就都没更新」的另一种形态。**

现场留下的日志（`.scratch/publish-log.txt`，712 行，末尾时间戳 16:12:59）与时间戳互相印证到同一条结论：

```
[16:12:44] TODO base-paint@0.3.13 云端没有        ← 第 693 行：这一刻官方源上确实没有 base-paint@0.3.13
[16:12:56] PLAN 待发 14 个：base-paint@0.3.13 排第一   ← 第 708 行：这一趟的排序是对的
[16:12:57] PKG-BEGIN base-paint@0.3.13            ← 第 710 行
[16:12:59] PKG-FAIL  base-paint exit=1 已发：（空）  ← 第 712 行，这一趟什么都没发成，脚本按 :99 停下
```

而 registry 说 `dsh-calorie@0.3.13` 与 `skill-calorie@0.3.13` 分别在 **16:13:07** 与 **16:13:44** 上了架——都在上面那一刻「云端没有」之后、base-paint（16:15:03）之前。⇒ **是别人（另一趟／另一个动作）把依赖方先发出去的**：这一趟的排序没错、失败即停也没错（`tooling/wizard-publish.ps1:67` 的 `Sort-Object rank, name` 与 `:99` 的 `exit 1`），错在「一趟死在半路之后，剩下的包没有按依赖顺序重排就发了」。

一句口径说明：第 690 行那条 16:11:51 的 `PKG-FAIL … 已发：<15 个包>` 不能当读数用——它列出的包里含 `base-paint@0.3.13`，而两分钟后的第 693 行官方源读回是「云端没有」，registry 又记着 16:15:03；三者不可能同真。日志里掺了不是这一趟自己发出来的名字（`AGENTS.md` 的「里程碑同时追加到 `.scratch\publish-log.txt`」允许别处往同一份日志追加），故本节只认 registry 的 `time` 与第 693／708／710／712 四行脚本自己写的记录。
