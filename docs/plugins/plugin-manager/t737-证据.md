## 四、根因与修法

**根因（复核成立）**：面板总设置区那行「总管 dsh-life-pack · x.y.z」的唯一来源是
`packages/plugin-manager/src/nav.ts` 的手写常量 `MANAGER_VERSION`；定版提交 `6990a706` 只把
`packages/plugin-manager/package.json` 抬到 0.2.7，常量留在 0.2.6，而当时**没有任何门**把两者钉在一起，
于是它无声漂开了一整版（装机上也一样：装机那份包的常量同样是 0.2.6）。

**修法（三条，与票面一致）**：

| # | 动作 | 落点 |
| --- | --- | --- |
| 1 | 常量改到与包版本逐字一致（0.2.6 → **0.2.7**），并在常量上方写明「一起走」由哪条门钉住 | `packages/plugin-manager/src/nav.ts` |
| 2 | 立门：两条断言 —— ① 产物 `dist/nav.js` 导出的常量 ≡ 包描述文件 `package.json` 的 `version`；② 产物 `dist/client.js` 里那行屏幕文案带着同一个版本号 | `packages/plugin-manager/test/version-737.test.mjs`（新增） |
| 3 | 定版走查单补「定版第 0 步」：`dsh-life-pack` 除 `package.json` 还有这一处手写版本号，两者必须一起 bump，漏改即被上面那条门咬住 | `docs/plugins/plugin-manager/t727-发版走查单.md` §3 |

**门为什么这么设计**：

- 取值只从**构建产物**（`dist/nav.js` 的导出）与**包描述文件**（`package.json`）读，**不从源码文本抠字符串**——
  票面点名要求；也因此它咬的是「发出去的那份东西」，不是「源码里写了什么」。
- ② 是**屏幕那行**的产物侧代理：常量对了但 client 束没重出，屏上仍是旧版号（第四节 M4 单独证明了这条咬得住）。
- 门住包内用例（`packages/plugin-manager/test/`）⇒ 进 `pnpm test` 的 glob，CI 的 `build-test` 作业
  （`pnpm build` → `pnpm test`）与本地全量都会跑它；定版那一刻的人工步骤由走查单第 0 步兜住
  （`tooling/check-publish.mjs` 的三道门只管 workspace 外泄、打包清单与装机契约，不管包内常量，故不并进去）。
