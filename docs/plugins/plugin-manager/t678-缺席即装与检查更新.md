## 一、动手前的一条硬发现（裁定前提被证伪）

`#674` 的接法 (a) 写的是「总管宿主半给六个包名各调一次 `createHostUpdate`」；实施时按源码与实测核对，**这条前提只对「更新包装在目标包内部」的那一家成立**：

- 更新包默认读取器从**它自己的文件位置**向上找同名包（`reader.ts:170`、`containingPackage`），再用「找到的包 vs 磁盘已装包」比对（`reader.ts:218-232`）；
- 六个单品与总管是**兄弟包**（都住 `<使用范围>/node_modules/`），向上找不到同名包 ⇒ `runningVersion` 为 null ⇒ 每家电话必回 `unknown-profile`；即便硬给运行版本号，`sameLoadedPackage` 永远为假 ⇒ 一律落 `installation-changed`。

复现命令（只读，跑在仓库外的探针里）：

```sh
node -e "const {createRequire}=require('module');const {pathToFileURL}=require('url');const r=createRequire('C:/Users/辰辰洋洋/.dsh/profiles/web/package.json');import(pathToFileURL(r.resolve('dsh-plugin-update')).href).then(async m=>{const c=m.createHostUpdate({},{pluginId:'probe',prefix:'probe',targetPackageName:'dsh-calorie'});console.log(JSON.stringify(await c.handlers[c.phoneNames.updateStatus]({})))})"
```

读数：`{"ok":false,"error":"unknown-profile","errorKind":"unknown-profile"}`
（同一探针以 `dsh-life-pack` 为目标也是同一读数——因为更新包在 `web` 使用范围里只有一份被提升到顶层的副本，不在任何目标包内部。）

**处置**：不另起接法，仍走「总管统管」，只用更新包**公开的接缝** `readerOverrides.readInstalled`（`host.ts:141`、`:211`）自备环境读数。裁定里用户定的四件（落点、按钮形态、查七家、待重启横幅）一件没变。代价：总管多一个模块（`src/update-env.ts`，约 190 行），其中「包是否完整」那段是照更新包 `reader.ts:84-109` 重写的（它没有对外出口）。

## 二、做出来的形状

| 文件 | 职责 |
|---|---|
| `packages/plugin-manager/src/index.ts` | 宿主半：建电话表 ＋ 把表挂到 `/api/ilife-manager`（`connection.fetch.register`，样板卡路里 #80 写法） |
| `src/update-host.ts` | 电话表：七组更新电话（更新包建，`createHostUpdate`）＋ 两个总管自有电话；懒建（首次调用才读磁盘） |
| `src/update-env.ts` | 环境读数（`readInstalled` 接缝的实现）：使用范围、已装版本、是否按版本号装、指纹绑定、运行版本捕获、技能包 pin |
| `src/update-targets.ts` | 七个更新目标：总管 ＋ 导航表六家（包名不新开定义），七条互不相同的电话前缀 |
| `src/update-contract.ts` | 两侧共认的常量与文案：载体、自有电话名、八种原因码＋过程码的人话、手工兜底命令 |
| `src/update-view.ts` | 纯视图逻辑：缺席判定、一行结论（还没查／已是最新／有新版／装不了）、待重启文案、版本行 |
| `src/update-client.ts` | 面板到宿主的三条流程：取七家表、查一家、装上更新（查→提交→**有界轮询**查状态）、装上缺席包 |
| `src/update-panel.ts` | 面板件：检查更新按钮、七家结果行、待重启横幅、缺席卡的「装上」 |
| `src/dsh-plugin-update.d.ts` | 更新包不带 `.d.ts`，照其源码逐条声明总管用到的出口 |

三条与更新包 README 的对应：第 3 节（三个电话、构建期派生→本仓改成**宿主转交电话名**，见下）、第 8 节（八种原因码→人话）、第 9 节（手工兜底命令）、第 10 节（待重启横幅，文案含新旧两个版本号）、第 11 节（`check-expired` 重查一次再提交）。

两处与文档写法的偏差，理由都写进代码注释：

1. **电话名由宿主转交**，不在面板侧写死：面板既不能 import 更新包（浏览器产物纯度门），写一份派生常量就是两处定义。宿主把 `update.phoneNames` 连同版本行、轮询间隔（`resolveUpdateConfig(...).panelPollMs`）一起交给面板，面板一行字面量都不留。
2. **缺席即装走总管自有电话 `ilife-manager.install`**：更新包的三个电话只管**已装**的包（没装即 `invalid-installation`，`reader.ts:204-210`，`eligible=false` ⇒ `canInstall=false`、凭证为空）。装上缺席包这一件事交回更新包的**执行器** `createUpdateExecutor`（冻结配方：精确版本、官方源、`--save-exact`、路由由核心选），总管不自己拼命令。

## 四、还没做完的两件

1. **依赖进仓要授权**：`packages/plugin-manager/package.json` 要加 `"dependencies": { "dsh-plugin-update": "^0.1.1" }`，且要在仓库里跑一次安装（会改 lockfile）。并发协议 §2.1.1 明令「禁止在仓库内跑包管理器安装命令，唯一例外：编排者持锁显式授权」，故停手上报，没自行装。装完之后：`smoke.test.mjs` 恢复绿、`tsc -b` 与客户端产物门照旧、仓库外实证可搬进仓内。
2. **真机三条验收没做**：它们要先把新版本发上 npm 再装进使用范围（`dsh plugin --profile web add dsh-life-pack@<新版> --config.minimumReleaseAge=0 --registry=https://registry.npmjs.org`）并重启宿主——这是发版与动真机环境的动作，等编排者定（`#697` 已发过 `skill-chef@0.2.0` 的先例）。
