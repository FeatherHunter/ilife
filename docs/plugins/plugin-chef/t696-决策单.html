决策一：四家技能侧的「配置面」归谁做

前因

票面「交付物路径」只列了四个插件包的 src/；「不许动」写着不许改这四家的技能侧取数（那是隔壁票 #695 的地盘）。可是验收第 1 条要的是改得动：用户改一项、保存、宿主重启后仍在。

而配置文件的读写实现按 #675 冻结口径住在公共层 base-link-core/src/config/（#694 已交付），插件却又不许 import base-*——两道门一夹，插件自己写 YAML 就等于把配置实现抄第二处（破结构纪律铁律一）。

决定性边界：test/plugin-p10-boundaries.test.mjs:52 写死「单品源码不许 import base-／skill- 包」，而票面验收第 5 条要求这条门不红。

⇒ 只剩一条既不改门、又不抄实现的路：页面 → RPC → spawn 技能 CLI → 技能侧调公共层。技能侧必须有一个「配置面」才能闭环。

先例：卡路里那张票（#676）就是这么收的——技能侧配置面由那张票自己补落（skill-calorie/src/config.ts ＋ src/cli/config.ts ＋ cmd_read.ts 拦截），并在证据件里点名「票面交付物路径漏写了这一处」。「技能侧路径常量改读配置 ＋ 删环境变量」则留给另一张票（卡路里是 #718，四家是 #695）。

决策四：验收怎么出读数（含 ≥90 那条视觉打分）

前因

票面第 4 条写的是「vision_router 逐页打分 ≥90，做法：打开设置面板 → 桌面截图 → 逐页打分」。问题在于：本机那个 GUI 上装的不是本仓——127.0.0.1:43120 用的 profile 装的是 npm 发布版（大厨／居家／备忘／作息都还是 0.2.0），所以在真宿主面板上今天看到的是老页面。

先例：上一张面板票（#679）遇到同一件事，你当时的裁决是「真机那条验收换成对抗式审查」；那张票用的是渲染台——把真产物渲成真 DOM、量出版式读数、再截图。

三条路

A · 渲染台 ＋ 截图 ＋ vision 逐页打分 推荐

照 #679 的渲染台：物化四家 dist/client.js（真产物）→ 用 stub loader ＋ hooks 替身渲成真 DOM → 出四页整页图 → vision 逐页打分；「点得到、改得动」做成量出来的读数（真调输入框的 onChange、保存与重置按钮的 onClick）。「保存后重启宿主仍在」三连（改前／改后／新进程再读）走探针脚本，路径是插件 dist/bridge.js → 技能 CLI 三个配置 key → 盘上 YAML，跑完还原不留痕（照 t676-读数.mjs）。

利
  • 全在本仓、可重跑、可入证据件
  • 不动你正在用的 GUI，不需要装包授权
  • 三连读数走的就是面板按按钮那条真路
弊
  • 不过 DSH 的槽位渲染、不点链接——「真机」那一层进不了读数（会写进证据件的边界一节）
