决策一：配置读写走哪条路

前因

设置页要能读、改、重置 ~/.ilife/calorie.yaml。而按 #675 的冻结口径，读写实现住 base-link-core/src/config/（#694 已交付）。剩下的问题只有一个：谁来调这套函数。

决定性读数：边界门 test/plugin-p10-boundaries.test.mjs:52 写死了单品（六个 plugin-*）源码不许 import base- 包； 而本票验收要求这道门不红。

⇒「插件宿主半直接 import base-link-core」这条路，本身与验收冲突：要么改掉那条冻结断言，要么从它的扫描盲区绕过去（那是自欺，我不做）。

两条路

A · 插件直连公共层 第一轮席的方案

插件宿主半自己读写 YAML，再把值注入 spawn 出去的技能子进程环境。

利
  • 技能侧不用加「配置面」小件
  • 值立刻能注入子进程（那 2 项有接缝的先生效）
弊
  • 要你点头改一条冻结断言（或绕过它的盲区）
  • 要你持锁授权一次 pnpm install（协议 §2.1 禁自行安装）
  • 本票会开出「插件 → 公共层」的第一条连线，六家插件都要跟着改口径

B · 经技能 CLI 配置面 推荐

技能侧加一个小面（读／写／重置三个 key），页面走既有通道：面板 → RPC → spawn 技能 CLI。

利
  • 零授权、零依赖安装，今天就能开工
  • 不碰任何边界门，验收第 4 条天然成立
  • 技能侧本票已经要做，配置面正好一起落；六家照抄时只抄一个小件
  • 技能改读配置后，值自然生效——不需要往子进程塞环境变量
弊
  • 每次读写多起一次技能子进程（既有惯例，百毫秒级）
  • 卡片「交付物路径」漏写了技能侧那 3 个件（我会在票面记一笔）

➡️ 建议走 B：它在「不改门、不装依赖」的前提下满足全部验收；A 想省的那一个小件，代价是改一条冻结边界 ＋ 一次持锁授权。
